# Radeon X1300 (RV515, 1002:7146) in the ati family

Date: 2026-11-20

Status: phase 0 started 2026-11-21. The card is reachable: the
`V9X-EY69HT` reporter
([record](../decisions/2026-11-20-rv515-x1300-vbe-field-report.md)) is
remote-help machine `M-5CAPM3`, now running 0.57.0 `vbe` again
([phase 0 record](../decisions/2026-11-21-m-5capm3-rv515-phase0.md)).
Measured so far: a 256 MiB aperture at `D0000000`, a 64 KiB register
window, EDID preferring 1920x1080 with no such VBE mode cached. V9XGDI
and V9XMSW pass; V9XDDP is unread because the machine's USB network
adapter dropped out, and the owner is replacing it. Everything else
below is read from source, not measured.

Target: the RV515 (`1002:7146`, Radeon X1300 class) as a chip generation
in the one `ati` family (`one-family-per-vendor`), built from the RS690
tree (`src/chipsets/ati/rs690/`, `d3d_rs690*.c`, `eng_rs690.c`,
`rs690_scanout.c`). The RS690 plan's 2026-11-04 decision names the
R300-R500 discrete cards as that tree's next users
([`ati-rs690-x1200.md`](ati-rs690-x1200.md)). Other RV5xx/R5xx ids
(RV516, RV530, RV560, RV570, R520, R580) wait until one is measured;
the same design rule (`same-design-fix-applies-to-all`) means a working
RV515 path is their starting point.

## Sources

The RS690 collection in `build\external\rs690\` (outside version
control) already covers this chip:

- `linux-radeon\`: `rv515.c`, `rv515d.h`, `r500_reg.h`, `r520.c`,
  `r420.c`, `r300.c`, `r100.c`, `avivod.h`.
- `xf86-video-ati-6.14.6\`: the UMS `ACCEL_MMIO` path, which drives R500
  2D and Render (3D) with register writes alone, R500 fragment programs
  included.
- Mesa 22.3 `src/gallium/drivers/r300/` in `build\external\audit\mesa\`:
  the R500 fragment encoding (`r500_fragprog*`) and per-chip caps.

Not yet downloaded: AMD's *R5xx Acceleration* guide (v1.5) and the M56
register reference on x.org. Both describe R5xx directly and should be
fetched before phase 5.

## What carries over from the RS690, and what does not

| | RV515 per the sources | Against the RS690 tree |
|---|---|---|
| 2D engine | R100-style blit (`r100_copy_blit`), the same `DP_GUI_MASTER_CNTL` / `DST_PITCH_OFFSET` register file | `rs690_2d.c` should apply as is. A write probe confirms it |
| Display | AVIVO, `D1GRPH_*` 6100h-, `D1CRTC_STATUS` 609Ch (`r500_reg.h`); the RS690 plan already cites RV515 as the reference | `rs690_scanout.c` should apply. Whether the VBE mode scans out through D1GRPH is read first, as on the RS690 |
| Memory | Discrete VRAM (X1300 boards: 128 or 256 MiB). VBE reports 16 MiB (`V9X-EY69HT`) | New: real size from `CONFIG_MEMSIZE`, then a heap beyond 16 MiB |
| MC registers | `MC_IND_INDEX` 0070h / `MC_IND_DATA` 0074h, index written as `0x7f0000 \| reg`, restored to 0 (`rv515.c:196-208`, `rv515d.h:36-38`) | RS690 uses 0078h/007Ch with index 7Fh. New access routine; never write the FB location (the BIOS has POSTed) |
| BARs | Unread. Linux maps the register BAR by `pci_resource` like any discrete Radeon | `rs690_hw16.c` reads BARs with Evergreen's 64-bit-aware routine and its alignment checks (BAR0 256 MiB, BAR2 128 KiB). Whether an X1300 meets them is unknown; may need its own read |
| Pipe setup | `rv515_gpu_init`: `r420_pipes_init`, then `R400_GB_PIPE_SELECT` and `DST_PIPE_CONFIG` folded into PLL register 0Dh (`rv515.c:141-162`) | The RS690 had one pipe and needed none of this. A PLL write is a design change to discuss before doing |
| 3D init | `RADEONInit3DEngine` with `IS_R500_3D`: `R500_SU_REG_DEST` = pipe mask, `R500_VAP_INDEX_OFFSET` 0 (`radeon_commonfuncs.c:97-104`) | Small additions to the RS690's port |
| Vertex stage | `has_tcl = TRUE` for every non-IGP Radeon (`radeon_driver.c:2178-2189`), so xf86 runs the VAP with `PVS_BYPASS` clear and loads a pass-through vertex program (`radeon_commonfuncs.c:199-210`) | The RS690 runs in bypass. Whether bypass also works on the RV515 is a measurement; the fallback is xf86's pass-through program |
| Fragment ISA | R500 US: programs loaded through `R500_GA_US_VECTOR_INDEX` / `_DATA`, `R500_US_CODE_ADDR` (`radeon_exa_render.c:1950-2047`) | **Rewrite.** `rs690_3d.c`'s shader assembler emits R300 code. The register-PIO upload exists in UMS, so no CP is needed |
| Texture, Z, blend | R300-class registers, R500 adds `R500_US_FORMAT0_*` for texture formats | Mostly shared; every state is re-probed |
| CP | PM4 ring, needs `R520_cp.bin` | Not needed for any phase here; deferred with its licensing, as on the RS690 |
| Mode setting | AtomBIOS | Keep `vbe-lfb` |

## Phases

0. **Get a card.** A PCIe X1300 (or another RV5xx) in a machine we can
   drive: W9QI0DAD or M-NZHWBR have PCIe slots. Baseline on tier-0
   `vbe`: enable-ok, mode list (`V9XMODES.INI`), GDI and mode cycles,
   the 3D probes on the software engine. Record the BIOS's VBE memory
   figure against the board's real size.
1. **Identity.** Claim `1002:7146` in `packaging/families/ati/family.psd1`
   and `v9x_ati_device_ids[]` as tier-0 with no hooks, so the INF names
   the card. Function 1 (`7166`) stays unbound; problem 22 on it is
   normal.
2. **Read-only register probe**, the RS690's `V9XRSMM` with the RV515's
   id and MC access. Built, not yet run (2026-11-21):
   `scripts\build-rv515-mmio-probe.ps1` makes `RVMM.VXD` and
   `V9XRVMM.EXE` (`tools\diag\rv515_mmio_probe*`), report
   `C:\V9XDIAG\V9XRVMM.INI`. Plain runs write nothing to the device;
   `/mc` adds the MC indexed reads, which write `MC_IND_INDEX` (read
   select only) and put back the value found. Run plain first, then
   `/mc`. It reads every BAR's value but not its size, which needs
   configuration writes; the 256 MiB aperture came from Device Manager.
   It reads `CONFIG_MEMSIZE`,
   `CONFIG_APER_SIZE`, `RBBM_STATUS`; the 2D state block when idle;
   `R400_GB_PIPE_SELECT`, `DST_PIPE_CONFIG`, `GB_TILE_CONFIG`; every
   `D1GRPH_*` / `D1CRTC_*` at three VBE modes; `CP_CSQ_CNTL`,
   `CP_RB_CNTL`; through `MC_IND_INDEX`, the FB location and
   `RV515_MC_CNTL` (channels). Prove the GPU address of the VBE scanout
   and the pipe count.
3. **2D engine.** The RS690's write probe with the RV515 id: fill and
   copy at 8, 16 and 32 bpp, overlaps both ways, byte-exact. Then the
   engine32 ops under the existing engine type if the probe matches.
4. **Flips and vblank** through `rs690_scanout.c`, if phase 2 shows the
   VBE mode on D1GRPH.
5. **3D by PIO.** Probe first: the 3D init with the R500 additions, the
   vertex stage tried in bypass and, failing that, with xf86's
   pass-through program; one flat triangle through `SE_VF_CNTL` /
   `SE_PORT_DATA0` with an R500 pass-through fragment program, read
   back. Then an R500 shader assembler, host-tested against Mesa's
   encodings, covering what the RS690's covers (modulate, decal,
   DECALALPHA, ADD, vertex fog, colour key). Then textures, Z, blend,
   alpha test, mipmaps re-probed, and the Direct3D HAL on the `r3d`
   interface, in the RS690's split (`d3d_rv515_map.c` host-tested,
   `d3d_rv515.c`). Whether the map can be shared with the RS690's is
   decided once both exist.
6. **Heap beyond 16 MiB** from the measured `CONFIG_MEMSIZE`.

## Unknowns that need a measurement

- Whether the BARs fit the 64-bit read the RS690 borrows from Evergreen.
- Whether the VAP accepts `PVS_BYPASS` on a TCL chip.
- Whether the engines are usable as POSTed, or need `rv515_gpu_init`'s
  pipe setup (a PLL write) or a soft reset.
- Whether the RS690's per-draw CPU idle wait (2D before 3D) is needed
  here too.
- PIO throughput on a discrete card. The RS690 measured 1781 in 3DMark
  2000 against 7 on software; a faster CPU and card may make the CP
  worth its microcode.
- The board's VRAM size, and whether VBE's 16 MiB is a BIOS cap or the
  aperture it maps.
