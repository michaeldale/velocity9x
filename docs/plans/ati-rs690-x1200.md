# Radeon X1200 IGP (RS690, 1002:791F) in the ati family

Date: 2026-11-04

Status: Phase 0 done (tier-0 `vbe` on M-GB8KRE,
[record](../decisions/2026-11-03-m-gb8kre-rs690-vbe-first-look.md)).
Phase 2 read on the chip
([record](../decisions/2026-11-04-rs690-register-probe.md)): VBE scans
out through `D1GRPH` at GPU address `78000000` (the frame buffer's
base), the 2D engine is idle, the CP is off, one pipe, 128 MiB carved
out. Phase 3's write probe passed
([record](../decisions/2026-11-04-rs690-2d-write-probe.md)): fills and
overlapping copies byte-exact at 8, 16 and 32 bpp from the pure builder
`rs690_2d.c`, with no reset or CP work. Next: the engine32 ops for
DirectDraw. Other register facts below come from Linux `radeon` and
xf86-video-ati source.

Target: the RS690 IGP (`1002:791F`, "ATI Radeon X1200") as a new chip
generation in the one `ati` family (`one-family-per-vendor`), with its
own module tree `src/chipsets/ati/rs690/`. Test machine: `M-GB8KRE`
(Sempron 210U, Windows 98 SE, DirectX 6.1), reached only through the
remote-help relay. The owner asked for 3D; this plan gets there by way
of the 2D engine, because the 2D engine and the 3D engine share the same
register file, FIFO and idle rules, and the 2D engine is the cheaper
place to prove them.

## What the sources settle

| | RS690 per the sources | Consequence |
|---|---|---|
| Family | `CHIP_RS690`; xf86-video-ati's `IS_R300_3D`, not `IS_R500_3D` (`radeon.h:284-290`); Mesa: not `is_r400`, not `is_r500` (`r300_chipset.c:170`) | The fragment ISA is R300's (Mesa `r300_fragprog`), not R500's |
| Vertex hardware | None: `has_tcl = FALSE` for RS690 (`xf86-video-ati-6.14.6/src/radeon_driver.c:2178-2186`); the VAP runs with `PVS_BYPASS` (`radeon_commonfuncs.c:196-199`) | Fine for Direct3D's pre-transformed vertices. DDI T&L stays on the CPU, as on every other chip here |
| Memory | No dedicated VRAM (Mesa winsys); UMA carve-out, optionally sideport (`rs690.c:157-176`). `CONFIG_MEMSIZE` 00F8h in bytes | VBE reports 16 MiB; the 128 MiB BAR0 suggests more. `read_video_memory` hook once measured |
| GPU address of VRAM | `MCCFG_FB_LOCATION`, MC register 100h, reached only through `MC_INDEX` 0078h / `MC_DATA` 007Ch (`rs690.c:651-672`) | Reading it is an index write. Restore the index to 7Fh as Linux does; never write the location (the BIOS has POSTed) |
| 2D engine | **Present.** Linux's RS690 copy is `r100_copy_blit` (`radeon_asic.c:731-732`); UMS EXA drives it by MMIO: `DP_GUI_MASTER_CNTL` 146Ch, `DST_PITCH_OFFSET` 142Ch, `SRC_PITCH_OFFSET` 1428h | DirectDraw fill and blit without microcode, Rage 128 style. The register file descends from the Rage 128's; the existing `rage128/` code is the nearest model, not shared code |
| 2D cache flush / idle | R300+: `RB2D_DSTCACHE_CTLSTAT` 342Ch, `RBBM_STATUS` 0E40h | `wait_idle`, and a flush before the CPU reads what the engine drew |
| 3D without the CP | UMS `ACCEL_MMIO`: `SE_VF_CNTL` (2084h, `R300_VAP_VF_CNTL`) then each vertex dword to `SE_PORT_DATA0` 2000h (`radeon_exa_render.c:2453-2470`, 2258-2275) | **Direct3D can be register PIO**, like the Rage 128 PIO path. No CP microcode to ship, no ring, no GART. Throughput is bounded by PIO writes over the PCIe link; to be measured |
| 3D engine init | `RADEONInit3DEngine` (`radeon_commonfuncs.c:60-250`): `GB_TILE_CONFIG` 4018h, pipe count from `R400_GB_PIPE_SELECT` 402Ch for RS690 (`radeon_accel.c:474-485`), VAP in bypass | A port of that sequence, host-checked as data |
| CP | PM4, `r300_gfx_ring`, needs `RS690_cp.bin` | Not needed for any phase here; deferred, with its licensing |
| Display | AVIVO (RV515-class): `D1GRPH_PRIMARY_SURFACE_ADDRESS` 6110h, `D1GRPH_PITCH` 6120h, `D1GRPH_UPDATE` 6144h (bit 16 lock), `D1CRTC_STATUS` 609Ch, `D1VGA_CONTROL` 0330h (`r500_reg.h:291-480`) | Flips and vblank as on Evergreen, other offsets. Whether VBE modes run through D1GRPH or the VGA path is the first thing to read |
| Mode setting | AtomBIOS, as on Evergreen | Keep `vbe-lfb` |

## Phases

0. **Baseline (done).** Tier-0 `vbe`: enable-ok, 35 modes, GDI and mode
   cycles pass, the 3D probes pass on the software engine except the
   cull checks it declines by design. `/pal8` stops at 320x200x8.
1. **Identity.** Claim `1002:791F` in the `ati` manifest and
   `v9x_ati_device_ids[]` as a tier-0 device with no hooks, so the INF
   names the card. Other RS690/RS740 ids wait for a survey of one.
2. **Read-only register probe** (`V9XRSMM`), modelled on the Evergreen
   one: a VxD that maps the 64 KiB register BAR and reads a list of
   offsets twice, refusing anything that is not `1002:791F`. Read:
   every BAR; `CONFIG_MEMSIZE`, `CONFIG_APER_SIZE`, `RBBM_STATUS`,
   `HOST_PATH_CNTL`, `SURFACE_CNTL`; the 2D state block (1400h-17FFh,
   behind the FIFO, so only when `RBBM_STATUS` says idle); the GB block
   including `R400_GB_PIPE_SELECT`; `D1VGA_CONTROL`, `VGA_RENDER_CONTROL`
   and every `D1GRPH_*` / `D1CRTC_*` at three VBE modes; `CP_CSQ_CNTL`
   and `CP_RB_CNTL` (is the CP idle, as expected under VBE?). A second
   mode, `/mc`, reads `MCCFG_FB_LOCATION`, `K8_FB_LOCATION` and
   `MC_MISC_UMA_CNTL` through `MC_INDEX`, restoring it. Prove the GPU
   address of the VBE scanout.
3. **2D engine.** A write probe first: one solid fill and one
   screen-to-screen copy at 8, 16 and 32 bpp, byte-exact readback, an
   overlapping copy in both directions, `wait_idle` by `RBBM_STATUS`.
   Then the engine32 ops (`fill`, `copy`, `wait_idle`) under a new
   engine type, packet-free register builders host-tested first.
4. **Flips and vblank** via `D1GRPH_PRIMARY_SURFACE_ADDRESS` and
   `D1CRTC_STATUS`, if phase 2 shows the VBE mode on D1GRPH.
   Phases 3 and 4 run on M-GB8KRE (2026-11-05, boot 56): V9XDDP fill,
   copy and overlaps PixelOk=1, 23 flips taken by D1 at the blank
   (`docs/decisions/2026-11-05-rs690-flips.md`). Monitor not looked at.
5. **3D by PIO.** A probe first: `RADEONInit3DEngine`'s sequence, then
   one flat triangle through `SE_VF_CNTL` / `SE_PORT_DATA0` with an R300
   fragment program that passes the colour through, read back. Then the
   Direct3D HAL on the `r3d` interface: flat and Gouraud, Z, textures
   (R300 texture formats), the blend and alpha-test states, culling in
   hardware. OpenGL and Glide follow through the ICD and the Glide
   layer, as on the Rage 128.
   The probe passed on M-GB8KRE (2026-11-05, 16 and 32 bpp): quad, flat
   and Gouraud triangles where the model says, the 2D engine still exact
   afterwards (`docs/decisions/2026-11-05-rs690-3d-draw-probe.md`,
   builder `rs690_3d.c`). Next: textures in the probe, then the HAL.
   Textures passed the same day: decal and wrap byte-exact, modulate
   within a step, bilinear on the right texels with weights up to 0.018
   coarse (`docs/decisions/2026-11-05-rs690-texture-probe.md`). Then the
   Direct3D state: D3DTLVERTEX taken as it is, Z16, blend, alpha test,
   cull and perspective all as modelled
   (`docs/decisions/2026-11-05-rs690-z-blend-probe.md`). Next: the HAL
   glue on the `r3d` interface, in the Rage 128's split: a host-tested
   `d3d_rs690_map.c` from the neutral draw to `struct v9x_rs690_3d_state`
   (D3DCULL_CCW = CULL_BACK), then `d3d_rs690.c` for caps, texture and
   Z placement and PIO submission behind `eng_rs690.c`'s idle and flips,
   and `D3D` in the row's EngineCaps.
   Built and booted the same day: V9XD32 passes at 32 and 16 bpp (runs
   6-9) after three fixes the probes had missed. Specular is on by default
   in DX5, so it had to be built. The X byte of an XRGB target must be
   masked. Texture rows must be 64 bytes apart: the RS690 steps 64
   whatever TX_FORMAT2 says
   (`docs/decisions/2026-11-05-rs690-d3d-hal-first-boot.md`). The stray
   writes to physical RAM at 0600xxxxh (T15) were a 3D draw starting
   while a 2D fill still ran. `WAIT_UNTIL` does not hold the engine back
   with the CP off, so the HAL now polls for idle on the CPU before each
   draw (boot 71: T15 clean, eight runs)
   (`docs/issues/2026-11-05-rs690-t15-heap-words-zeroed-once.md`). Fog
   followed: vertex fog in the shader as three ALU instructions, measured
   in the probe at both depths. The presubtract form read wrong
   components; SRC2_AAA reads the alpha unit's source. No fogged draw has
   gone through the HAL yet, since V9XD32's fog tests need DirectX 7
   (`docs/decisions/2026-11-05-rs690-fog-probe.md`). DECALALPHA and ADD
   followed, through one shader assembler of up to five instructions.
   They are measured in the probe; no application draw has used them yet
   (`docs/decisions/2026-11-06-rs690-decalalpha-add.md`). Colour key
   followed for RGB565 textures, through the texture unit's chroma key:
   FORCE kills the fragment, and the key compares the stored texel, alpha
   bits included, so alpha formats stay refused
   (`docs/decisions/2026-11-06-rs690-colour-key.md`). V9XD32's new T20
   then drew all four through the HAL, passing at 32 and 16 bpp; the
   software renderer fails it, and other chips may too
   (`docs/decisions/2026-11-06-rs690-d3d-t20.md`). Mipmaps followed, in
   the layout the sampler was measured to read (64-byte rows, levels
   packed, TXPITCH_EN off), proven through DX5 by V9XD32's new T21
   (`docs/decisions/2026-11-06-rs690-mipmaps.md`). The Rollcage demo
   (Direct3D, DX6) ran through the HAL with nothing refused; the per-draw
   idle wait takes about 38% of the CPU time in its draws
   (`docs/decisions/2026-11-06-rs690-rollcage-and-idle-wait.md`). The
   wait is now taken only after the HAL's own 2D work (GDI does not use
   this engine): T15 stays clean, and a Rollcage draw costs 17% less CPU,
   the rest of the old wait moving into FIFO waits. With DirectX 8.0
   installed, 3DMark 2000 scored 1781 on the HAL and 7 on the software
   renderer, with nothing refused, so PIO does beat software on this
   Sempron (`docs/decisions/2026-11-06-rs690-dx8-3dmark2000.md`).
6. **Heap beyond 16 MiB** once `CONFIG_MEMSIZE` and the carve-out are
   measured.

## Unknowns that need a measurement

- Whether the 2D and 3D engines are usable as POSTed, or need the
  `RBBM_SOFT_RESET` and clock gating Linux does (`rs600_asic_reset`,
  `r300_clock_startup`).
- Whether a register write through the BAR is visible to a following
  read without a flush (the MMIO path has no `HDP` flush on R300; the
  2D destination cache has one).
- Whether the VBE mode set (AtomBIOS) disturbs the 2D/3D engine state.
- Whether the DOS box leaves engine and scanout state alone. The owner
  reports DOS prompts now work under `vbe`, so this has a baseline.
- PIO vertex throughput, and whether it beats the software engine on a
  1.5 GHz Sempron at all. Answered for 3DMark 2000: 1781 against 7
  (2026-11-06).
- The carve-out size and where it sits in system memory.

## Decisions

- 2026-11-04, Michael: start on 3D. The tree is also the starting point
  for RS600/RS740 and the R300-R500 discrete cards should one turn up:
  the 2D engine and 3D core are the same family; the display and memory
  blocks differ.
- 2026-11-06, Michael: the branch stays out of the 0.36.0 release and
  merges after it. Before the merge, V9XD32's T20 and T21 (which count
  toward Failures) are run on the other chips, or limited to chips that
  publish those caps. Done the same day: T20/T21 now count only what the
  HAL advertises (68c45d5c), and the merged tree booted on M-GB8KRE
  (RS690), the Haswell 4570 (intel-gma) and A8U4I5 (Rage 128 Pro) with
  V9XD32 as before the swap on each; merged to main.
