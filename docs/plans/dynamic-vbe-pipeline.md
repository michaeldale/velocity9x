# Dynamic VBE pipeline

## Purpose

Finish Velocity9x's generic VBE path so the modes offered by the video BIOS
become one bounded runtime mode table consumed by GDI, Display Properties and
DirectDraw. Add EDID only as a preferred-geometry hint. Preserve the current
static family tables as the fallback when discovery is unavailable or suspect.

This is a new implementation plan. The driver work must be written from the
VBE specification and Velocity9x's own interfaces; no third-party driver source
is to be copied.

This document supersedes the dynamic-discovery portions and the former EDID/DDC
scope cut in `docs/plans/high-depth-dynamic-modes.md`. Completed high-depth work
and its hardware evidence remain valid.

## Current state

The repository is part-way to this design:

- `src/minivdd32/loader.asm` collects VBE `4F00h` once at `Device_Init`, but it
  queries a fixed seven-mode list rather than walking `VideoModePtr`.
- Mini-VDD API version 1 exposes controller information, cache status and one
  mode selected by VBE number. It does not enumerate the cache or expose VBE 3
  linear stride and colour fields.
- `include/velocity9x/vbe_parse.h`, `src/common/vbe_parse.c`,
  `include/velocity9x/vbe_modes.h` and `src/common/vbe_modes.c` already contain
  host-tested parsing, filtering, merging and DirectDraw-subset policy.
- The C mode builder is not linked into the display driver. `ddi.c` and
  `dd16.c` still consume `v9x_hw16.modes`, the static family table.
- The DirectDraw shared ABI already has `mode_count` and room for 32 modes, but
  `dd16.c` publishes the first 32 static rows and synthesizes masks from depth.
- Display Properties learns modes from `MODES\<bpp>\<width>,<height>` registry
  keys generated by the INF. It has no runtime inventory source.
- The DOS survey can read EDID through VBE `4F15h`; the installed driver does
  not collect or parse EDID.
- Mini-VDD VBE collection is build-gated per family. It is enabled where the
  VBE cache is required and disabled for families for which the boot-time BIOS
  calls are all risk and no benefit. That gate remains.

## Non-negotiable invariants

1. **Failure means the static table.** A bad controller block, invalid mode-list
   pointer, missing terminator, failed `4F01h`, full cache, unavailable DDC or
   invalid EDID must never leave a partial table as the only table. Hardware
   initialization may still refuse when the controller or active baseline
   probe cannot provide prerequisites such as `PhysBasePtr`; that is the
   existing staged failure, not permission to trust partial discovery.
2. **The mini-VDD returns facts, not policy.** It bounds BIOS access, checks
   return status and caches fields. Host-tested C decides whether a record is
   usable and how it is merged.
3. **No late BIOS calls.** All buffered `4F00h`, `4F01h` and `4F15h` calls occur
   at `Device_Init`. The protected-mode API remains a locked-data lookup.
4. **No unbounded pointer walk.** BIOS mode-list access has fixed word, query
   and cache limits. Every count exposed across an ABI is validated again by
   its consumer.
5. **Configured modes win.** EDID does not silently replace a valid user mode.
   It is used only for fallback/recommendation among modes already accepted
   from VBE.
6. **No timing generation.** EDID cannot add a mode, select a refresh variant
   or program a CRTC. It can only identify a preferred width and height that
   already exist in the runtime table.
7. **Dynamic registry ownership is narrow.** The synchronizer deletes or
   replaces only mode keys carrying a Velocity9x dynamic marker. INF baseline
   keys and keys owned by another driver are never pruned.
8. **The LFB path stays linear.** Banked support, if pursued, is a separate
   family and package. It adds no conditional banking to the existing GDI or
   DirectDraw fast paths.
9. **Mixed binaries fail cleanly.** A display driver and mini-VDD with
   different API contracts may fall back or refuse tier-0 initialization, but
   may not interpret registers using the wrong layout.
10. **Boot-call risk stays explicit.** `Exec_Int 10h` has no timeout. Existing
    per-family `MiniVddVbeCollect` gating and pre-call serial markers therefore
    remain release gates, not optional diagnostics.

## End-to-end design

```text
VBE 4F00h
  -> bounded copy of VideoModePtr list
  -> checked 4F01h calls and fixed mini-VDD cache
  -> mini-VDD API v2 indexed enumeration
  -> host-tested parse/admit/merge policy
  -> runtime mode table + parallel colour masks
       -> GDI lookup / ValidateMode / Enable / ReEnable
       -> DirectDraw shared mode table
       -> validated mode-inventory file
            -> marked registry MODES keys
            -> native Display Properties enumeration

VBE 4F15h EDID block 0
  -> header + checksum + descriptor validation
  -> preferred width/height hint
  -> exact match in the accepted runtime table, or no hint
```

## Data contracts

### Mode-list and cache limits

Use separate limits so one corrupt BIOS field cannot turn into an unbounded
boot delay or overwrite:

- `V9X_VBE_MODE_LIST_MAX = 128` mode numbers copied from `VideoModePtr`.
- `V9X_VBE_MODE_QUERY_MAX = 128` `4F01h` calls.
- `V9X_VBE_CACHE_MAX = 64` list-derived records returned for enumeration.
- `V9X_VBE_BASELINE_PROBE_MAX = 16` family baseline records reserved for
  active-mode lookup when they were absent from, or could not be reached
  through, the BIOS list.
- `V9X_MODE_TABLE_MAX = 64` accepted GDI rows, which already exists.
- `V9X_DD_MODE_COUNT = 32` DirectDraw rows, which already exists.

The mode list is valid only when all of the following hold:

- `4F00h` returns `AX=004Fh` and a `VESA` signature.
- The controller version is at least VBE 2.0 for the LFB family.
- `VideoModePtr` is non-null and resolves to addressable real-mode memory.
- Reading each word stays below the first-megabyte boundary after segment plus
  offset arithmetic.
- A `FFFFh` terminator appears within 128 words.
- A listed value other than the terminator has no set-mode flag bits in its
  high two bits. Duplicate mode numbers are ignored after their first entry.

Copy the complete bounded list to staging storage before making any `4F01h`
call. Some BIOSes point `VideoModePtr` into the controller buffer, which the
mode-information calls will reuse and overwrite.

An unterminated or invalid list sets a diagnostic reason and contributes zero
dynamic records. The static table remains available.

The static LFB path still needs `4F01h` data for its active baseline mode,
especially `PhysBasePtr`. Generate a bounded baseline mode-number include from
the selected family manifest when building the mini-VDD. After the list walk,
query any required baseline number not already cached. Store those answers in a
separate reserved baseline-probe cache and expose them only through by-mode
lookup, not indexed dynamic enumeration. On an invalid mode list, run just
these bounded probes after a credible `4F00h` response. This preserves today's
static recovery path without retaining a hand-written seven-mode list in
`loader.asm`.

### Cached mode record

Replace the parallel seven-element arrays with a fixed packed record. Keep the
layout in a shared assembly include used by both `loader.asm` and
`runtime.asm`. One record contains:

- VBE mode number;
- mode attributes;
- legacy `BytesPerScanLine`;
- VBE 3 `LinBytesPerScanLine`;
- width and height;
- memory model;
- physical framebuffer base;
- storage depth (`BitsPerPixel`);
- significant colour depth;
- red, green, blue and reserved mask size/position pairs;
- flags describing whether linear or legacy mask fields supplied the layout.

The flags also identify whether the record came from the terminated BIOS list
or from the generated baseline rescue probes. Only list-derived records are
enumerated into new runtime rows.

`storage_depth` is the number of bits occupied by one pixel in memory.
`significant_depth` is the sum of red, green and blue mask widths; reserved or
unused bits are not counted. Examples:

| Format | Storage | Significant |
|---|---:|---:|
| palettized 8 bpp | 8 | 8 |
| RGB 5:6:5 | 16 | 16 |
| packed RGB 8:8:8 | 24 | 24 |
| XRGB 8:8:8:8 | 32 | 24 |

For VBE 3 linear modes, prefer `LinRedMaskSize` through
`LinRsvdFieldPosition`. If all linear colour fields are zero, fall back to the
legacy colour fields and record that fallback. For VBE 2, use the legacy
fields. Preserve the reserved pair even though DirectDraw will continue to
publish `dwAlphaBitMask=0`; it is needed to validate storage layout and derive
significant depth.

Before each `4F01h` call, zero the full mode-information scratch area. Cache a
record only when `AX=004Fh`; a failed call must not reuse the preceding mode's
bytes. Ring 0 may cheaply reject unsupported records, zero dimensions, an
unknown memory model and storage depths outside 8/16/24/32 so text and planar
modes cannot fill the cache. All layout, VRAM and LFB admission remains in C.

### Mini-VDD API version 2

Bump `V9XMINI_API_VERSION` and define the constants once in a shared include.
The new display driver requires the exact v2 contract for enumeration. Keep a
clean diagnostic distinction between no mini-VDD, wrong version, scan invalid,
index out of range and a valid empty cache.

The API needs these operations:

- `HANDSHAKE`: magic and exact contract version.
- `CONTROLLER`: VBE version, total-memory blocks and controller-valid flags.
- `STATUS`: list state, listed/query/cached counts, baseline-probe count,
  truncation/failure flags and EDID state.
- `MODE_AT(index)`: mode number, attributes, geometry, both strides, physical
  base, memory model and storage/significant depths.
- `MODE_MASKS(index)`: RGB/reserved size and position bytes plus mask-source
  flags.
- `EDID_CHUNK(index)`: block 0 returned in a small fixed number of register-only
  chunks. No caller pointer crosses into the mini-VDD.

Retain by-mode lookup for active aperture discovery. It searches list-derived
records first and then the reserved baseline-probe cache; indexed enumeration
never returns rescue-only records. Every API function must be a bounds-checked
read of locked data and must leave output registers untouched on failure except
for its documented status value.

### Runtime table ownership

Add a display-side module, `src/display16/modes16.c`, owning fixed DGROUP
storage:

- `V9X_HW16_MODE v9x_runtime_modes[V9X_MODE_TABLE_MAX]`;
- `struct v9x_mode_masks v9x_runtime_masks[V9X_MODE_TABLE_MAX]`;
- a validated runtime count;
- the preferred-row index, or `FFFFh`;
- scan and drop diagnostics.

Do not modify `v9x_hw16.modes`; it remains the immutable family baseline.
Build the runtime table before `v9x_apply_mode` and before any DDI entry can
run. Large arrays must be static DGROUP storage, not stack locals. Add a map
file assertion that the Win16 data segment retains an agreed safety margin
below 64 KiB.

Initialization has one transaction boundary:

1. Copy the baseline rows and canonical masks into the runtime arrays.
2. Read and validate the mini-VDD controller and status.
3. Enumerate at most 64 cache records into bounded scan storage.
4. Call `v9x_vbe_build_mode_table` with the reported VRAM size.
5. Validate the output count and every output row again.
6. Commit the runtime count only after all steps succeed.

Any failure before step 6 leaves the already-copied baseline table committed.
The existing order of baseline rows is preserved: row zero remains the safe
boot fallback, and the low-resolution Doom95 row is not moved. A scanned row
matching `(width,height,storage_depth)` updates the baseline row's BIOS mode,
effective pitch and colour masks. New rows are appended deterministically.

Extend the host-tested admission result from a boolean to a reason code so the
guest inventory can say why a BIOS record was rejected. Required reasons
include unsupported, non-linear, invalid physical base, wrong memory model,
unsupported storage depth, unsupported colour layout, zero/short stride,
geometry limit, VRAM overflow, duplicate and table full.

Initial colour-layout policy is intentionally narrower than what VBE can
describe:

- 8 bpp is palettized;
- 16 bpp must be RGB 5:6:5;
- 24 bpp must be packed RGB 8:8:8;
- 32 bpp must be XRGB 8:8:8 with 24 significant colour bits;
- 5:5:5 in 16 storage bits and unusual channel orderings remain rejected until
  both DIB Engine and DirectDraw behavior are implemented and tested for them.

This prevents the DirectDraw masks from describing one surface while the DIB
Engine draws another.

## Publication paths

### GDI and mode switching

Repoint `ddi.c` mode access through the runtime table module. The following
must all use the same table and count:

- initial requested-mode selection;
- `v9x_find_mode`;
- `ValidateMode`;
- `Enable` and `ReEnable` mode selection;
- active geometry and pitch publication;
- the existing VRAM fit check.

The registry-selected mode always wins when it is in the runtime table. If the
selection is absent, use an accepted EDID geometry at the requested storage
depth. If that is absent too, use baseline row zero. Do not change a working
mode merely because a new monitor has a different EDID.

Mode entry remains the existing VBE `4F02h` sequence. A dynamically discovered
row must pass the same post-set pitch verification and aperture checks as a
baseline row. A failed set follows the current staged failure and previous-mode
restore paths; it is not silently quarantined during this project.

### DirectDraw

Change `dd16.c` to source rows and masks from `modes16.c`, not from
`v9x_hw16.modes` and depth-based constants. Use `v9x_vbe_dd_subset` when the
runtime table has more than 32 rows.

DirectDraw publication must guarantee that the current desktop row is present.
If the ordinary subset omitted it, replace the lowest-priority selected row
with the active row. Continue to validate `0 < mode_count <= 32` on the 32-bit
side.

For every published row:

- `dwBPP` is storage depth;
- `lPitch` is the effective linear stride;
- RGB masks come from the parallel runtime mask table;
- 8 bpp carries `V9X_DDMODEINFO_PALETTIZED` and zero masks;
- `dwAlphaBitMask` remains zero;
- refresh remains the adapter-default/current 60 Hz convention; this project
  does not create refresh variants.

The shared structure already has dynamic count and capacity fields, so no
DirectDraw ABI bump is required unless implementation work changes its layout.
If layout changes, bump `V9X_DD_SHARED_ABI` and keep old/new pair tests.

### Display Properties registry mirror

GDI can validate a dynamic row immediately, but the native Windows 9x Settings
page enumerates the driver's registry `MODES` tree. Bridge that boot-time gap
with a validated inventory emitted by the 16-bit driver and a narrow registry
synchronizer exported by `v9xsetp.dll`.

The inventory file should contain:

- schema and build ID;
- family ID and detected PCI identity where available;
- a generation value and final `Complete=1` sentinel;
- scan state and controller/cache counts;
- runtime count, dropped count and rejection counts;
- preferred geometry and whether it matched;
- one row per mode: mode number, width, height, storage/significant depth,
  pitch, masks and baseline/dynamic flags.

Write `Complete=0` before replacing rows and write `Complete=1` last. The
synchronizer rejects a missing sentinel, unknown schema, duplicate row,
out-of-range count, malformed number, unsupported depth, mask mismatch or a
row whose visible bytes overflow. An invalid inventory causes no registry
change.

Add an INF marker to the Velocity9x display devnode and a persistent command:

```text
rundll32.exe v9xsetp.dll,V9xSyncModes
```

The synchronizer must uniquely identify a marked Velocity9x display instance
using the marker, family and hardware identity before writing. Zero or multiple
matches are a recorded no-op. It creates missing
`MODES\<storage_depth>\<width>,<height>` keys and stamps only newly created
dynamic keys with `V9xDynamic=1` plus the current generation.

Pruning rules:

- delete a key only when it has `V9xDynamic=1` and is absent from a complete
  current inventory;
- never delete an INF baseline key, `MODES\4`, an unmarked key or anything
  below an unmarked display instance;
- if `DEFAULT\Mode` names a dynamic row that disappeared, replace it with an
  accepted row at the same depth, preferring EDID geometry, then the family
  baseline default;
- if the inventory is unavailable or invalid, preserve the previous registry
  state and report the reason.

Add a dry-run/report mode that writes intended add/keep/delete operations to a
diagnostic INI without mutating the registry. Installation must still ship a
complete static mode list, so first boot, Safe Mode and synchronizer failure all
retain today's usable baseline.

## EDID design

### Collection

After mode collection, use VBE `4F15h` to query DDC support and read EDID block
zero into a separate 128-byte locked cache. Clear it before the read and accept
it only when the BIOS returns `AX=004Fh`. Do not fetch extension blocks in the
first implementation; record their advertised count for diagnostics.

DDC failure is non-fatal and must not change mode-scan validity. Keep the
existing family scan gate: a family that assembles out VBE collection also
assembles out EDID collection unless a later family-specific DDC provider is
designed.

### Parsing and use

Add `include/velocity9x/edid.h` and `src/common/edid.c` as a no-I/O parser shared
with host tests. A usable base block requires:

- exactly 128 bytes;
- header `00 FF FF FF FF FF FF 00`;
- checksum sum modulo 256 equal to zero;
- a supported EDID base version;
- a detailed timing descriptor with non-zero pixel clock and non-zero active
  width and height within the driver's geometry limits.

Read the first valid preferred detailed timing into `(width,height)`. Validate
all packed-field arithmetic with widened types. Record interlace and pixel
clock for diagnostics, but do not use either to program hardware.

The resulting geometry is a hint only:

- it never admits a VBE record;
- it never removes a VBE record;
- it never changes storage depth;
- it is ignored unless an exact width/height row exists in the accepted table;
- an explicit valid registry mode always wins;
- invalid header, checksum, descriptor or no exact match behaves exactly like
  no EDID.

Publish the recommendation and validation reason in the mode inventory and
Velocity9x settings report.

## Implementation stages

Each stage is independently buildable and has a rollback point.

### Stage 0 - freeze evidence and contracts

- Capture the outstanding QEMU std-vga `4F00h` list, `4F01h` records and EDID
  with `vbe_inventory_dos`/the survey tool.
- Record the number of listed modes, VBE version, linear fields, masks and
  whether the mode-list pointer lands in ROM or the controller buffer.
- Define the packed cache layout and API v2 constants in one shared assembly
  include.
- Define generation of the family baseline-probe include from manifest modes,
  with deduplication and the 16-entry build-time limit.
- Add the DGROUP size gate and document exact cache/table byte costs.
- Write negative fixtures before ring-0 changes: unterminated list, more than
  128 entries, duplicate numbers, failed `4F01h`, stale scratch, VBE 2 versus
  VBE 3 masks and malformed EDID.

Exit gate: contracts and fixtures are reviewed; no product behavior changes.

### Stage 1 - bounded mini-VDD enumeration, diagnostic only

- Replace the fixed seven-number loop with the bounded `VideoModePtr` staging
  walk.
- Clear scratch before every query and require `AX=004Fh` before reading it.
- Populate up to 64 packed records, counts and reason flags.
- Query the generated baseline rescue list into its reserved cache without
  exposing rescue-only answers as dynamic enumeration results.
- Add API v2 indexed mode/mask access while retaining the old active lookup if
  needed.
- Extend serial status with listed, queried, cached, failed and overflow counts.
- Add a display-side diagnostic dump, but continue to use the static family
  table for all rendering.

Roll out first only to the `vbe` QEMU package. Do not enable collection for S3
or Matrox. ATI remains behind its existing family gate until the QEMU walk is
stable.

Exit gate: the guest dump matches the DOS inventory record-for-record; corrupt
or truncated fixtures yield a valid baseline boot and an explicit reason.

### Stage 2 - runtime table consumed by GDI

- Add and link `modes16.c`, `vbe_modes.c` and their required parser objects.
- Convert API v2 records to `v9x_vbe_scan_entry` values.
- Derive significant depth and effective VBE 3 masks in the shared parser.
- Add admission reason codes and deterministic duplicate selection.
- Build and transactionally commit the runtime table during driver load.
- Repoint every GDI lookup and mode-switch path to it.
- Emit the complete inventory file after successful initialization/enable.

Exit gate: OEM/nonstandard QEMU modes pass `ValidateMode`, enable cleanly and
survive live same-depth switching; a scan-disabled or invalid-scan build is
byte-for-behavior equivalent to the static baseline path.

### Stage 3 - DirectDraw publication

- Publish the runtime subset and its real masks from `dd16.c`.
- Guarantee inclusion of the active desktop row.
- Verify the 32-bit HAL rejects zero/over-capacity counts.
- Exercise mode enumeration, `SetDisplayMode`, primary creation, CPU blits,
  flips and `RestoreDisplayMode` at every newly published depth.

Exit gate: DirectDraw's list is a subset of GDI's list, contains no duplicate
geometry/depth rows and describes pitch/masks exactly as the active surface.

### Stage 4 - native Display Properties synchronization

- Add the device marker and persistent `V9xSyncModes` command to generated
  INFs for scan-enabled families.
- Implement inventory validation, unique-devnode matching and dry-run output.
- Add marked-key creation and ownership-safe pruning.
- Update the settings report to show runtime modes, scan state and drop reasons.
- Test first boot, ordinary reboot, monitor/card change, missing inventory,
  corrupt inventory, ambiguous devnodes and removal of a formerly selected
  dynamic row.

Exit gate: after boot, native Display Properties offers exactly the accepted
runtime geometries plus the permanent VGA fallback; disabling or breaking the
synchronizer leaves the static package modes usable.

### Stage 5 - EDID preferred hint

- Add bounded `4F15h` collection and API chunk access.
- Add the host-tested EDID parser and negative corpus.
- Match preferred geometry against the committed runtime table.
- Apply the configured-mode, same-depth EDID, baseline fallback order.
- Publish recommendation and reason to the inventory/settings page.

Exit gate: a valid exact-match EDID is reported and used only on fallback; bad
checksum, unavailable DDC, nonmatching geometry and monitor changes never
remove modes or override a valid user selection.

### Stage 6 - family rollout and cleanup

- Enable the consumer for `vbe`, then ATI after its own guest/physical mode
  inventory agrees.
- Keep S3 and Matrox collection disabled unless a separate decision proves a
  benefit that outweighs boot-time BIOS risk.
- Remove the v1/fixed-list compatibility code after package-pair and rollback
  testing.
- Update README, install docs, family manifests, mode summaries, diagnostics
  and changelog.

Exit gate: all enabled families pass their VM and physical gates; disabled
families retain identical static behavior and contain no new BIOS calls.

## Future banked VBE family

Banked VBE is a separate follow-up with a go/no-go design spike. It is not an
alternate branch inside the LFB runtime table.

Create a distinct `vbe-banked` family only if testing proves one of these can
provide correct GDI semantics:

1. a VFLATD-backed virtual-flat mapping with an audited bank-switch callback;
2. a system-memory DIB Engine shadow surface with bounded dirty-region copies
   through VBE `4F05h`.

The spike must measure both approaches on VBE 1.2 hardware before selecting
one. Its mode record will need window attributes, segment, granularity, window
size and bank-switch mechanism, none of which should be added to the LFB API
until that decision exists.

The banked family has these hard boundaries:

- its own family manifest, INF, mini-VDD contract and display-side backend;
- GDI only; no DirectDraw HAL, video-memory surfaces, page flipping, D3D or
  hardware acceleration claims;
- no `PhysBasePtr` or linear-attribute requirement;
- no banking checks or branches in `vbe`, ATI, S3 or Matrox LFB paths;
- failure returns to VGA/static-safe behavior rather than loading the LFB
  driver with a fake aperture.

Go only if a prototype displays correctly, handles bank-boundary drawing and
scrolling, survives mode changes and is acceptably fast on target-era CPUs.

## Verification matrix

### Host tests

- Controller and mode parsing for VBE 2 and VBE 3 records.
- Linear-stride precedence and legacy-mask fallback.
- Storage/significant depth derivation, including 16/16, 24/24 and 32/24.
- Rejection of 15-bpp storage, 5:5:5, overlapping/out-of-range channels,
  noncanonical channel order, zero/short pitch and VRAM overflow.
- Baseline-only transaction, duplicate update, stable sort and 64-row overflow.
- DirectDraw 32-row selection, active-row inclusion and exact mask propagation.
- EDID header, checksum, version, DTD arithmetic, no-DTD, interlaced and
  nonmatching geometry cases.
- Inventory parser/diff logic with fake registry operations: add, keep, prune,
  selected-mode replacement, foreign key protection and ambiguous devnodes.

### Build and package checks

- API constants and packed offsets agree in both assembly users.
- The generated mini-VDD baseline-probe set equals the selected manifest's
  distinct VBE mode numbers and never exceeds its reserved capacity.
- Win16 DGROUP remains below its safety threshold.
- Generated INFs retain every manifest baseline mode.
- Only scan-enabled families receive the persistent synchronizer entry.
- Package audits prove scan-disabled mini-VDDs contain the disabled marker and
  no VBE collection body.
- Old/new DRV, VXD and HAL pairings refuse or fall back without a crash.

### QEMU std-vga

- Mini-VDD dump equals the DOS `4F00h` inventory.
- More than the original seven modes appear when the BIOS lists them.
- Every accepted mode: boot or switch, GDI smoke, real display capture and
  pitch verification.
- DirectDraw enumeration is the expected subset; set/restore and CPU
  fill/copy/flip tests pass at 8/16/24/32 as available.
- Native Display Properties mirrors the runtime inventory after synchronization.
- EDID exact match, bad-checksum fault injection and no-DDC fallback.

### ATI targets

- Mach64 VT2 guest inventory and mode matrix before enabling publication.
- Rage Mobility physical boot with its known underreported `4F00h` memory; the
  baseline must remain available and dynamic admission must fail conservative.
- No-EDID panel and `4F15h` refusal both take the static fallback unchanged.

### Regression targets

- S3 and Matrox packages show no new `Exec_Int 10h` collection calls.
- S3 8/16/32 mode matrix, Doom95 640x400, DirectDraw and ViRGE D3D remain
  unchanged.
- Physical 2 MiB Trio64 continues to reject rows that do not fit VRAM.
- Safe Mode retains the stock VGA fallback.

## Diagnostics required for release

The following facts must be available without a debugger:

- mini-VDD API version and build pair status;
- controller valid/version/VRAM;
- mode-list pointer state, terminator state and listed/query/cache counts;
- last BIOS function and argument before a hang, using the existing serial
  pre-call marker;
- per-reason rejected and dropped counts;
- runtime GDI count and DirectDraw count;
- EDID unavailable/header/checksum/descriptor/match state;
- registry sync target, generation, add/keep/delete counts and no-op reason.

Never log the full EDID serial number in routine status output. The raw block
may remain available only in explicit diagnostics, consistent with the survey
tool's privacy warning.

## Rollback strategy

- Stage 1 can ship with enumeration diagnostic-only.
- Stage 2 can be disabled at the display side, leaving the static table.
- Stages 4 and 5 are additive; absent or invalid inventory/EDID is a no-op.
- Setting `MiniVddVbeCollect=$false` removes boot-time VBE/EDID calls for a
  family at build time.
- Reinstalling a baseline package removes the generated `MODES` tree through
  the existing INF cleanup and recreates its static entries.
- No rollback requires changing S3, Matrox or native accelerated backends.

## Definition of done

The pipeline is complete when all of the following are true:

- the scan-enabled mini-VDD contains no hand-written seven-mode query list;
  its bounded rescue probes are generated from the selected family manifest;
- its BIOS mode-list walk and every exported count are bounded and status
  checked;
- VBE 3 linear stride, physical base, effective masks, storage depth and
  significant depth survive the mini-VDD API unchanged;
- one committed runtime table drives GDI validation, mode entry, live switching
  and DirectDraw publication;
- native Display Properties mirrors that table without taking ownership of
  baseline or foreign registry keys;
- EDID can recommend only an already accepted geometry and every invalid or
  absent EDID case is indistinguishable from the current safe fallback;
- scan-disabled families execute no new video-BIOS calls;
- host, QEMU and required physical tests pass with release diagnostics captured;
- banked support remains a separate, GDI-only family decision rather than a
  condition in the LFB fast path.
