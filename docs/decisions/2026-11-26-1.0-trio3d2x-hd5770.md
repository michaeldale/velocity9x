# Trio3D/2X and HD 5770 on the 0.61.0 tree: the HD 5770 passes everything and gives DirectDraw 128 MiB; the Trio3D/2X's 3DMark 2000 completes with 51 engine timeouts

Date: 2026-11-26. Build: `6244dc08-dirty` (the 0.61.0 tree), installed
by `run-release-checks.ps1` (WININIT renames, `reset`, 8 of 8 files
hash-checked on each machine).

## HD 5770 (M-BXMFA8, remote help)

Daniel's machine (Core 2 Duo E7500, Windows 98 SE) with the HD 5770
(Juniper, `1002:68B8`, subsystem `1002:2543`) fitted again in place of
the Oland 6611; Windows had kept it on our `ati` driver. Boot 191, the
`ati` set installed over the relay, desktop 1024x768x32.

| Check | Result |
|---|---|
| V9XD32, 32 bpp and `/bpp16` | PASS, `Failures=0` |
| V9XGLP, V9XGLIDP, V9XWPRS, V9XFBCMP | PASS |
| V9XR3DP | COMPLETE |
| 3DMark 2000, default benchmark, 1024x768x16 | ran to its score, 8626 (recorded, not compared); 2,092,213 draws, none refused, none into the presented buffer, no engine stall |

The ten grabbed Helicopter frames are whole
(`hd5770/3dmark2000-grabs.jpg`). The last run on an HD 5770 was 0.34.0
(2026-11-01). With the HD 7470 and the HD 5450 this is the third
Evergreen card on which the Caicos per-group flush fix runs without a
hang.

**B7, 16 MB against 128.** On this card the `ati` driver gives
DirectDraw 128 MiB: `V9XBOOT.INI` has `VddReserve=... vram=134217728`,
and V9XGLP's own DirectDraw object reads `LifetimeVramFreeFirst`
130,460,544 bytes free. The card's VBE BIOS reports 16 MiB
(`VbeController ... mem=256`, 64 KiB units; `V9XHW.INI`
`VbeVramBytes=16777216`). So 16 MB is the figure of anything that reads
the VBE BIOS: the generic `vbe` package, or an `ati` path that fell
back to the VBE size. That fits the reporter's number. It does not show
which happened on their Windows Me machine; they never sent the files.

## Trio3D/2X (A8U4I5)

The second card of the A8U4I5 round (`5333:8A13`, 4 MiB, Velocity9x
class key `Display\0002`). The machine came up with the Rage XL's `ati`
files, which refused this card (`Stage=fail-hardware-present`), and
with `BitsPerPixel=4` again; set to 16 at 800x600 (previous values
recorded). The `s3` set went in at boot 699 to 700.

3DMark 2000's default 1024x768x32 needs 16 MB, so the runner's run
stopped at the welcome dialog. Set by hand in its Display and CPU
Settings to 640x480, 16-bit colour, 16-bit textures and Z, triple
buffer (2,400 KB of 4,096 used; `trio3d2x-3dmark-640/settings-640x480.png`)
and run with Benchmark:

- ran to its score, 175 (recorded);
- across the run, from V9XTRACE snapshots before and after:
  `FlipHandled` 1,676, **`EngineIdleTimeouts` 51 and `EngineResets` 51**,
  `TrianglesDeclined` 9, `DrawsFlipWaited` 1,530.

3DMark 99 on this card had no engine timeouts in September
([issue](../issues/2026-09-03-3dmark99-on-the-trio3d-after-the-stride-fix.md));
3DMark 2000 had not run on it before. Where in the run the timeouts
fell, and whether anything was seen on screen at those points, was not
recorded (no grabs; the runner's grab path was not used).

The release probes, run separately without 3DMark. The first pass found
the desktop at 8 bpp (Windows had changed `BitsPerPixel` to 8); set back
to 16 and run again, boot 702, 800x600x16:

| Check | Result |
|---|---|
| V9XFBCMP, V9XGLP, V9XWPRS | PASS |
| V9XR3DP | COMPLETE |
| V9XGLIDP | FAIL: BlendHalf, FogTable |
| V9XD32 `/bpp16` | FAIL: T21 (`T21Ok=8`: one of four mip sizes picks its level) |

All three fit README known issues for the S3D cards: half alpha
saturating on the Trio3D/2X, the Trio3D's mip selection differing from
the ViRGE/DX's
([issue](../issues/2026-09-03-trio3d-alpha-and-mip-differ-from-virge-dx.md)),
and the fog table, which the ViRGE/DX guest fails too. Not compared
against an earlier run of these probes on this card.
