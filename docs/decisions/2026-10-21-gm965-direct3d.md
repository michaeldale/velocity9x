# GM965: Direct3D on the Gen4 pipeline, pixel-exact at 16 and 32 bpp with a 16-bit Z buffer

Date: 2026-10-21
Status: **V9XD32 passes every check at 16 and 32 bpp on one machine.** A
32-bit Z buffer hung the 3D pipe once, and the engine no longer offers one.
Phase 2 of `docs\plans\intel-gen4-gen5-bringup.md`. That plan had judged
this "a different project". It took one evening because the encodings
could be checked against xf86-video-intel's Gen4 kernels before anything
ran.

Machine: TOMMOHP, `M-KYHT4Q` (`2026-10-20-gm965-ring-and-blits.md`).
Captures: `docs\probe\tommohp-gm965-igma-2026-10-20\boot8-*`, `boot9-*`.

## What was built

- `src\chipsets\intel\g4_eu.c`, `intel_g4_eu.h`: a Gen4 EU encoder (mov,
  add, mul, send, nop; GRF/MRF/null/immediate operands, regions,
  compression). Field positions are Mesa `brw_inst.h`'s Gen4 columns. The
  host test builds eleven instructions from xf86's `exa_*.g4a` sources and
  matches its `.g4b` binaries word for word:
  - add with a V immediate;
  - compressed add with a negated scalar;
  - compressed mul;
  - math inv;
  - the URB write with EOT;
  - the masked header mov;
  - the MRF copy;
  - the SIMD16 sample;
  - the sechalf mov;
  - the render target write;
  - nop.
- **SF kernel:** Mesa's `brw_emit_tri_setup` without the accumulator.
  1/det comes from a math inv, and z and 1/w go into the first
  attribute's z and w. Three setup registers, each written to the URB
  transposed at offsets 0, 4 and 8.
- **WM kernel:** SIMD16. It interpolates diffuse and specular, and texture
  coordinates as u/w, v/w and 1/w, which the CPU writes from rhw. 1/w is
  inverted per pixel as xf86's `exa_wm_projective.g4i` does. Then it
  samples (binding table 1, sampler 0) and combines:
  - DECAL/COPY;
  - MODULATE, with and without texture alpha;
  - ADD;
  - specular;
  - vertex fog.

  It ends with xf86's SIMD16 render target write.
- `src\chipsets\intel\g4_3d.c`, `intel_g4_3d.h`: the state blocks (VS
  passed through, SF, WM, COLOR_CALC, viewports, SURFACE_STATE,
  SAMPLER_STATE) and one batch per draw. The batch runs: MI_FLUSH with
  instruction invalidate, PIPELINE_SELECT, STATE_BASE_ADDRESS at the
  reserve, the binding table and pipelined pointers, URB_FENCE inside one
  64-byte line, CS_URB_STATE, the drawing rectangle, the depth buffer, one
  vertex buffer, seven vertex elements, 3DPRIMITIVE TRILIST, MI_FLUSH and
  MI_BATCH_BUFFER_END. Layouts are genxml `gen4.xml`'s; the URB partition
  and unit choices are xf86's `sna\gen4_render.c`. `v9x_g4_batch_check`
  refuses any batch that is not what the builder emits.
- `src\display32\d3d\d3d_g4.c`: the engine. Synchronous:
  1. drain;
  2. rewrite the state, kernels and vertices in the reserve's free 896 KiB;
  3. submit;
  4. wait for the breadcrumb.

  Mapping policy is Haswell's, through `d3d_hsw_map.c`. Intel's surface
  format numbers are the same on Gen4 and Gen7.5.
- `v9x_d3d_i9xx_submit_g4_batch` in `d3d_i9xx.c`, **a new external symbol
  in the HAL**, for the reason `submit_blt` is one: the breadcrumb sequence
  stays private to the Gen3 file. It puts `MI_BATCH_BUFFER_START` (GTT,
  non-secure, as i915's `gen4_emit_bb_start`) and the breadcrumb in the
  ring. Made without stopping, at Michael's request; he approved it
  afterwards ("g4 batch is on", 2026-10-21).
- Selection: `V9X_DD_ENGINE_CAP_I9XX_GEN4`, stamped by the GM965
  descriptor, routes Direct3D to the Gen4 engine. The Gen3 engine refuses
  when it is set.

## Flips (boot 10)

The GM965 descriptor now keeps FLIP (FLIP_RING stays off: Gen4's
MI_DISPLAY_FLIP is not the 915 packet). On the I9XX_GEN4 bit,
`i9xx_scanout.c` does two things differently:

- It writes the remainder to DSPxLINOFF and then the 128 KiB-aligned base
  to DSPxSURF, whose write latches the flip, and reads back the sum of the
  two.
- It skips the Gen3 FW_BLC write. Gen4 keeps its watermarks in DSPFW,
  which the BIOS set for the mode.

V9XDDP `/hold` at 640x480x16. V9XG4MM read during the hold:

| Register | Value | Reading |
|---|---|---|
| DSPBSURF | `00080000` | 128 KiB aligned |
| DSPBLINOFF | `00016000` | the remainder |
| sum | `0x96000` | = 640 x 480 x 2: the back buffer after the primary |
| DSPBSTRIDE | `00000500` | 1280 bytes |

- 20 flips with DDFLIP_WAIT took 324 ms: 16.2 ms each, the 59.8 Hz panel.
- `FlipPixelOk=0` is the probe's GDI readback, which sees GDI's page, not
  the flipped one. The registers above are the measurement.
- Every blit check in the same run passed.
- V9XD32 then passed at 16 and 32 bpp with flips on.

## Two slots (boot 11)

Each draw used to wait for its own breadcrumb, and the next one waited
again in the render drain before it rewrote the one state block, batch
and vertex area. Now there are two of each, as on Haswell
(`intel_g4_3d.h`): 4 KiB of state and 4 KiB of batch each, and 352 KiB of
vertices each. Two pipeline words in the reserve at `0x2fc00` record the
last slot used and the breadcrumb of the batch last submitted from each
slot. A draw takes the other slot and waits only for that slot's
breadcrumb, so the CPU builds draw N+1 while the GPU runs draw N.
`v9x_d3d_i9xx_submit_g4_batch` returns the sequence for this. The draw
waits for its own breadcrumb only while GDI may be drawing on the screen
(`v9x_present_gdi_may_draw`, Haswell's rule).

- The SF and WM kernels are shared by both slots. They are rewritten only
  after a full drain.
- The kernel signature now carries a revision (`V9X_D3D_G4_KERNEL_REV`).
  The reserve survives a warm reset, so a kernel written by an older HAL
  is rewritten, not trusted.
- A slot whose breadcrumb is not seen within the poll bound falls back to
  a full drain. A stale sequence left in the reserve by an earlier boot
  costs one drain, not a hang.
- ASYNC_SUBMIT is on for this chip (inherited from the 945 fill), so a
  submission without wait returns once the tail moves.

Measured on TOMMOHP, boot 11, with the `V9XHAL.DLL` of this change
(468,992 bytes):

- V9XD32 passed at 16 and 32 bpp, Failures=0
  (`boot11-V9XD32-bpp16.TXT`, `boot11-V9XD32-bpp32.TXT`).
- 3DMark 2000's default benchmark, same settings as boot 9, ran to its
  score: **793** (`boot11-3dmark2000-score.png`). The machine was
  responsive afterwards. The score is recorded, not compared. Whether the
  slots overlapped in the run was not measured: no diagnostics snapshot
  was taken, and 3DMark 2000's transform and lighting run on this CPU.

## Mip levels (boot 12)

Until now a chain sampled level 0 only. SURFACE_STATE has one base and
one pitch for every level, and DirectDraw's heap placed each level as a
surface of its own. The engine now places a video-memory `TEXTURE |
MIPMAP` chain as one tree, as Haswell does (2026-10-18-haswell-mipmaps):

- **Layout.** `v9x_intel_hsw_miptree` is reused unchanged. The 965 PRM
  Vol 1 6.17.3 lays out a 2D map the same way:
  - MIPLAYOUT_BELOW (SURFACE_STATE DW0 bit 10 left 0): LOD 1 at
    (0, h0), LOD 2 at (w1, h0), every later level below the one before.
  - Table 6-23's alignment unit, i = 4 and j = 2 for every uncompressed
    format: Haswell's HALIGN 4 / VALIGN 2.
- **Placement.** `create_surface` puts the tree in one 4 KB-aligned block
  from the heap (`d3d_place.c`). Whole pages also cover Vol 1 6.18's
  rule that every page the sampler can reach past the edge is mapped.
- **Binding.** At bind, `v9x_d3d_g4_mip_levels` (Haswell's walk) counts
  the levels that sit at the tree's pitch and offsets.
- **Sampler and surface.** The MIP count goes into SURFACE_STATE DW2 5:2,
  and MAX LOD into SAMPLER_STATE DW1 as the last level, U4.6. The mip
  filter is MIPFILTER_NEAREST 1 or LINEAR 3, from Vol 4 SAMPLER_STATE
  DW0 21:20.
- **No kernel change.** The WM kernel's sampler message is the SIMD16
  `sample` (type 0), which takes its LOD from the subspan derivatives.
- **Host test.** `test_mips` checks the tree for 256x256 against Vol 1's
  equations, and the MIP count and Max LOD bits.

V9XDDP, boot 12 against boot 10 (`boot12-V9XDD.INI`, `boot12-V9XDD2.INI`,
HAL 470,016 bytes). Every Ok key that changed:

| key | boot 10 | boot 12 |
|---|---|---|
| `ChainAOk`, `ChainDOk`, `ChainEOk` | 0 | 1 |
| `D3DMipmapLevelSelectOk` | 0 | 1 |
| `D3DTrilinearBlendOk` | 0 | 1 |
| `MipLadderOk` (levels 0-3 red, green, blue, magenta) | 0 | 1 |
| `MipTriOk` | 0 | 1 |
| `MipLadderShapeOk` | 1 | 0 |

- `MipLadderShapeOk` checks the heap's per-surface placement, which a
  tree replaces. The ladder's deltas are the tree's: level 1 +32768
  (128 rows at pitch 256), level 2 +128, level 3 +8192.
- **`ChainBOk`, `ChainCOk` and `ChainRowsOk` stay 0. This is the probe.**
  - Those draws fill each level with `v9x_fill_surface`, one run of
    `lPitch * height` bytes.
  - In a tree, level 2 sits beside level 1 at the same pitch, so filling
    level 2 overwrites level 1's rows with blue. The probe's own comment
    at `v9x_fill_surface_rows` records this from the netbook (2026-09-25).
  - The ladder fills row by row and reads all four levels.
  - The netbook's 945GSE (`netbook-gma950-0.19.0-2026-10-18`) reads the
    same `Chain*Ok` set and the same twelve `ChainSweep*Raw` values: red
    at 1.4, blue from 1.7 to 5.0, and magenta from 6.0.
  - The change out of level 0 falls between ratios 1.4 and 1.7, and the
    one into level 3 between 5.0 and 6.0. Both brackets hold the ratios
    the nearest-level rule gives, 1.41 and 5.66.
- Every other `Ok=0` key was 0 at boot 10 too.

## Colour key, two texture units, ring flips (boots 13-17)

### Colour key

- **Mechanism.** The texture's DirectDraw source key goes into the
  sampler's chroma key: 3DSTATE_CHROMA_KEY entry 0 (965 PRM Vol 4
  4.7.5), and SAMPLER_STATE DW3 25/24:23/22.
  - Low and high are widened to 8 bits a channel by replicating the high
    bits, as the PRM says the sampler widens the texel it compares.
  - Alpha gets the full range, so it is not compared.
  - The conversion is `v9x_g4_chroma_key`, host-tested.
- **Why REPLACE_BLACK, not KILL_ON_ANY_MATCH.**
  - KILL needs `sample+killpix`, which exists in SIMD8 only (Vol 4
    4.8.1.4), and this kernel samples SIMD16.
  - REPLACE_BLACK samples a matching texel as (0,0,0,0) before
    filtering. The PRM leaves the discard to "alpha test, etc.".
  - So a keyed draw gets an alpha test of GREATER 0, or keeps the
    application's own test when that already rejects 0.
  - The stage must carry the texel's alpha to the output. TEXTURE,
    MODULATE and MODULATE_TEXALPHA do. ADD and the two-unit DECAL do not
    and are refused.
- **Measured.** V9XDDP boot 13 against boot 12, with only one Ok key
  changed: `ColorKeyHalvesOk` 0 to 1.
  - 565 and 1555 alike: the keyed left half keeps the blue target (31),
    and the right half draws green (2016).
  - At boot 12 both halves read blue: the draw was refused.

### Two texture units

- **Vertex layout.** Unit 1's u/w and v/w ride in the VUE's first zero
  slot (dword 24), from 8 more bytes per vertex (pitch 44). The WM
  already read that attribute, so the URB and SF are unchanged.
- **Kernel.**
  - Unit 1 is a second SIMD16 sample: binding table entry 2, sampler 1.
  - Stage 1 multiplies the colour, alpha included, by texture 1.
  - Stage 0 gains DECAL (texel colour, fragment alpha).
  - The combines are Haswell's mapping (`v9x_d3d_hsw_two_unit_stages`).
- **Kernel slots.** The two-unit kernels take 24 slots of their own at
  reserve `0x34000`, which was free.
- **Kernel revision.** It is now 2, so kernels a boot-12 HAL left in the
  reserve are rewritten.

Only OpenGL and Glide reach a second unit: Direct3D's DDI path carries
stage 0 only. Testing it through V9XGLP found two faults on this chip
that predate today.

1. **Odd-width Z buffers hung the 3D pipe.**
   - Boots 12 and 14: the ICD's first draw, into its 400x300 window,
     took 65 s (`draw-ms=64829`). The engine timed out and quarantined
     itself, and every later GL draw returned NOT_READY.
   - The cause: a linear depth buffer's pitch "can be any multiple of 64
     bytes" (Vol 2, 3DSTATE_DEPTH_BUFFER), and DirectDraw's heap gave
     the 400-wide one 800.
   - Direct3D never met it: V9XD32 and 3DMark draw at 640 and 1024
     wide.
   - The fix: `create_surface` places a lone video-memory Z buffer at a
     64-byte pitch, and a depth surface whose pitch is not one is
     refused.
   - Boot 15: the nine V9XGLP checks that failed at boot 12 pass (fog,
     polygon offset, Rect, Vertex2s, AttribClear).
2. **The ICD got no hardware textures.**
   - `describe` had no Gen4 branch, so every GL texture went from the
     CPU to the software engine.
   - It now has Haswell's terms: video-memory textures, powers of two,
     1 to 2048.

That exposed a third fault:

3. **The alpha test with depth writes hung the 3D pipe** (boot 16, the
   first GL draw with alpha test, depth test and depth write;
   BreadcrumbAbandoned=1).
   - Vol 2 8.4.3: "Pixel Shader Kill Pixel" must be set for "alphatest"
     or a chroma-keyed texture.
   - With depth writes, the write then moves after the pixel shader,
     with source depth carried to the render target (the non-promoted
     and computed cases). This kernel carries none.
   - Such a draw is now refused and drawn by the fallback.
   - The same rule covers a colour key with depth writes.
   - Carrying source depth (Mesa's Gen4 IZ table) is the fix that would
     lift this. It is not done.

Boot 17, `boot17-V9XGLP.INI`:

- Result PASS: 30 Ok keys at 1, none at 0.
- The SGIS checks all pass: MODULATE, REPLACE, BLEND, DECAL, coordinates
  left/right, and unit 1 off.
- Every SgisMip key reads the level its ratio selects, L0 to L4, on unit
  0 and unit 1, linear and perspective.
- ICD log: 36 two-unit batches. 3 were split, which are the combines the
  one stage 1 cannot express.
- V9XD32 passed at 16 and 32 bpp.
- V9XDDP's Ok keys matched boot 13.

### Ring flips

- **The packet.** The 915 packet `i9xx_flip.c` builds - MI_DISPLAY_FLIP
  length 1: plane, pitch, base - is a valid Gen4 synchronous flip. The
  optional panel fitter dword is left out, which Vol 1 9.5 allows for a
  synchronous flip, so TOMMOHP's panel fitter is never touched.
- **The limit.** For a linear buffer, Gen4 takes the dword offset from
  DSPLINOFF, not the packet (Vol 1 9.5, programming note 5). DSPSURF
  must be 128 KiB-aligned. So the ring flips only when the new buffer's
  remainder below 128 KiB equals what LINOFF holds; every other flip is
  the register write, which sets both.
- **Descriptor.** The GM965 descriptor keeps FLIP_RING.

3DMark 2000 default benchmark, 1024x768x16 triple-buffered, boot 17
(`boot17-after-3dmark-V9XTRACE.INI`):

| Counter | Value |
|---|---|
| FlipHandled | 4156 |
| FlipRingIssued | 9 |
| FlipRingRefused | 0 |
| FlipRingPendingSeen | 9 |
| EngineIdleTimeouts | 0 |
| BreadcrumbAbandoned | 0 |

- The VBIOS's stride at 1024x768x16 is 2112 bytes (`FlipStrideLast`
  `0x840`), so the three buffers sit at `0`, `0x18C000` and `0x318000`.
- Their remainders are 0, `0xC000` and `0x18000`, and almost every flip
  changes the remainder.
- So the ring path is correct but rarely taken on this machine.
- Placing a flip chain on 128 KiB boundaries would change that. It is
  not done.
- The score was **816**, recorded and not compared
  (`boot17-3dmark2000-score.png`).

## The alpha test with depth writes: still refused (boots 18-20)

An attempt to lift the refusal. Nothing from it was committed: the code
was reverted and boot 21 runs `8b105c34` again.

**The table.** The 965 PRM Vol 2 8.4.3.2 tables were extracted from the
PDF pages (244-246). With the early depth test enabled, as this engine
sets it, and stencil off:

| Depth test | Depth write | Kill pixel OR alpha test | Mode | SD to EU | SD to RT | DD |
|---|---|---|---|---|---|---|
| 1 | 1 | 0 | P | 0 | 0 | 0 |
| 1 | 0 | 1 | P | 0 | 0 | 0 |
| 1 | 1 | 1 | **N** | 1 | 1 | 0 |

- The column is "Kill Pixel OR Alpha Test Enable", so the CC alpha test
  alone switches the mode. That is why the boot 16 draw hung with the kill
  bit clear.
- Mesa's Gen4 table agrees: `elk_fs_thread_payload.cpp` index 13 is
  N 1 1 0 0. So does its payload: g0, g1 subspans, source depth g2-g3,
  `num_regs` 4.
- So does its RT write: the implied g0/g1 header, colour, then source
  depth. The PRM puts the source-depth flag at R1.6 bit 29, the same bit
  as the header's M1.6 bit 29.

**What was built.**
- A kernel form that reads setup from g4 and writes source depth (g2-g3)
  into M10-M11, with mlen 12 (Vol 4 5.10.6.9).
- WM_STATE: Kill Pixel (DW5 22) and dispatch start 4.
- A signature-searched kernel cache, to make room for the extra forms.

**What the GPU did** (V9XGLP, the draw at `boot1*-V9XGL.LOG` line 94: a
16x16 ARGB4444 texture, the alpha test, depth test LEQUAL, depth write):

| Boot | Build | Result |
|---|---|---|
| 18 | source-depth form | hung (`draw result=8`, then NOT_READY) |
| 19 | diagnostic: alpha test dropped from that draw (mode P) | no hang, V9XGLP 30 Ok |
| 20 | source-depth form, Z buffer Y-tiled (pitch 128, rows 32, tiled bit and Y walk set) | hung |

Hypotheses killed:
- **"The kill bit not being set"**: it is irrelevant, as the table shows.
- **"A linear depth buffer cannot take a post-shader depth write"**: the
  boot 20 Y-tiled Z hung the same way. That rules this out for D16.
  Whether it explains the linear D24 hang is not known.

Two more runs (boots 22-23), again reverted. Boot 24 runs `8b105c34`.

| Boot | Build | Result |
|---|---|---|
| 22 | SIMD8 source-depth form: 8-pixel dispatch, SIMD8 sample (mlen 4), RT write control `0xC` (SIMD8 single source, subspans 0-1) with sZ in m6, mlen 7; kill bit set | hung |
| 23 | the same with the kill bit clear | hung |

More hypotheses killed:
- **"SIMD16 cannot carry source depth in mode N"**: SIMD8 hung the same
  way.
- **"The kill bit brings expectations the kernel does not meet"**: clear,
  it hung the same way.

What is left:
- An encoding of the source-depth write that none of the four forms got
  right. The PRM and Mesa describe it the same way, and these forms
  follow them.
- A part-specific condition in mode N that neither documents.

Probing it further needs an instrument that shows where the pipe stops,
such as INSTDONE and ACTHD read during the hang with V9XG4MM. These runs
did not take one. The refusal stays, and such draws go to the fallback.
The SIMD8 kernel code was not committed.
