# GM965: Direct3D on the Gen4 pipeline, pixel-exact at 16 and 32 bpp with a 16-bit Z buffer

Date: 2026-10-21
Status: **V9XD32 passes every check at 16 and 32 bpp on one machine.** A
32-bit Z buffer hung the 3D pipe once, and the engine no longer offers one.
Phase 2 of `docs\plans\intel-gen4-gen5-bringup.md`. That plan had judged
this "a different project". It took one evening because the encodings
could be checked against xf86-video-intel's Gen4 kernels before anything
ran.

Machine: TOMMOHP, `M-KYHT4Q` (`2026-10-20-gm965-ring-and-blits.md`).
Captures: `docs\probe\tommohp-gm965-igma-2026-10-20\boot8-*`, `boot9-*`.

## What was built

- `src\chipsets\intel\g4_eu.c`, `intel_g4_eu.h`: a Gen4 EU encoder (mov,
  add, mul, send, nop; GRF/MRF/null/immediate operands, regions,
  compression). Field positions are Mesa `brw_inst.h`'s Gen4 columns. The
  host test builds eleven instructions from xf86's `exa_*.g4a` sources and
  matches its `.g4b` binaries word for word:
  - add with a V immediate;
  - compressed add with a negated scalar;
  - compressed mul;
  - math inv;
  - the URB write with EOT;
  - the masked header mov;
  - the MRF copy;
  - the SIMD16 sample;
  - the sechalf mov;
  - the render target write;
  - nop.
- **SF kernel:** Mesa's `brw_emit_tri_setup` without the accumulator.
  1/det comes from a math inv, and z and 1/w go into the first
  attribute's z and w. Three setup registers, each written to the URB
  transposed at offsets 0, 4 and 8.
- **WM kernel:** SIMD16. It interpolates diffuse and specular, and texture
  coordinates as u/w, v/w and 1/w, which the CPU writes from rhw. 1/w is
  inverted per pixel as xf86's `exa_wm_projective.g4i` does. Then it
  samples (binding table 1, sampler 0) and combines:
  - DECAL/COPY;
  - MODULATE, with and without texture alpha;
  - ADD;
  - specular;
  - vertex fog.

  It ends with xf86's SIMD16 render target write.
- `src\chipsets\intel\g4_3d.c`, `intel_g4_3d.h`: the state blocks (VS
  passed through, SF, WM, COLOR_CALC, viewports, SURFACE_STATE,
  SAMPLER_STATE) and one batch per draw. The batch runs: MI_FLUSH with
  instruction invalidate, PIPELINE_SELECT, STATE_BASE_ADDRESS at the
  reserve, the binding table and pipelined pointers, URB_FENCE inside one
  64-byte line, CS_URB_STATE, the drawing rectangle, the depth buffer, one
  vertex buffer, seven vertex elements, 3DPRIMITIVE TRILIST, MI_FLUSH and
  MI_BATCH_BUFFER_END. Layouts are genxml `gen4.xml`'s; the URB partition
  and unit choices are xf86's `sna\gen4_render.c`. `v9x_g4_batch_check`
  refuses any batch that is not what the builder emits.
- `src\display32\d3d\d3d_g4.c`: the engine. Synchronous:
  1. drain;
  2. rewrite the state, kernels and vertices in the reserve's free 896 KiB;
  3. submit;
  4. wait for the breadcrumb.

  Mapping policy is Haswell's, through `d3d_hsw_map.c`. Intel's surface
  format numbers are the same on Gen4 and Gen7.5.
- `v9x_d3d_i9xx_submit_g4_batch` in `d3d_i9xx.c`, **a new external symbol
  in the HAL**, for the reason `submit_blt` is one: the breadcrumb sequence
  stays private to the Gen3 file. It puts `MI_BATCH_BUFFER_START` (GTT,
  non-secure, as i915's `gen4_emit_bb_start`) and the breadcrumb in the
  ring. Michael asked for the work to continue overnight without stopping
  for approvals; this is the design change to review.
- Selection: `V9X_DD_ENGINE_CAP_I9XX_GEN4`, stamped by the GM965
  descriptor, routes Direct3D to the Gen4 engine. The Gen3 engine refuses
  when it is set.

## Measured

| Boot | Run | Result |
|---|---|---|
| 8 | V9XD32 `/bpp16` (640x480x16, Z16) | PASS, 0 failures: T1 0/3861 mismatches, T2 corners, T3 depth, T5 precision, T6 the four texels exact, T7 blend average `847D00`, T4 off-screen 0 mismatches |
| 8 | V9XD32 (640x480x32, Z16) | PASS, 0 failures |
| 8 | V9XD32 `/z24` (32-bit Z, D24_UNORM_X8 linear) | FAIL from T3 on: **the 3D pipe hung** |
| 9 | the same three, D16 only | 16 bpp PASS, 32 bpp PASS, `/z24` refused (`NO-Z-AT-DEPTH`, HAL Z depth 16 only) |

The draws ran on the GPU. After boot 8's first V9XD32 run the session
stamp read `EngineCaps=00040410` (GEN4, ASYNC, D3D) and
`Direct3DMode=hardware`. The ring had advanced from 0 to `0x298`, about
one sealed submission per probe draw. IPEIR and EIR read 0.

The hang, read afterwards with V9XG4MM:

| Register | Value |
|---|---|
| HEAD / TAIL | `00000660` / `000006C0` |
| ACTHD | `006A20F8`: reserve `670000` + batch `32000` + `F8`, dword 62, the `MI_BATCH_BUFFER_END` after the closing MI_FLUSH |
| IPEHR | `02000000`: MI_FLUSH |
| INSTDONE | `FF45F8FD` (`FFE5FAFE` when idle) |

The MI_FLUSH waited for a 3D pipeline that never drained. The difference
from the passing runs is the depth buffer's format (3, D24_UNORM_X8, from
DirectDraw's heap) and its 4-byte cells; the batch is otherwise the
same. The 965 PRM permits linear depth and lists D24_UNORM_X8 for every
project. Mesa's Gen4 driver never puts a linear D24X8 buffer in front of
the hardware, so it neither confirms nor contradicts this. Not pursued: the
engine sets `depth32_bits` 0 and publishes `DDBD_16` only. Whether a tiled
D24, a D24_UNORM_S8 cell, or a 64-byte-aligned base would run is open.

**`reset` after a GPU hang recovered this machine**, unlike the Haswell
RCS hang that hard-locked the i5-4570.

## 3DMark 2000 v1.1 Pro, default benchmark (boot 9)

Installed from `3DMark2000v11.exe` (19,950,524 bytes, CRC `0FA79279`, as
on TOMMO33) and registered with the published Futuremark key, on
Michael's instruction. The default benchmark ran to its score: 1024x768,
16-bit colour, 16-bit textures, 16-bit Z, triple buffer, on "Velocity9x
Intel GMA X3100 (GM965)". The details name V9XHAL.DLL 0.23.00.0000,
chipset `2A02`, and 6544 KB of video memory.

| | |
|---|---|
| 3DMark result | **825** (CPU speed 87) |
| Game 1 Helicopter, low / medium / high | 11.7 / 9.0 / 4.7 fps |
| Game 2 Adventure, low / medium / high | 17.5 / 14.3 / 11.5 fps |
| Fill rate, single / multi texturing | 187.4 / 189.5 Mtexels/s |
| High polygon count, 1 / 4 / 8 lights | 1148 / 1092 / 1055 Ktriangles/s |
| Texture rendering, 8 / 16 / 32 / 64 MB | 56.2 / 35.2 / 21.2 / 11.7 fps |
| Bump mapping | not supported (one texture stage) |

During the run, V9XG4MM read the ring advancing with no error: HEAD's wrap
count went from `1BB` to `25D`, IPEIR and EIR were 0, and ACTHD equalled
HEAD. The run finished with the machine responsive. Screens:
`boot9-3dmark2000-*.png`. The score is recorded, not compared; every draw
is synchronous today. Image correctness was not inspected frame by frame:
screenshots are blind during flips.
