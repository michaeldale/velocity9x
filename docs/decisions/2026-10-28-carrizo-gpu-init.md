# Carrizo's 3D engine configured as Linux's gpu_init does: the writes land, the draw still writes nothing

Date: 2026-10-28

Status: **measured, one machine, one run; the draw does not work yet.**
M-XP7053's Radeon R7E (`1002:9874`), the same session as
[the first draw attempt](2026-10-28-carrizo-first-draw-attempt.md) (boot
not re-read). Phase 2 of [the 3D plan](../plans/ati-carrizo-gfx8-3d.md).
Report in
[`../probe/m-xp7053-carrizo-gpu-init-2026-10-28/`](../probe/m-xp7053-carrizo-gpu-init-2026-10-28/).

## What was built

- `vi_gpu_init_tables.c`, generated by `gen-carrizo-gpu-init.ps1` from
  Linux v4.9 `gfx_v8_0.c` (MIT; its SHA-256 is checked):
  `cz_mgcg_cgcg_init` (75 entries), `cz_golden_settings_a11` (12),
  `cz_golden_common_all` (8), and the Carrizo tile (32) and macrotile
  (16) tables, evaluated from the field macros against `gfx_8_0_sh_mask.h`.
- `vi_gpu_init.c`: one ordered list of 224 register writes, the three
  tables then `gfx_v8_0_gpu_init`'s own (`GRBM_CNTL`, `GB_ADDR_CONFIG` and
  `HDP_ADDR_CONFIG`, the tile tables with Carrizo's skipped entries,
  `SH_MEM_*` for VMIDs 0-15 through `SRBM_GFX_CNTL`, `GRBM_GFX_INDEX`
  broadcast, `PA_SC_FIFO_SIZE`). `DMIF_ADDR_CALC` is a display register
  and left out. Host test `test_gpu_init`, written first; it failed to
  build before the module existed.
- `CZCP.VXD` gained a table op: entries of offset, clear mask and value,
  applied as `amdgpu_program_register_sequence` does. Every offset is
  checked against the 38 runs those writes cover before any is written.
  The probe's single `GB_TILE_MODE8` write and its restore are gone.
- `V9XCZ3D.EXE` applies the list before `rlc_resume`, as
  `gfx_v8_0_hw_init` does, and does not put it back afterwards.

## What ran

| Register | Before | After |
|---|---|---|
| `PA_SC_FIFO_SIZE` | `00000000` | `98184020` |
| `SH_MEM_CONFIG` (VMID 0) | `00000000` | `00000378` |
| `GB_TILE_MODE8` | `00C0077C` | `00000004` |
| `GB_ADDR_CONFIG` | `22010001` | `22010001` |

All 224 entries were applied, and the registers read back as written. The
ring test, the full clear state and the draw then ran as before:
- the ring test passed;
- `600DCAFE` landed in 12h polls;
- the draw's end-of-pipe fence landed in 6 polls, and RPTR reached 450h.

All 1,024 target dwords still read the guard `5A5A5A5A`. The CP was
halted and the RLC stopped after the run. SDMA0 and the desktop were
unaffected.

## What the evidence says

The hypothesis the first draw record left open was zero-depth scan
converter FIFOs, or an SQ with no memory configuration. It is dead:
both were zero, both now hold Linux's values, and the result is the same.
The BIOS did leave all of this unwritten, so the list stays. It is the
configuration a driver needs regardless.

A fence that lands in six polls still says the draw passed through the
pipe without doing measurable work. Where it stops is not known. Untested
candidates, cheapest first:

- **The target address.** The CP has written only through `WRITE_DATA`
  and the EOP event, never the colour buffer's path. A CP `WRITE_DATA` or
  `DMA_DATA` into the target would show the address is reachable.
- **Whether any wave runs.** A compute dispatch storing to a buffer
  (no PA, SC, CB) would separate the shader core from the raster back
  end.
- **The render back ends.** `setup_rb` reads `CC_RB_BACKEND_DISABLE` and
  `GC_USER_RB_BACKEND_DISABLE` to size `PA_SC_RASTER_CONFIG`. Golden
  common writes Linux's value, but the fuses were not read. A raster
  configuration that names a disabled back end would drop every pixel.
- **`GRBM_STATUS_SE0` and `GRBM_STATUS2`** sampled while the draw is in
  flight, to see which blocks go busy.

## Not checked

- The golden registers other than those four, read back one by one.
- The CU and RB harvest fuses.
- Whether the GFX state written here survives a mode set or the driver's
  SDMA use. Nothing else on the machine has touched the 3D engine.
