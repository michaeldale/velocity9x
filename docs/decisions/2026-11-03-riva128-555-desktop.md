# RIVA 128ZX: 16 bpp desktops at 5:5:5, by the DAC

Date: 2026-11-03

Machine: M-7V636C (remote help), RIVA 128ZX 8 MiB, Windows 98 first
edition, boot 26, desktop 800x600x16. Plan:
`docs/plans/nvidia-riva128-d3d.md`, step 3. Files:
`docs/probe/m7v636c-riva128-d3d-2026-11-03/hal/b26-*`.

## Why

The D3D object writes X1R5G5B5 and nothing else, and the 2D engine sets
bit 15 at 16 bpp
([2D record](2026-11-02-riva128-2d-engine-writes.md),
[HAL record](2026-11-03-riva128-d3d-hal-first-light.md)). This BIOS lists
46 modes and every 16 bpp one is 5:6:5 (RedPos 11, GreenSize 6 in the
survey); there is no 15 bpp mode. The driver's existing 5:5:5 path programs
a row's 15 bpp sibling, so on this card it found none and stayed 5:6:5.

## What was built

- **The DAC switch.** The nvidia family's `place_desktop` hook runs after
  every mode set and pitch step, on Enable and on the return from a DOS
  box. When the row is 16 bpp and the layout is 5:5:5, it clears bit 12 of
  PRAMDAC general control (BAR0 680600h), through the BAR0 window the
  device's engine descriptor maps. 86Box's `vid_nv3.h` names bit 12
  `NV3_PRAMDAC_GENERAL_CONTROL_565_MODE`, and rivafb writes 00100100h on
  NV3. Off the measured memory size there is no window, and the card keeps
  5:6:5.
- **The row is its own sibling.** In the nvidia build, `modes16.c` takes
  each 16 bpp row's own mode as its 5:5:5 sibling. The masks, FIVE6FIVE and
  DirectDraw's primary format then follow the existing logic unchanged.
- **The NV3 wants 5:5:5**, so with hardware Direct3D the automatic layout
  resolves to 5:5:5 (`dd16.c`).
- **The first Enable.** The layout is decided before stage 3 reads 4F00h,
  and the RIVA claims its engine only at 8 MiB. Its memory check now falls
  back to the mini-VDD's cached 4F00h figure, so the first boot already
  decides 5:5:5.

Not a new `V9X_HW16_OPS` field, which was the first version. Open Watcom
puts the ops tables in `_TEXT` (`-zc`), so a field costs every family two
bytes. intel-gma's `_TEXT` was at 57,343 of its 57,344-byte budget, and
`I9XXCODE` at 57,340. The shared code is under `V9X_NVIDIA_FAMILY`, as in
`gdi_accel.c`. intel-gma's `_TEXT` is 57,343 after the change.

## Boot 26

- `V9XHW.INI`: `ColourLayout=555-auto`, `Direct3DMode=hardware`.
  PRAMDAC general read 00101100h before the switch and 00100100h after
  (1052928 and 1048832 in the INI's decimal), on the boot Enable and again
  after V9XMSW set 800x600x16.
- **V9XDDP:** 200 of its 227 `Ok` keys are non-zero, up from 35 on boot
  25, and none that was non-zero on boot 25 is now zero (last value of
  each key in the step logs). Newly passing:
  - every textured check (Tex2-256 halves, the 4444 and R565 halves,
    clamp, decal, modulate);
  - the full mipmap texture matrix (`TexMatrixOk` 75h, from 0Ch);
  - the Z compare and write-mask ladders, alpha curves, fog and table fog,
    perspective, sprites, vertex alpha blend, and the 320 and 640 render
    targets (`TargetsOk` 6, from 2).

  Same batches as boot 25: 592 drawn, 7 refused, no engine timeout.
- **V9XGDI /accel:** PASS at 16, 32 and 8 bpp. 16 bpp is drawn by the CPU
  at 5:5:5 (engine disabled there, as before); 32 and 8 bpp use the engine
  as on boot 18.

## Still failing on V9XDDP (27 keys)

- Mipmap level choice: ChainA-E, ChainRows, MipLadder, MipTri,
  MipTriDegraded, D3DMipmapLevelSelect, D3DTrilinearBlend.
- Colour key: ColorKeyOk, ColorKeyHalvesOk.
- Specular: D3DSpecularGouraudOk, D3DSpecularTexOk.
- Z with perspective: D3DZPCompareOk, D3DZPWriteMaskOk.
- 2D and 3D in one surface: Mixed*.
- Formats the chip has no texture format for: Tex8A8888, Tex8X8888.
- Refused or not corrected: Tex8DecalAlpha4444, Tex8DecalAlpha565,
  Tex8Bilinear (the half-texel offset).
- FlipPixelOk, which also failed on boot 25. Not investigated.

## Not seen

What the monitor shows. Agent screenshots read the framebuffer through
GDI, which now agrees with itself at 5:5:5 whatever the DAC does. Only
the readback of the register says the DAC changed; the owner has to look
once at a 16 bpp desktop to confirm the colours are right.
