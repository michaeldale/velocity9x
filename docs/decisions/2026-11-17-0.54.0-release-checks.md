## The two failing machines

**W9QI0DAD, Oland XT.** Both V9XD32 runs fail on T19 FfSpecFog alone,
the known mismatch
([issue](../issues/2026-11-17-t19-ffspecfog-mismatch-oland-gt218.md)).
Every other T19 row passes, and `T20ModAlphaOk` is 1. The `/bpp16` run
reports `T19DisplayFormat` 16h (X8R8G8B8), the same as the default: the
switch does not change T19's format on a 32 bpp desktop, so both runs
measured 32 bpp. That is a probe trait, not a driver change.

**M-BXMFA8, GeForce 210.** V9XD32 fails T19 on ten rows at X8R8G8B8
(tolerance 2): FourTex, Kill, Bem, KillFog, Cube, Normal, FfBem, FfSpec,
FfSpecFog and FfTwo, with about 1,040 pixels each. That is whole draws.
0.53.1's GT218 check ran on W9QI0DAD at R5G6B5, where only Cube, Normal
and FfSpecFog failed, so this was the first 32 bpp T19 on a GT218 in
any release check.

To tell a regression from an old fault, the machine's boot 142 set was
put back by WININIT rename and checked by hash (boot 145). That set
predates this release's GT218 change, 448e2f2d. Then the same V9XD32
binary ran at the same desktop:
- the same ten rows failed;
- `T20ModAlphaOk` was 0, against 1 on 0.54.0.

The ten failures predate 0.54.0: a 32 bpp fault in the GT218's
pixel-shader draws, not yet filed or traced. The MODULATE fix shows
there as ModAlpha 0 to 1. Evidence:
[`../probe/0.54.0-release-checks-2026-11-17/gt218-ab-boot142/`](../probe/0.54.0-release-checks-2026-11-17/gt218-ab-boot142/).
M-BXMFA8 then got the 0.54.0 nvidia set back.
