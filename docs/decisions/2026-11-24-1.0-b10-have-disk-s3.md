# B10, the s3 package by Have Disk on a guest that never had the driver: it installs and starts, and the Display Properties tab never registered

Date: 2026-11-24 (started 2026-11-23). Machine: 86Box, clones of
`Win98SE-Native-S3` (the S3 reference VM: ViRGE/DX `virge_dx_pci`, S3's
own Windows 98 SE driver "S3 ViRGE-DX/GX PCI (375/385)", 1024x768x16,
remote agent 0.18.0), each clone with its own MAC, host port 9879 and COM
pipe; the reference VM itself was not started or changed.

## The guest had never had Velocity9x

On each clone, before the install: no `V9XDISP.DRV`, `V9XMINI.VXD` or
`V9XHAL.DLL` in `C:\WINDOWS\SYSTEM`, no `C:\V9XDIAG`, no Velocity9x INF
in `C:\WINDOWS\INF\OTHER`. Four clones were made from the same disk
image (SHA-256 of the VHD equal to the reference's); each was used once.

## Released 0.60.0, as a user gets it

`releases/0.60.0/velocity9x-0.60.0-s3.zip`, its SHA-256 `10CEA784...`
matching `SHA256SUMS.txt`, unpacked on the host and copied into the
guest as `C:\V9X060S` (the guest has no unzip; the files are the zip's).
Then the package's own INSTALL.TXT steps, by the agent's mouse and keys:
Control Panel, System, Device Manager, Display adapters, the S3 adapter,
Driver, Update Driver, "Display a list...", Have Disk, `C:\V9X060S`.

- Have Disk offered one compatible model, "Velocity9x S3 ViRGE/DX
  86C375". Windows copied the files with **no prompt for
  `V9XDISP.DRV`** (the 2026-08-29 report) and asked to restart.
- Before the restart `HKCC\Display\Settings` kept S3's 1024x768x16
  (`BitsPerPixel=16`, not 4) and no `WININIT.INI` was queued.
- First boot (85): `Stage=enable-ok`, `DriverInitResult=ok`,
  1024x768x16, `Adapter=S3 ViRGE/DX 86C375`, `Direct3D=hardware-s3d`.
  So **no 16-colour first boot** on this package and card (the
  2026-11-07 report was the `intel-gma` package on Eee PCs).
- **Display Properties had no Velocity9x tab.**

## Why the tab was missing

Windows 98 keeps a Display property-sheet handler only if its `Tag`
DWORD checks out against a per-machine seed, and deletes the key
otherwise (`settings_propsheet.c`). The INF writes the handler key and
puts `rundll32 v9xsetp.dll,V9xRegisterPage`, which writes the right Tag,
in RunOnce for the first boot. A replay on a second fresh clone, reading
the registry at each step (`released-0.60.0-replay/`):

| Moment | Handler key | RunOnce |
|---|---|---|
| Before the install | absent | empty |
| After the files were copied | present, `Tag=0xDD2532C1` | empty |
| After Finish | the same | empty |
| After the restart, at the desktop | the same | empty |
| After Display Properties opened | **deleted** | empty |

The installer writes the key with a Tag of its own; the shell's seed on
this machine is `0xC4754D1C` (the same from all three neighbour
handlers: PlusPack, DeskHtmlExt, Voodoo2), so the right Tag is
`0x3EEABBC9`. The RunOnce value was gone before the first boot, so
`V9xRegisterPage` never ran after the install, and the first Display
Properties deleted the key. Run by hand, `V9xRegisterPage` wrote
`0x3EEABBC9` and the tabs appeared. This is the netbook's missing tab of
2026-10-04 too
([issue](../issues/2026-10-04-netbook-settings-page-not-registered.md)),
whose cause was never found. When or whether Windows ran the RunOnce
value during the install was not read.

## The fix

`V9xSyncModes`, which the INF's Run key starts at every logon, calls
`V9xRegisterPage` first; `V9xRegisterPage` now returns at once when the
handler already holds this machine's Tag, and otherwise writes it. No
new export (`V9xRegisterPage` was one). `run-checks.ps1` passes.

On a fourth fresh clone, the same Have Disk install from the rebuilt
package (`build\win98se-s3`, build `885063bc-dirty`, `V9XSETP.DLL`
SHA-256 `AB200139...` installed): the installer's Tag at the first
desktop, `0x3EEABBC9` after logon, the Velocity9x and Velocity9x Advanced
tabs present, and still there after one more restart (boot 86)
(`fix-verify/`).

On the third clone the tab was still missing: Display Properties was
opened seconds after the desktop came up, before the Run entries had
reached `V9xSyncModes`, so the shell deleted the installer's key first;
`V9xSyncModes` run then wrote the right one. So a user who opens Display
Properties within seconds of the first logon sees no tab until the next
logon.

## Also found

The package's `INSTALL.TXT`, which a user reads first, is still the
bring-up text: "an engineering bring-up build, not a release driver",
prerequisites to cold-copy a VM disk image and capture COM1, and serial
checkpoints. Not changed here; owed before 1.0.

`nvidia`, `sis`, `3dfx` by Have Disk on a guest or machine that never
had the driver (the pre-driver backups of the Trio64 and Mach64 guests
have no network, so no agent to drive them), and the release
candidate's own zips once they exist.
