# GDI acceleration, build 002: non-overlapping screen-to-screen copy

Date: 2026-08-27
Status: accepted

Implements build `gdi-accel-002` of
[`docs/plans/gdi-acceleration.md`](../plans/gdi-acceleration.md). The
infrastructure and harness are
[2026-08-26-gdi-accel-000.md](2026-08-26-gdi-accel-000.md); the fill is
[2026-08-26-gdi-accel-001.md](2026-08-26-gdi-accel-001.md).

## What changed

`V9X_GDI_DEFAULT_COPY` goes from 0 to 1. Non-overlapping screen-to-screen
`SRCCOPY` now runs on the engine on both S3 chips - the operation behind a
window scroll or a window move, and the one the 32-bit HAL already measured at
six times the CPU copy's rate on the same registers
([2026-08-14-virge-blitter.md](2026-08-14-virge-blitter.md)).

Overlap stays off. An overlapping same-surface copy is only correct if the
engine walks from the corner that keeps it correct, and that is build 003's
claim to make.

`C:\V9XHW.INI` now reports `GdiAcceleration=gdi-fill-copy` on both S3 guests and
`none` on the Mach64 VT2.

## The one real defect, and how it was found

Not by the harness - by reading the reference driver before flipping the
default, which is the habit build 001's fill defect earned.

**A copy has to exclude the software cursor from the source rectangle as well
as the destination.** A fill only writes; a copy *reads* the framebuffer, so a
software cursor sitting over the source is part of the pixels the engine copies,
and it lands a second cursor in the destination. The reference driver keeps two
separate exclusion routines for precisely this distinction:
`B_SWCursorExcludeRect` for the pattern paths and `B_SWCursorExcludeUnion` for
`DSP_ScreenBlt` (`98DDK/src/display/mini/s3v/S3BLT.ASM`). This driver had only
the destination form, written for the fill and then inherited by the copy.

The union is the bounding box of the two equal-sized rectangles - `min` of the
origins, `max` of the origins plus the extent, less one for the last pixel
drawn - which is what `B_SWCursorExcludeUnion` computes and what the driver
computes now.

### This class of bug cannot be checked from a Win32 application at all

An automated check for it was written, and then measured to be vacuous. It is
worth setting out in full, because the conclusion is a property of the DIBENG
cursor contract rather than a shortage of effort, and because the check was
briefly believed to be sound.

The check placed the pointer inside the source rectangle, issued the copy
directly rather than approximating it through USER's window-move behaviour, and
compared the result against a reference DC that has no cursor. A dropping would
be a mismatch. It looked airtight.

A driver deliberately built to exclude only the destination rectangle passed it
**40 iterations out of 40**. Twice:

1. First because the phase's window class had `hCursor = 0` - the struct was
   zeroed and never given one - so USER drew no cursor over that window and
   there was no cursor image in the framebuffer to copy. That was a defect in
   the check and was fixed.
2. Then, with a real class cursor, it passed 40 out of 40 again.

A premise probe added to find out why - compare immediately after positioning
the cursor over the source, which must fail if a cursor is really there -
reported that no cursor was visible. And that probe explains the whole thing,
including itself:

> Every way a Win32 application can read the screen goes through GDI, GDI goes
> through the DIB Engine, and the DIB Engine announces framebuffer access
> through `deBeginAccess` - **which lifts the software cursor before the read
> happens.** The readback therefore never contains the cursor, whatever the
> driver did or did not exclude.

So no comparison built on a screen readback can distinguish a correct source
exclusion from a missing one. The check was removed rather than kept: a green
light that cannot go red is precisely the failure the `/accel` phase exists to
prevent, and it would have been shipped inside the phase built to prevent it.

**The cursor-over-source case therefore has no automated coverage in this
project.** The fix rests on the reference driver's authority for its shape -
`B_SWCursorExcludeUnion` exists, and it is what the reference calls from
`DSP_ScreenBlt` - and on somebody looking at a screen for confirmation. The
window-drag soak the exit gate asks for supplies volume through USER's own copy
paths and a survival check, which is real, but it does not verify pixels and
should not be described as though it did.

## What the harness could not exercise, and now can

The copy generator produced only *overlapping* copies: its shift was 8 to 31
pixels against a rectangle of 48 to 167, which always intersects. Against build
002 that would have meant every copy declining, no copy firing, and
`copy-enabled-but-never-fired` - the anti-vacuous-pass check doing its job on a
harness that could not reach the feature under test.

Disjoint copies are now generated, and their disjointness is constructed rather
than hoped for: the source lies entirely in the left half of the test area and
the destination entirely in the right, so they cannot intersect on x whatever
the y offsets are. The y offsets still vary, which exercises the engine's scan
direction on a copy where direction cannot affect the result. The smallest
rectangle is 32x32 = 1024 pixels, exactly the accelerated threshold, so the
boundary is covered on purpose.

## Build 002 makes two claims, so both are checked

A build with copy on and overlap off says two things: disjoint copies are
accelerated, and overlapping ones are not. Only the first had a check.

`decline_overlap` is now its own counter rather than part of the geometry tally,
and the run fails with `overlap-declines-never-exercised` when copy is enabled,
overlap is not, and no overlapping copy was declined. If that fires, either the
generator stopped producing overlapping copies or the gate stopped catching them
- and the second means an overlapping copy executing on an engine that was
never told which corner to start from, which is a smeared rectangle on a live
desktop.

The counts from the first run make the correspondence exact rather than
plausible: **99 disjoint copy operations produced 99 engine copies, and 58
overlapping operations produced 58 overlap declines.** Nothing was
double-counted, nothing leaked between the two paths.

## A difference from the reference, recorded for build 003

The reference's `ScreenToScreenBlt` flips the X and Y scan directions
*independently*, testing each and applying both when both apply. This driver,
following the 32-bit HAL, uses `if (dest_y > src_y) ... else if (dest_y ==
src_y && dest_x > src_x) ...` - either the Y flip or the X flip, never both.

That is correct, and for a reason worth writing down rather than rediscovering:
when the copy moves vertically, walking rows from the far end already
guarantees that every source row is read before it is overwritten, so the
within-row direction cannot matter. The X test is only needed when the copy
stays on the same rows. The classic rule and the 32-bit HAL agree.

It is also moot at build 002, which declines every overlapping copy. It becomes
load-bearing at 003, and 003 should satisfy itself on this point directly rather
than inheriting the reasoning above - the reference doing something more general
is a reason to check, not a reason to assume one of the two is wrong.

## Verification

Build id `gdi-accel-002`. `run-checks` green on all four families. Enable gate
`Stage=enable-ok` on all three emulated targets, with `Started=false`
throughout - the guests were already up and the gate did not disturb them.

### Mode matrix

| Guest | Engine | Modes | Result |
|---|---|---|---|
| ViRGE/DX (`:9869`) | `EngineType=1` | 11/11 | `enable-ok`, V9XGDI PASS, `/accel` PASS |
| Trio64 (`:9871`) | `EngineType=2` | 11/11 | `enable-ok`, V9XGDI PASS, `/accel` PASS |
| Mach64 VT2 (`:9873`) | `EngineType=0` | 6/6 | `enable-ok`, V9XGDI PASS, `/accel` PASS |

Every accelerated mode on both S3 chips reported the same triple: **198 fills,
99 engine copies, 58-65 overlap declines**, `Compared=PASS`, no uninjected
timeout, no poison before the deliberate injection. The 32-bpp modes reported
zeros with every check recorded as skipped. The counts are reproducible because
the operation stream is seeded, so their invariance across four depths and two
chips is itself the evidence that nothing here is depth- or chip-dependent.

The `ati` run is the regression check: `Enabled=0`, `EngineType=0`,
`CopiesDelta=0` in all six modes. Turning copy on for the S3 changed nothing for
the three families that have no engine.

### DirectDraw regression

| | reference range | build 002 |
|---|---|---|
| Ironfield ViRGE | 18 FPS, 303-310 frames | 18 FPS, 310 frames / 16537 ms |
| Ironfield Trio64 | 16 FPS, 274-280 frames | 16 FPS, 274 frames / 16572 ms |

Both inside their bands. Worth noting against build 001's write-up: that run
measured 19 FPS and 321 frames on the ViRGE, marginally above the band, and was
reported as measured with no mechanism claimed. This run is back inside the band
on the same guest with more acceleration enabled, which supports reading the 001
figure as run-to-run variance rather than an effect.

`V9XDDP` reports `Result=COMPLETE` with all fifteen modes enumerated on both S3
guests.

### Not covered

- **The cursor-over-source case**, for the structural reason above. No automated
  check in this project can reach it.
- **Overlapping copies**, which are declined by design until build 003 - and the
  decline is now itself checked.
- **The `vbe` family's enable gate**, whose guest is QEMU-hosted.

## Still off

- **Overlap** (build 003), declined by rectangle intersection and now
  measurably so.
- **CPU-to-screen upload** (build 004) and **extra ROPs** (005).
