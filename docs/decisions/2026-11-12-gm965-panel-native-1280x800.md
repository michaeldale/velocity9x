# TOMMOHP's panel at its own 1280x800: the BIOS slot patch, measured

Date: 2026-11-12. Machine: TOMMOHP (`M-KYHT4Q`), GM965 GMA X3100
`8086:2A02`, 1280x800 LVDS panel on pipe B, Windows 98 SE, agent
`dev-fault-3` (0.16.0). Build: `5dc632be` (intel-gma package and mini-VDD).
Captures: [`../probe/tommohp-panel-1280x800-2026-11-12/`](../probe/tommohp-panel-1280x800-2026-11-12/).

## Why

The owner asked whether the laptop can run above 1024x768. Its video BIOS
heads a panel slot (VBE 163h-165h) 1280x800 but fills it with a 1024x768
descriptor, so VBE described the panel's mode as 1024x768 and the BIOS
scaled 1024x768 to the panel with the fitter
([`../issues/2026-11-06-intel-vbios-mode-table-lacks-panel-modes.md`](../issues/2026-11-06-intel-vbios-mode-table-lacks-panel-modes.md),
the offline table read in `69450ae0`).

## What was built

`5dc632be`: `src\common\vbios_panel.c` plans the patch from the shadowed ROM
and the EDID (host-tested); the 16-bit driver runs it at Enable on the
GM965 only and stores `SYSTEM.INI [Velocity9x] VbiosPanelPatch`; the
mini-VDD applies it at the next Device_Init, before the VBE collection,
only while the ROM holds the planned bytes, through PAM1 (0:0.0 91h) bits
1:0.

## What was measured

- **Boot 45** (install by `run-release-checks.ps1`, a one-machine list):
  `V9XHW.INI VbiosPanel=planned 12BC 91 03 641900404100263018883600000000000018 C71B00A050201730302036004BCF10000018`.
  The old bytes are the 1024x768 placeholder the offline read found; the
  new ones are the panel's own EDID descriptor: 1BC7h = 71.11 MHz,
  1280 + 160, 800 + 23, sync 48/32 and 3/6, image 331 x 207 mm. The same
  record went to SYSTEM.INI. All seven probes passed at 1024x768.
- **Boot 46** (reset): `VbiosPanel=already` with the same offset, so the
  mini-VDD had written the descriptor before the driver read the ROM. The
  VBE collection now describes `0163/0164/0165` as `1280x800x8/16/32`
  (pitches 1280/2560/5120, `V9XBOOT.INI` VbeMode03-05), the runtime table
  published them (`V9XMODES.INI` Row06/09/0d, `src=dynamic`), and the
  recommendation changed from `edid-unpublished` to
  `Recommendation=1280x800 reason=edid-preferred`.
- **Boot 47**, after `HKLM\Config\0001\Display\Settings` `Resolution` was
  set to `1280,800` (`RES1280.REG`, by `regedit /s`): `Stage=enable-ok`,
  `Surface=pitch=2560 bpp=16 w=1280 h=800`, agent `ScreenWidth 1280
  ScreenHeight 800`, the desktop drawn (`desk1280.png`).
- **The display, read with V9XG4MM** (read-only, `V9XG4MM-1280.INI`),
  against the 2026-10-20 reading at VBE 640x480:

  | Register | 2026-10-20 | Boot 47 | |
  |---|---|---|---|
  | PIPEBSRC | `027F01DF` | `04FF031F` | source 1280x800 |
  | PFIT_CONTROL | `A8000000` | `20000000` | fitter off |
  | HTOTAL_B / VTOTAL_B | `059F04FF` / `0336031F` | same | the panel's timing |
  | DSPBCNTR | `C9000000` | `95000000` | plane on, 16 bpp 5:6:5, pipe B |
  | DSPBSTRIDE | `280` | `A00` | 2560 bytes |
  | DPLL_B / FPB0 | `98046A00` / `00021407` | same | the same clock |
  | LVDS | `C2308300` | same | |

  The BIOS sets the panel 1:1 from the patched slot: same pipe timing and
  clock, the fitter off, the plane at 1280x800.
- **Probes at 1280x800x16**, boot 47, nothing installed (`boot47-probes/`):
  V9XD32 PASS, V9XGLP PASS, V9XGLIDP PASS failures=0, V9XR3DP COMPLETE,
  V9XWPRS PASS, V9XFBCMP PASS with `Differ=0` and its wide-surface check
  at 1920 wide `WideResult=PASS`.

## What it does not show

- The panel was checked by its owner only, by eye, after boot 47: it
  "looks good" (relayed by Michael, 2026-11-12). No photograph.
- The PAM register and its bit layout are from the 945/965 datasheets. The
  write landing and reading back (boot 46) is consistent with them; the
  PAM value before and after was not logged.
- One stray registry value: a first `.REG` built with `printf` turned
  `\0001` into a NUL, and regedit wrote `Resolution="1280,800"` onto
  `HKLM\Config` itself. Windows does not read it there; REGEDIT4 cannot
  delete it. Left in place.
- The 1280x768 slot (60h-62h, block 129Ah) still holds the placeholder;
  this panel has no use for it.
- No other chip runs the plan: `intel_panel16.c` gates on 2A02.
- Undo: `RES1024.REG` puts the desktop back to 1024x768; removing the
  SYSTEM.INI record stops the patch from the next boot.
