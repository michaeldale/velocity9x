# B1 on a second family: the Oland's back-buffer Lock ran ahead of the flip on 0.59.0 and waits on the fix

Date: 2026-11-23

## Reading (written by hand; the rest of the record is generated)

W9QI0DAD, Radeon Oland XT `1002:6610`, FX-6300, Windows 98 SE, desktop
1024x768x32. dispbench `FlipSafety` (DB3D `381b802`, the command in the
[B1 issue](../issues/2026-11-21-haswell-lock-does-not-wait-for-pending-flip.md)
with `-EndpointHost 10.0.1.172`), at 1024x768, 16 and 32 bpp.

The machine's `[Velocity9x] VSync=2` (Michael's) makes every flip unsynced,
and FlipSafety cannot judge without a vertical blank. It was set to
`VSync=0` for these runs (boot 125 to 126) and put back afterwards, the
file byte-identical to the saved original (boot 127 to 128).
`SYSTEM.INI-original-vsync2.txt` in the evidence folder is that original.

| Build | Boot | Lock: early / judged | Draw: early / judged |
|---|---|---|---|
| released 0.59.0 (`6899f1cd`), 16 bpp | 126 | 114 / 114 (`writes-reach-the-page-on-screen`) | 0 / 119 (`held`) |
| released 0.59.0, 32 bpp | 126 | 117 / 117 (`writes-reach-the-page-on-screen`) | 0 / 119 (`held`) |
| `713bc38a-dirty` (the code of `6a1c80d0`), 16 bpp | 127 | 0 / 119 (`held`) | 0 / 119 (`held`) |
| `713bc38a-dirty`, 32 bpp | 127 | 0 / 119 (`held`) | 0 / 119 (`held`) |

On 0.59.0 every judged Lock returned within 0-7 % of a refresh of the
blank's end, so the CPU's write reached the page on screen. On the fix,
every Lock returned at 95 % of a refresh, at the next blank. V9XTRACE
after both fixed runs (`oland-after-flipsafety.INI`):
`LockFlipPending=240`, `LockFlipWaited=240`, `LockFlipWaitTimeouts=0`,
`DrawsIntoPresented=0`, `EngineIdleTimeouts=0`, `EngineResets=0`;
driver, HAL and trace builds agree.

So the gap was not Intel's: the shared Lock path ran ahead of the flip on
GCN too, and the fix holds it on both families. The release probes on the
fixed build match boot 123's (all pass but the known V9XD32 T19).

The runner installed the package already built in the previous session
(`713bc38a-dirty`), not one rebuilt from `55f4ccfa`; that build's code is
what `6a1c80d0` committed. The 0.59.0 on the machine at boot 125 was
identified from its HAL's build string (SHA-256 `E7C3C264...`).

Not measured: whether the wait changes a program's frame rate.
