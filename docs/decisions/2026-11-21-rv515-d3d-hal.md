## The change

The HAL must know it has an R500 before it writes 3D state, and every
engine-capability bit is taken. So the X1300 gets engine type 18,
`ATI_RV515`; Michael chose this over overloading a chip-identity bit.

The RS690's engine (`eng_rs690.c`), scanout (`rs690_scanout.c`) and
Direct3D code (`d3d_rs690.c`, `d3d_rs690_map.c`) accept the new type. For
it:
- the 3D init is `rv515_3d.c`'s;
- every state is `v9x_rv515_build_3d_state`: the RS690 builder's lists
  through the R500 fixup, with R500 rasterizer setup and programs;
- the vertex runs and the finish are unchanged.

`d3d_select` gives the type the RS690 engine when `CAP_D3D` is stamped,
and the renderer is named "Velocity9x Radeon X1300". The RV515 row stamps
`CAP_D3D`; the manifest says `Direct3D = hardware-rv515-pio`. The ati
driver's `_TEXT` is 57,311 of 57,344 bytes.

## Boot 46

- `V9XHW.INI`: `Direct3D=hardware-rv515-pio`, `Direct3DMode=hardware`,
  `EngineCaps=00000017` (fill, copy, flip, D3D).
- `V9XD32` at 32 and 16 bpp: `Failures=0x00000002` both times. The one
  failure is T22X: an XRGB8888 texture draws black. The RS690 HAL offers
  only RGB565, ARGB1555, ARGB4444 and ARGB8888 (`d3d_rs690.c`
  `v9x_d3d_rs690_format_of`), so it refuses the draw on either chip, as
  the RV630 did before its fix
  ([`2026-11-13-rv630-direct3d-hal-first-light.md`](2026-11-13-rv630-direct3d-hal-first-light.md)).
  The RV280's HAL passes T22X since it offered XRGB8888. This is a gap in
  the shared code, not an R500 fault.
  - Everything else passes or skips for want of a feature the engine does
    not claim: T1, T4, T13, T14, T15 and T16 pass; T12 is skipped (one
    stage), T18 finds no T&L device, T19 no pixel shaders.
- `V9XDDP` (`Result=COMPLETE`, two files): its `*Ok` keys equal the RS690's
  last full run
  ([`rs690-mixed-engine-2026-11-06`](../probe/rs690-mixed-engine-2026-11-06/))
  key for key, with these exceptions:
  - The two Mixed keys, which that run took with the opt-in Mixed test on
    and this one with it off.
  - `TargetsOk`, 12 here against 6 there. That key is a count, not a pass
    flag; what changed between the two runs was not looked into.

  Failing on both chips: chain, colour-key-halves, mip-gap/trilinear,
  ZP compare/mask, FlipPixelOk (the GDI-readback instrument defect) and
  Tex8X8888.
- 3DMark 2000, default benchmark: completed, 2836 3D marks (screenshot
  saved). Per the project rule this is a recorded score, not compared with
  anything. Nobody watched the frames; the frames are not known to be
  right.
- `V9XTRACE` after all three programs (`V9XSNA4.INI`):
  - driver and HAL both `72d05d70`, `EngineType=18`, `EngineFlags=9`;
  - `M64Draws=2280408`, `M64Triangles=95113833`, `M64TextureDraws=2069202`;
  - `M64Refused=90` across the three processes (the probes refuse on
    purpose, T22X among them), `M64Unrenderable=0`, no timeouts;
  - `FlipHandled=10655`, `FlipTakenAtDone=10652`, `FlipDeclined=0`;
  - `CountBltEngine=15401`.
- `BootCounter` stayed 46 throughout.
