# GDI acceleration, build 001: the first accelerated drawing operation

Date: 2026-08-26
Status: accepted

Implements build `gdi-accel-001` of
[`docs/plans/gdi-acceleration.md`](../plans/gdi-acceleration.md). Build 000, its
infrastructure and its harness, are
[2026-08-26-gdi-accel-000.md](2026-08-26-gdi-accel-000.md).

## What changed

`V9X_GDI_DEFAULT_FILL` goes from 0 to 1. Solid rectangle fills on the screen
now run on the engine on both S3 chips: `PATCOPY` with a solid brush, and
`BLACKNESS`/`WHITENESS`. This is the first drawing operation Velocity9x
accelerates outside DirectDraw.

Everything else is unchanged. Screen-to-screen copy is compiled and still off,
waiting for build 002. `ati`, `vbe` and `matrox-m2` decline every operation and
always will - they have no 2D engine, and the per-chip capability clamp refuses
the fill on their behalf even with the compile-time default on. Measured: with
no `SYSTEM.INI` at all, `C:\V9XHW.INI` reports `GdiAcceleration=gdi-fill` on
both S3 guests and `none` on the Mach64 VT2.

## The defect that had to be fixed first

Build 000's deliberate `GdiAccelFill=1` run proved the primitive could fire and
proved it painted the wrong colour. That is recorded in full in
[the issue](../issues/2026-08-26-gdi-fill-brush-colour-not-physical.md); the
short version is that the dispatcher took its colour from the realized brush's
`FgColor`, which `DIBENG.INC:189` labels "Physical fg color" and which actually
holds the **logical** `COLORREF`. Handing that to the ViRGE's `PATTERN_FG`
painted the low byte - the red channel - as a palette index, so every colour
with red 255 came out white.

The physical value lives in `Bits`, and the reference driver says so in
first-party code (`PB_SolidPatBlt`, `98DDK/src/display/mini/s3v/S3BLT.ASM`):

```
        mov     ecx,dword ptr ds:[si.dp8BrushBits] ; ECX = solid foregnd color
        ...
        EngineWrite B_PAT_FG_CLR,  es, ecx ; write ECX = foreground color
```

Worth keeping the reason, because it shows no other field could have worked:
DIBENG renders `Bits[]` at the **destination's** depth, so its first DWORD is
already the physical value replicated across the dword - four pixels at 8 bpp,
two at 16 - which is exactly the form a pattern-colour register wants. A single
logical RGB could not have served both depths whatever the driver did to it.

Two corrections came with it.

**The brush style is checked before the flag.** `PatternBlt` branches on
`BrushStyle` first, and only `BS_SOLID` means a solid colour: `BS_HOLLOW` draws
nothing at all, and the other two carry a pattern this driver does not read. The
original gate tested `COLORSOLID` alone and would have solid-filled a hollow
brush.

**BLACKNESS and WHITENESS stopped being normalised into a colour.** They now
reach the ViRGE as ROPs in `CMD_SET` bits 24:17, which is what `DoBltNoDSP`
does: with an all-ones mono pattern the engine generates the pixel values from
the ROP alone, so neither chip needs an opinion about what black and white are.
The Trio64's 8514/A command set has no ROP field - `FRGD_MIX` selects a mix, not
a ternary operation - so there the two stay a solid fill of 0 or of all ones.

That last change retires an open question build 000 had to carry. The original
normalisation wrote the all-ones bit pattern for `WHITENESS`, matching both DDK
reference blitters, while GDI documents the operation in terms of physical
palette indices; on a desktop whose realized palette does not put white at 0xFF
those are different answers. Letting the hardware's own ROP field decide means
the question never has to be answered.

## What the harness cost, and what it returned

Four bugs in the harness itself, all found against a DIB Engine reference at
000 and 001, and all four of the same shape: the harness asserting something the
driver had never claimed. Three of the four were surface-format or depth
assumptions.

1. **A 24-bpp reference against an 8-bpp screen** (build 000). `PATINVERT` XORs
   the destination, so one side XORed palette indices and the other RGB bytes.
2. **The zero-counter check firing on a 32-bpp desktop** (build 000), where the
   depth gate correctly refuses every fill. Now conditioned on the depth, and it
   reports whether it ran so it can never skip silently.
3. **The injection step selecting its brush into one DC of two** (this build),
   comparing a red screen against a white reference. `MismatchBytes` at exactly
   two thirds of the region is what gave it away - red and white differ in green
   and blue and agree in red.
4. **The injection step gated on `enabled` alone rather than on the depth**
   (this build), so every 32-bpp mode asserted that an injection had been
   consumed when the depth gate had declined every operation before any bounded
   wait could run. The same mistake as (2), made twenty minutes after fixing
   (2), in the check next door - build 000's plan even states the rule it
   violates. Both now share one `accelerated_depth` predicate rather than two
   conditions that merely look alike, and each records why it skipped.

Each of those would have presented as a driver defect in an already-signed-off
primitive had the harness landed after 001 rather than before it. That is the
argument the plan made for the ordering, and it has now been paid four times.

The diagnostics that made the fill defect a ten-minute diagnosis rather than a
guessing game - `LastRop256`, `LastColor`, `LastBrushFlags`, `LastBrushBpp`,
`LastBrushStyle`, `LastBpp`, and the mismatching pixel from both sides - are
kept. `LastBrushBpp=8` and `LastBrushStyle=0` are what ruled out the two wrong
candidates: the brush *was* realized at the screen's depth, so it was neither a
depth mismatch nor a missing palette translation.

`/inject:N` and `/stats` were added for a reason worth stating: fault injection
and the poison latch are properties of the bounded-wait and recovery paths, not
of any primitive's pixel output, and `/accel`'s own injection step sits behind a
passing comparison. With a primitive that fires but paints wrongly, that gate is
unreachable, and the recovery paths would have gone untested for the wrong
reason. The two claims are now separable.

## The second defect: the spin limits were 64 times too short

Found by the mode matrix, on the Trio64 only, and it is the reason this build
took two passes.

`V9X_GDI_IDLE_SPIN_LIMIT` was 0x00010000, scaled down from the 32-bit HAL's
0x00400000 on the grounds that this driver is built without a `-3` so one
iteration costs 60-100 clocks against the flat HAL's ten. **That scaled the
wrong quantity.** An iteration's cost is its bus access, not its instructions:
on the Trio64 every spin is an `in ax,dx` on a 9AE8h port, which is ISA-timed at
roughly a microsecond and costs exactly the same in 16-bit and 32-bit code, and
on the ViRGE it is an uncached MMIO dword read. The loop overhead is noise
beside either, so the two bitnesses' iterations cost about the same and their
limits belong in the same order.

The measurement that found it:

| Mode | Fill bytes | Outcome at 0x00010000 |
|---|---|---|
| 640x480x16 | 614 KB | fine |
| 1024x768x8 | 786 KB | fine |
| 800x600x16 | 960 KB | fine |
| 1280x1024x8 | 1.31 MB | **idle wait expired, session poisoned** |
| 1024x768x16 | 1.5 MB | **idle wait expired, session poisoned** |
| 1280x1024x16 | 2.6 MB | **idle wait expired, session poisoned** |

`IdleTimeouts=1` with `Resets=0` on each - correct, the Trio64 has no recovery
path, which the 32-bit side measured too. The desktop stayed correct throughout,
because a failed operation is completed by the DIB Engine; what was lost was the
feature, silently, for the rest of the boot. The ViRGE passed all eleven modes
at the same limit, and that asymmetry is what identifies the cause rather than
merely the symptom: its MMIO read is cheaper than a port cycle.

The limits are now the 32-bit values. The cost of being generous is bounded and
paid at most once per session, because an expiry latches the poison - a
genuinely hung engine stalls for a few seconds and then acceleration is off for
good, which is the trade the 32-bit side already accepts on the same registers.

### The harness passed it, twice over, and both holes are closed

This defect was in the first 001 matrix run and the run reported PASS. Two
independent reasons, both worth fixing regardless of this bug:

1. **The zero-counter check compared `fills` against zero, not against its own
   starting snapshot.** The driver's counters do not reset per Enable and the
   mode matrix runs the original V9XGDI smoke phase in the same boot first, so
   fills from that earlier phase satisfied a check that was supposed to be about
   this run. It compares deltas now.
2. **Being poisoned is a legitimate state and nothing asserted against it.** A
   session that poisoned itself on real work looked identical to a healthy one.
   The run now fails on `poisoned-before-run` and `poisoned-during-run`.

The first is the more embarrassing: a check built specifically to prevent a
vacuous pass, passing vacuously one level up.

## Verification

Build id `gdi-accel-001`. `run-checks` green on all four families. Enable gate
`Stage=enable-ok` on all three emulated targets.

### Mode matrix, all three guests

| Guest | Engine | Modes | Result |
|---|---|---|---|
| ViRGE/DX (`:9869`) | `EngineType=1` | 11/11 | `enable-ok`, V9XGDI PASS, `/accel` PASS |
| Trio64 (`:9871`) | `EngineType=2` | 11/11 | `enable-ok`, V9XGDI PASS, `/accel` PASS |
| Mach64 VT2 (`:9873`) | `EngineType=0` | 6/6 | `enable-ok`, V9XGDI PASS, `/accel` PASS |

The per-mode shape is the point rather than the PASS column, because it is what
says the gates are doing their jobs:

- **Every 8- and 16-bpp mode on both S3 chips: `FillsDelta=197`.** The engine
  performed 197 fills out of each run's 500 operations, `Compared=PASS`,
  `ZeroCounterChecked=1`, `InjectionChecked=1`, `PoisonedAfterInject=1`. The
  Trio64 consumes its injection through `IdleTimeouts` and the ViRGE through
  `FifoTimeouts`, which is correct - the Trio64 has no FIFO status to wait on.
- **Every 32-bpp mode: `FillsDelta=0`, both checks skipped and recorded.** The
  depth gate declines above 16 bpp by design, so no primitive can fire and no
  bounded wait can run; asserting otherwise is what produced two false
  positives before both checks were put on one predicate.
- **Every mode on the Mach64 VT2: `Enabled=0`, `EngineType=0`, `FillsDelta=0`.**
  The per-chip capability clamp refuses the fill on a chip that claims no
  `SOLID_FILL`, with the compile-time default on. That is the regression check
  that turning fill on for the S3 did not disturb the three engine-less
  families.
- **No uninjected timeout anywhere.** `IdleTimeouts=0`, `FifoTimeouts=0`,
  `Poisoned=0` in every mode before the deliberate injection, on both chips, at
  the corrected spin limits.

Fill correctness holds at both accelerated depths, and `LastColor` shows it:
0xFF at 8 bpp and 0xFFFF at 16 bpp for a `WHITENESS`, which is the
depth-correct all-ones value and confirms that the `Bits` DWORD carries the
right form at each depth rather than only at the one it was debugged on.

### DirectDraw regression

GDI now shares the 2D engine with DirectDraw for the first time, so this matters
more here than it did at 000.

| | reference range | build 001 |
|---|---|---|
| Ironfield ViRGE | 18 FPS, 303-310 frames | 19 FPS, 321 frames / 16744 ms |
| Ironfield Trio64 | 16 FPS, 274-280 frames | 16 FPS, 280 frames / 16917 ms |

The Trio64 is inside its band. **The ViRGE is marginally above it** - one frame
per second and about 3.5 per cent more frames than the best of five prior runs -
and that is reported as measured rather than rounded into "unchanged". It is not
a regression, which is what the gate asks; whether it is real or run-to-run
variance is not established by one run, and no mechanism is claimed. Ironfield's
`-benchmark -fullscreen` path is DirectDraw throughout, so the most likely
explanation is variance rather than the new fill.

`V9XDDP` reports `Result=COMPLETE` with all fifteen modes enumerated on both S3
guests.

## Still off, and why

- **Screen-to-screen copy** (build 002). Compiled, gated, and declining. Its
  `PALETTE_XLAT` exemption is already in place and is load-bearing there rather
  than here: an 8-bpp desktop with an active palette translate is exactly the
  desktop whose window scrolls and moves 002 exists to accelerate.
- **Overlap** (build 003). Declines by rectangle intersection until then.
- Nothing else from the parent plan's open items. Item 3, the 16-bit spin-limit
  calibration, is closed in this build - see below.
