# GeForce 9500 GT (G96): Direct3D on NV84_3D, with the Z kept as Z24S8

Date: 2026-11-28

Phases 4 and 5 of [docs/plans/nvidia-g96-geforce9500gt.md](../plans/nvidia-g96-geforce9500gt.md),
on M-Z2T02D. Follows [2026-11-28-g96-flips-from-the-vbios.md](2026-11-28-g96-flips-from-the-vbios.md).

## Phase 4: the channel

Already answered by the 2D record: the GT218's channel, context program
(nouveau's pre-A0h branches) and bring-up run on the G96 with only the
VM trap value changed.

## Phase 5, step 1: the methods

Every 3D method the Direct3D path names (61 `V9X_8597_*` offsets, in
`nv50_3d.h`, `nv50_3d.c` and `nv50_d3d.c`) was mapped by a script onto
Mesa's `nv50_3d.xml.h`: each has an `NV50_3D_` name, so each exists in
every Tesla class, NV84_3D included. None is one of the `NVA0_3D_` or
`NVA3_3D_` methods Mesa gates by class (`BLEND_INDEPENDENT`, the per-RT
blend functions, `TEX_MISC`, `FP_MULTISAMPLE`, `SAMPLE_SHADING`). No
method is sent by raw number. The setup push is xf86-video-nouveau's
NVAccelInitNV50TCL, which that driver sends unchanged to every Tesla class.
The row-block arithmetic (`nv50_rblock.c`) is nouveau's for the whole family.

## Step 2: the class

`nv50_chan.c` puts the 3D object's class by chipset, as
xf86-video-nouveau and Mesa choose it: NV84_3D (`8297h`) below A0h,
NVA0_3D (`8397h`) at A0h, NVAF_3D (`8697h`) at AFh, NVA3_3D (`8597h`)
otherwise. A host test over seven chipsets failed first (five wrong)
and passes now. The G96 row stamps `D3D` and `D3D_DDI8`; Direct3D names
the device "Velocity9x GeForce 9500 GT" by its PCI id.

## Boot 12: nothing drawn

V9XD32 at 32 bpp: every call returned `S_OK`, every pixel check read 0,
`RunIdleTimeouts=3`. The HAL's fault record (`V9XN50F.TXT`):
`PgraphIntr=00100000` (ERROR), `PgraphTrapClass=00008297` (the class
change took), `PgraphTrapAddr=82011228`: subchannel 1, method `1228h`
ZETA_HORIZ, data 280h and 1E0h (640 by 480). Our ZETA setup is Mesa's
`nv50_validate_fb` word for word, so the data was not the fault; the
format was. Mesa's `nv50_screen_is_format_supported` refuses
`PIPE_FORMAT_Z16_UNORM` when the 3D class is below NVA0_3D. The GT218's
Direct3D keeps its Z as Z16 (`V9X_NV50_3D_ZETA_Z16`, kind 6Ch).

## Step 3: Z24S8 on the G96

`d3d_nv50.c` keeps the G96's Z as Z24S8 (format 16h, four bytes a
pixel) through the kind-28h window the channel already maps (the GT218
channel probe's `ZDepth24S8` stage drew through it). The GT218 is
unchanged. Applications still see a 16-bit Z buffer; it was tiled, and
so not readable as one, already.

## Boot 13

Set by WININIT (DRV, VxD, HAL, SETP, GL; HAL hash-checked), `reset`.

V9XD32 (`d3d32-probe-local`, this tree), at 32 and at 16 bpp:
`RunIdleTimeouts=0`, `RunFifoTimeouts=0`, and every stage passes but
one: T1 and T4 and T14 flat `EXACT`, T3 7, T8 F, T6 F, T22A and T22X F,
T7 1, T9 F, T10 3F, T12 FF, T13, T15, T16 and T21 `PASS`, T20 `F203`.
**T5 fails as designed**: it checks that a 16-bit Z cannot separate two
quads a tenth of a 16-bit step apart, and a Z stored at 24 bits does, so
the nearer red quad is drawn (`T5Pixel=00FF0000` at 32 bpp, `F800` at 16).
`Failures=1` both times.

On a 1024x768x32 desktop (set by V9XMSW), T19, the DirectX 8 interface:
pixel shader 1.1 `FFFF0101`; Push, FourTex, Kill, Bem, PushFog, KillFog,
Cube and Normal `pass`; FfDot3, FfDot3F, FfBem, FfBem3, FfSpec,
FfSpecFog, FfSpecU, FfSpec2 and FfTwo `pass`; FfBemL8 and FfBemL6
`skip-no-texop`. **Dxt1, Dxt3 and Dxt5 `mismatch`**, MaxChannelError 4,
3 against a tolerance of 2 (Dxt1: 364 of 1040 pixels, e.g. want
`AF6B68`, got `B06868`). The GT218 passes these.
