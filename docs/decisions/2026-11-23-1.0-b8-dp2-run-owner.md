# B8: a pending DrawPrimitives2 run is drawn only by the process that queued it; DDHELP no longer faults beside UT2004

Date: 2026-11-23

## Reading (written by hand; the rest of the record is generated)

The fault
([issue](../issues/2026-11-23-ddhelp-destroysurface-runs-another-process-draw.md)):
DDHELP called the HAL's DestroySurface, which calls
`v9x_d3d_dp2_flush_pending` before a surface goes, and that drew the
pending DrawPrimitives2 run under its context's state. The triangles are
copies, but the state names the queuing process's surfaces, and one of
its texture pointers was in that process's private arena. The T&L batch
already had this guard (`v9x_d3d_tnl_pending` compares the context's `pid`
with the caller's, since DDHELP faulted the same way on the HD 4600, boots
101 and 102); the DrawPrimitives2 run did not.

The change (`src\display32\d3d\d3d_core.c`): `v9x_d3d_dp2_flush_pending`
draws the run only in the process whose context queued it; anywhere else
it discards the run and counts it in `dp2_foreign_dropped` (appended to
`V9X_D3D_DIAGNOSTICS` within ABI 2026112001; V9XTRACE writes
`Dp2ForeignDropped`). The owner loses those triangles. `d3d_core.c` is
not in the host build, so the check is measured on the guests only.
`run-checks.ps1` passes.

The two builds below are both labelled `a92e01f3-dirty` (one commit,
dirty both times); they differ by HAL. The B2 build's, on which DDHELP
faulted, is SHA-256 `24BB5351D31FD3DA...`; the fix's is
`7BAFCE3A3AC5DEF5256BAF2F30BEF92E48B63AD4BDB0A9D4E065D1FDAD82A5C1`,
read back from both machines after the runs.

The B8 case on each machine: UT2004 demo (Direct3D 8) windowed, a
