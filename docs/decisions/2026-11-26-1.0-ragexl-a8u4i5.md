# Rage XL on the 0.61.0 tree: probes pass but for V9XD32's first additive-blend and 32-bit texture checks; GLQuake refuses nothing and shows lightmaps only with -nomtex

Date: 2026-11-26. Machine: A8U4I5 (Pentium III 1 GHz, 128 MiB, Windows
98 SE), its Rage XL PCI (`1002:4752`, subsystem `1002:8008`). Build: the
`ati` package of `6244dc08-dirty` (the 0.61.0 tree), installed by
`run-release-checks.ps1 -Machine ragexl` (WININIT renames, `reset`,
8 of 8 files hash-checked, boot 695 to 696). The first card of the
A8U4I5 round; the last Velocity9x run on this card was October's.

## Getting the card onto our driver

The machine came up on ATI's own Rage XL driver (`DISPLAY\0020`,
`ati2ddad.drv`, an error code 255 in its key) at 640x480 in 16
colours. Velocity9x's Rage XL key from October (`Display\0007`) was
still present. The devnode's `Driver` was set back to `DISPLAY\0007`
through the agent (previous value `DISPLAY\0020`, recorded), and the
first run then found Windows at 640x480x4 with `vga.drv`'s 16-colour
mode, so 3DMark 2000 refused to start ("needs DirectX 7"):
`HKLM\Config\0001\Display\Settings` held `BitsPerPixel=4`, the trap
this machine hit with the SiS 6326 in October. Set to 16 and
`800,600` (previous values recorded) and restarted: boot 695 came up
`enable-ok` at 800x600x16, and the checks below ran from there. The
agent was updated from 0.15.0 to 0.19.0 first.

## Release checks

| Check | Result |
|---|---|
| V9XD32 `/bpp16` | FAIL, two of its tests: T20 (blend and texture states) and T22 (32-bit textures) |
| V9XGLP, V9XGLIDP, V9XWPRS, V9XFBCMP | PASS |
| V9XR3DP | COMPLETE |
| 3DMark 2000, default benchmark | ran to its score, 239 (recorded, not compared); 479,328 Mach64 draws, 155 refused (last reason 4, write mask), none into the presented buffer, no engine stall |

The ten 3DMark frames V9XTRACE grabbed (Helicopter and Adventure) are
whole (`ragexl/3dmark2000-grabs.jpg`).

**T20:** every state draws but additive blending: `T20Ok=FFF3`, its
two ADD cells (`T20AddRed`, `T20AddBlue`) read 0. **T22:** the A8R8G8B8
and X8R8G8B8 textures are created, locked and drawn without an error
(every `Hr` 0), but every judged pixel is 0. Neither test had run on a
Mach64 before (no V9XD32 report from October has a T20 or T22 line), so
these are first measurements, not regressions. Cause not looked at.

## GLQuake, the owed runs

Windowed 640x480, `+gl_texsort 0 +timedemo demo1`, as October's run
(`docs/probe/a8u4i5-rage-xl-glquake-2026-10-08/`):

| Run | Result | ICD |
|---|---|---|
| `-nomtex` | 969 frames, 51.1 s, 19.0 fps | 734,209 batches on the engine, `hw-refused=0/0`, `draw-invalid=0`; `alpha-dropped=11954` |
| multitexture (control) | 969 frames, 48.6 s, 19.9 fps | `hw-refused=0`, `draw-invalid=0` |

October's `-nomtex` run refused 111,915 batches; now none. But the
walls show only their lightmaps, as on the GMA 950 today
(`glquake-nomtex/mids.jpg`), and the control draws textured, lit walls
(`glquake-mtex/mids.jpg`). That fault is already a README known issue
for the GMA 950 and is left for 1.1; it is now seen on the Mach64 too.

The oversize-texture fix (`v9x_gl_tex_fit`, 2026-10-04): no draw was
invalid or refused in either run, where October's refusals were the
console's 512x256 texture. Whether a texture over 256 was bound in
these runs was not read from the log.
