# SiS 6326 page flips: the start address, and what FlipPixelOk can see

Date: 2026-10-05. Machine: A8U4I5, SiS 6326 card 2 (rev 0Bh), boot 230.
Evidence: `docs/probe/a8u4i5-sis6326-flip-2026-10-05/`. Follows
[the Direct3D engine](2026-10-05-sis6326-d3d-engine.md) and
[15-bit Z](2026-10-05-sis6326-z-compares-15-bits.md).

## The defect

V9XDDP's `FlipPixelOk` failed on every SiS run, before and after the
Direct3D engine (boots 208, 209 and 229), with `Flip20Ms=0`.

The SiS family declared no V9X_DD_ENGINE_CAP_FLIP, so
`v9x_can_set_display_start` answered no and the HAL declined every primary
flip to DirectDraw. The VGA fallback could not have served it anyway: its
start-address bits 19:16 go to S3's CR69.

## The change

`eng_sis6326.c` writes the 6326's start address:
- CR0D holds bits 7:0, CR0C bits 15:8, and SR27 D[3:0] bits 19:16
  (registers section 2, datasheet 7.7.38).
- The unit is doublewords, so twenty bits reach 4 MiB.
- SR27 D[7:4] (Turbo Queue, engine enable, logical width) are kept as
  read.
- An offset that is not a whole doubleword, or lies past 4 MiB, is
  declined.

`v9x_set_display_start` dispatches to it when the engine type is SIS_6326
and CAP_FLIP is stamped. `sis6326_hw16.c` stamps the cap; the manifest
lists `FLIP`. Timing is the VGA path's: the write happens at any time, and
the flip completes at the next vertical blank.

## Measured (boot 230)

| | Before | After |
|---|---|---|
| `Flip20Ms` (20 flips) | 0 | 328 ms (16.4 ms each, the 60 Hz retrace) |
| `FlipMaxMs` | 0 | 17 |
| `FlipHandled` / `FlipDeclined` | 0 / 46 (boot 228 trace) | 23 / 0 |
| `FlipPixelOk` | 0 | 0 |

V9XDDP completed, and the snapshot read `EngineIdleTimeouts=0` with 11
batches refused (the fog, specular and DESTCOLOR draws).

## Why FlipPixelOk still reads 0

The check fills the back buffer red, flips, and reads screen pixel
(100,100) through GDI; then it does the same with blue. GDI reads its own
page at offset 0, not the page being scanned out, as the check's comment
says. Across every recorded run:

| Runs | 20 flips | FlipPixelOk |
|---|---|---|
| Rage IIC boots 126-130 | 505-507 ms | 1 |
| Rage IIC boot 142, flips in hardware | 308-331 ms | 0 |
| Rage XL PCI, vsync on and game-decides | 332 ms | 0 |
| SiS boot 230 | 328 ms | 0 |
| SiS boots 208, 209, 229; Rage IIC boots 131-141 | 0 | 0 |

The check passes only at about 25 ms a flip: DirectDraw copying the back
buffer into the GDI page. Real page flips read 0 on every chip, which is
the open instrument issue
[2026-09-02 FlipPixelOk is uninterpretable](../issues/2026-09-02-flippixelok-is-uninterpretable.md).
On the SiS, 0 now means the check cannot see the flip. Before, it meant
the flip never happened.

## Correction to the Direct3D engine record

That record cites "the live snapshot read 0 idle timeouts" for boot 228.
That `V9XSNAP` file (`B228-V9XSNAP.INI`) was stale. A8U4I5's
`V9XTRACE.EXE` was build `e4cbfa0`, which refuses the current HAL
(`Error=abi-mismatch`), so the file read was left over from an earlier
boot (`DumpUptimeMs=860954`). The record's conclusion stands on its other
evidence: every textured check passed, which cannot happen after the
quarantine, and `V9XSIS3D.TXT` was not rewritten. A real snapshot on boot
230, with the current `V9XTRACE.EXE`, reads `EngineIdleTimeouts=0` after
a full V9XDDP run.

## Not established

- **When the 6326 latches the start address.** The flip state machine
  assumes a latch at the vertical retrace, as standard VGA does. A
  mid-frame write was not watched for tearing.
- **Whether SR27 D[3:0] latches with CR0C/CR0D.** A second 640x480x16
  page sits about 600 KB in (25800h doublewords), so every other flip
  wrote 2 to the nibble. Whether it takes effect in the same frame as the
  low bits was not observed.
- **The picture itself.** No capture of the scanout was taken. The 16.4 ms
  pacing says the flips completed at the retrace, not which page was
  shown.
