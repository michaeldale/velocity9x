# RV515 first 3D draw: RS690 state, an R500 shader, and a register that must not be read

Date: 2026-11-21
Machine: remote-help `M-5CAPM3`, Radeon X1300 `1002:7146`, ati `21e0358f`
installed, boots 39 to 44, 800x600 at 16 and 32 bpp.
Probe: `R53D.VXD` + `V9XR53D.EXE` (`tools\diag\rv515_3d*`,
`scripts\build-rv515-3d.ps1`), built from the RS690's `V9XRS3D`; see the
publisher's header for the R500 fixup. Reports in
[`docs/probe/m-5capm3-rv515-2026-11-21/3d-first-draw/`](../probe/m-5capm3-rv515-2026-11-21/3d-first-draw/).
Plan: [`ati-rv515-x1300.md`](../plans/ati-rv515-x1300.md), phase 5, first
step.

## Result (boot 44)

| Test | 16 bpp | 32 bpp |
|---|---|---|
| Quad (flat magenta rectangle, byte-exact) | PASS, 0 bytes wrong | PASS, 0 bytes wrong |
| Triangle (flat green, slanted edge's band not judged) | PASS, 242 inside, 0 wrong | PASS, 0 wrong |
| Gouraud (red/green/blue corners) | PASS, worst 0.66 step | PASS, worst 0.59 step |
| FillAfter3D (2D fill after the 3D tests) | PASS, 0 bytes wrong | PASS, 0 bytes wrong |

Init and every draw ended idle (`RBBM_STATUS` `10000140` at the end), and
the 32 bpp run did a second init on the same boot without trouble. So:

- The RS690 builder's R300-class state works on the R500 once the R300
  rasterizer and shader writes are removed and the scan-converter points
  lose their 1440 offset (the fixup dropped 4 init writes and 11 per draw).
- The R500 rasterizer setup and the one-instruction R500 fragment program
  (OUT temp0 * 1 + 0, loaded through `GA_US_VECTOR_INDEX/DATA` in Mesa's
  r500 order) are right: the interpolated colour reaches the target.
- The vertex stage in PVS bypass works on this TCL chip.
  `VAP_CNTL_STATUS` reads `00020100` after the init (bit 8, PVS_BYPASS).

## The hang that wasn't the draw: reading GB_TILE_CONFIG

The first run (boot 39) timed out at the first wait for idle after the
init. `RBBM_STATUS` read `94000140`: GUI_ACTIVE and bit 26, GA_BUSY in
Linux r300d.h. It stayed that way until a reboot. The machine itself
stayed up. Tracing it took boots 40 to 43:

- `/bisect` (boot 40, 41): the init in chunks of eight writes, a wait and
  16 status reads after each. Every chunk ended idle, 0 busy reads.
- `/watch` (2,000 status reads, nothing written): on a fresh boot 0 busy
  at three times over two minutes (boot 41). After an init it was 2,000
  of 2,000 busy, every read GA_BUSY. In one watch the status read just
  before was idle and the watch was busy throughout, so whatever set it
  came between: the probe's start-up reads.
- `/readafter=XXXX`, one fresh boot each: init, watch, one read, watch.
  Reading `VAP_CNTL_STATUS` (2140h): idle before and after (boot 42).
  Reading `GB_TILE_CONFIG` (4018h): idle before, busy on all 2,000 reads
  after (boot 43). It read back `00000011`.

So on this card a read of `GB_TILE_CONFIG` after the 3D init leaves the
GA busy for good. Before the init the same read is harmless, and every
boot's start-up read was. The RS690 probe reads it after the init on
M-GB8KRE without trouble, so this is an R500 behaviour, or this card's.
Why the read does it is not known. The probe no longer reads it outside
`/readafter`, and no driver code reads it (`rs690_3d.c` and `eng_rs690.c`
only write it).

Hypotheses this kills: the init list leaves the engine busy (the bisect
says no); bypass is refused on a TCL part (the draws pass); the GA goes
busy on its own on this card (a fresh boot stays idle).
