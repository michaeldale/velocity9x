# GT218: Direct3D's programs and vertices on the Tesla 3D engine

Date: 2026-11-14

Step 5a of [docs/plans/nvidia-gt218-3d-z.md](../plans/nvidia-gt218-3d-z.md):
the builders the HAL will draw with (`src/chipsets/nvidia/gt218/nv50_d3d.c`),
measured by the channel probe's `/3d:d3d` stage before any HAL code
depends on them. M-BXMFA8 (GeForce 210, GT218 A8), boots 118 and 119,
probe built from 84c33dda with the working tree's changes. Evidence:
`build/driver-results/m-bxmfa8-gt218-3d/d1-V9XN5CH.INI` to
`d6-V9XN5CH.INI`.

## What the stage draws

Into a 128x72 X8R8G8B8 pitch-linear surface prefilled with a pattern,
four rectangles, two triangles each, one kick each, in Direct3D's vertex
terms (half a pixel added to sx and sy by the builder):

- A: untextured, solid red, rhw 0.5 at every vertex.
- B: REPLACE, a 4x4 texture of 16 distinct texels, nearest, rhw 1.
- C: MODULATE with specular and fog (the 12th program variant), specular
  alpha 0, so all fog; rhw 1 left, 0.5 right.
- D: REPLACE with rhw 1 on the left and 0.25 on the right.

## Final run (`d6`, boot 119): every check passes

| Check | Matching | Wrong |
| --- | --- | --- |
| A, red within one step | 960 | 0 |
| B, each pixel its texel exactly | 960 | 0 |
| C, the fog colour within one step | 960 | 0 |
| D, perspective-correct texel, off texel edges and the diagonal | 804 | 0 |
| Pattern outside the rectangles | 5376 | 0 |

D's 156 edge pixels are not judged. Of D's pixels, 257 would also fit
affine interpolation, so the interpolation is perspective-correct, not
affine.

## What the runs found, in order

1. **Short instructions must come in pairs** (`d1`, `d2`). Draw C
   trapped with `PGRAPH_INTR` 200000h, trap 80h (MP). The MP's own words
   (nouveau `nv50_gr_mp_trap`, read windows added to the probe VxD) said
   INVALID_OPCODE at fragment offset D54h. The opcode registers showed the
   short `interp $r15 v[0x2c]` before it and B1000015h, the first word of
   the long `fadd` after it: the long instruction began half-way through a
   64-bit word. EXA's programs keep their short instructions paired by
   hand. The encoder (`nv50_shader.c`) now puts a short `mov $r0, $r0`
   before a long instruction that would start on an odd word. The host test
   holds it, and EXA's programs still encode word for word.

   Between `d1` and `d2` the fog constants also moved from `c2[]` to
   `c0[]`: the setup binds buffer 2 to the fragment program's slot 0
   (`SET_PROGRAM_CB` 31h | 2 << 12, as Mesa does). `d2` still trapped, so
   that change did not cause the trap. C's exact fog colour from `d3` on
   shows `c0[]` reads the buffer. Whether `c2[]` would also have read it
   was not tried.

2. **No divide by w with the viewport transform off** (`d3`). The
   builder sent (sx w, sy w, sz w, w). A, at w 2, matched in exactly the
   345 pixels where a rectangle at twice its coordinates overlaps the
   expected one: the engine took x and y as given. The builder now sends
   x, y and z as they are.

3. **The varyings start at `v[0x4]`, w at `v[0x0]`** (`d3`). B's texture
   read texel (0, 0) everywhere. The fragment programs read w at `v[0x0c]`
   and diffuse from `v[0x10]`, a misreading of Mesa's slot code. EXA's
   PFP_C and phase 3's Gouraud program, which ran, read w at `v[0x0]` and
   the first varying at `v[0x4]`. With that layout, A, B and C pass
   (`d4`).

4. **The fourth position word is the weight itself** (`d4`, `d5`).
   Sent 1/rhw, D's texels followed weights of w, not rhw: at x 67 it read
   column 1, which weights of w predict (u 0.257). Perspective and affine
   both give column 0. The builder now sends rhw (`d5`).

5. **The test's own model was wrong** (`d5`, `d6`). `d5` failed 350 of
   D's pixels in v, not u. The quad is not a projected rectangle: v/w is
   not planar across it, so each triangle interpolates v differently. The
   first model took v as linear in y. Recomputed per triangle, every
   judged pixel matches (`d6`).

## The HAL's first run (46da5ad4, boot 120)

The driver built from 46da5ad4 (`d3d_nv50.c` on the builders above, CAP_D3D
stamped) was installed on M-BXMFA8 by WININIT renames. The staged files
were gone after the boot and the installed V9XHAL.DLL was the new size.
V9XD32 ran at 640x480x32 with a Z16 buffer on the flip chain (evidence
`d32a-V9XD32.TXT`):

| Check | Verdict |
| --- | --- |
| T1 flat, T4 offscreen flat, T14 | EXACT |
| T2 Gouraud corners | 7 of 7 |
| T6 1555 texture, T22 ARGB8888 texture | 4 of 4 quadrants each |
| T7 half-alpha blend | 807F00h in all 64 pixels |
| T9, T10, T11 (all six cull forms), T13, T16 | pass |
| T3, T5, T8 (depth) | fail: step 5a refuses Z-tested draws, as planned |
| T22X X8R8G8B8 texture | nothing drawn: not a format the engine takes |
| T20 DX5 states, T21 mip chain | partial (T20Ok F203h, T21Ok 1) |
| T4Copy and T4Recopy | 4096 of 4096 pixels wrong |
| Overall | FAIL |

T4Copy blits a 64x64 pattern into T4's render target, which
`create_surface` placed. The first wrong pixel read 1242h, a value the
pattern never holds (its largest is 1000h). The control copy, with no 3D
work before it, fails the same way, so the cause is not the 3D work. It
is not the 2D copy in general either: V9XDDP's fill and source copy
checks pass on the same build (`ddp-46da-V9XDD2.INI`, 16 bpp).

**Explained and fixed: 502D addresses pitch surfaces from 256 bytes.**

1. `/bpp16` (`d32b16`) failed the same way, every copied pixel 0, the
   value the target was cleared to. So the cause is not the depth, and
   the copy was not landing elsewhere.
2. V9XD32 was given the source's address (`d32c16`): the target spans
   83F57A00h to 83F59A00h and the source starts at 83F59AC0h. The
   surfaces don't overlap, but the source is C0h past a 256-byte
   boundary. DirectDraw places surfaces on 8 bytes; xf86-video-nouveau's
   EXA keeps every pixmap on 256.
3. With 935d3c50, `push_fill` and `push_blit` (`nv50_2d.c`) round each
   surface address down to 256 bytes and move the remainder into x and
   the width. On boot 121, T4Copy and T4Recopy have 0 of 4096 wrong at
   both 32 bpp (`d32d`, source 84087AC0h) and 16 bpp (`d32d16`, source
   83F59AC0h). Every other V9XD32 verdict is as before.

This is the 2D engine's, not the 3D engine's, so it predates the HAL:
every DirectDraw fill or copy on the GT218 whose surface was not on 256
bytes went wrong. The installed 2c0f02e8 and main share it. V9XDDP's
surfaces evidently sat on 256 bytes. That the engine ignores the low
eight bits, rather than some other rule, is inferred from the fix
working, not read from a register.

## Step 5b on the card: depth through the shadow targets (1da0a043)

1da0a043 adds the shadow targets and tiled Z16 (the plan's option A).
Each Z buffer is placed block-linear with a tiled colour shadow beside
it. Z-tested draws go to the shadow, which is loaded from and copied
back to the linear target by 502D, and depth fills are drawn. It was
installed on M-BXMFA8 (boot 122; the staged files were gone and the
installed HAL was the new size).

V9XD32, 640x480x32 (`d32e`) and 640x480x16 (`d32e16`), the same at
both depths:

| Check | 5a (46da5ad4) | 5b (1da0a043) |
| --- | --- | --- |
| T3 depth test | 0 | 7 of 7 |
| T5 depth precision | 0 | 1 (T5Pixel 00FF00h) |
| T8 sloped depth, x, y and w | 0 | 4 of 4, crossings at the centre |
| T4Copy, T4Recopy | 0 wrong (935d3c50) | 0 wrong |
| T1, T2, T4, T6, T7, T9-T11, T13, T14, T16 | pass | pass |
| T22X, T20, T21 | not taken / partial | unchanged |

The flip chain's back buffer, the Z buffer and V9XD32's offscreen
target therefore all draw through the loads, resolves and depth fills
in the order DirectDraw asks for them: every frame clears the back
buffer by Blt (the shadow is let go), draws with Z (loaded again) and
is read back by Lock (resolved first). This also measures, for this
case, the two things the code left unmeasured: tiled blocks on 4 KiB,
and 16 bpp block-linear copies.

ZClearFirst and ZDepthFirst read FFFFh through a Lock of the tiled Z
buffer. A constant reads the same in any layout, so this says nothing
about Lock conversion, which there is none of yet.

## Step 5c: 3DMark 2000 (afc43ce4, boot 125)

3DMark 2000 Pro's default run is 1024x768x16, a triple-buffered flip
chain and a Z16 buffer.

**First starts failed: CreateDevice DDERR_GENERIC** (1da0a043, boot
122). The HAL had given the engine up inside a Lock (fault code N5ID at
400700h). A fault record the engine now writes on its first give-up
(`V9XN50F.TXT`, b1a5744a and fe7c2662) found the cause:

- A PROP trap (TP0 status 80000001h, a bit nouveau's table does not
  name) on a 2D blit.
- The blit went into a 420-pixel RGB565 surface with 840-byte rows at
  1A2DD0h. 935d3c50's alignment had moved that destination's base down
  208 bytes and widened it to 524 pixels, past its pitch (`3dm-c`).
- A source widened the same way copied right (T4Copy). A destination
  does not.

**Fixed by afc43ce4:**

- Only sources are moved.
- A fill or copy into a destination off 256 bytes is declined to the
  CPU.
- The engine asks DirectDraw for 256-byte offscreen, overlay and alpha
  alignment, through a new `V9X_ENGINE32_OPS.surface_align`, so
  DirectDraw's own surfaces need no move.

**Then the default run completes (`3dm-d`): score 2762.** The after
snapshot shows:

- the engine still valid, 0 idle timeouts;
- every refusal counter 0;
- 1,633 surfaces the engine placed;
- `FlipDeclined` 68,206: the GT218 row cannot move the display start,
  so DirectDraw presents every flip by its own copy.

The score is recorded, not compared.

**A second run, with V9XTRACE's frame grabs (`3dm-e`), drew right but
3DMark crashed before its score.** The grabbed Game 1 frames (V9XGRAB0
to 7) show:

- the helicopter, textured terrain and sky;
- fog in the distance;
- alpha-tested trees that stand in front of and behind each other, as
  depth decides;
- the rotor's translucent blur;
- the HUD.

3DMark's process then ended at 4.5 minutes without a score window. The
after snapshot records an access violation (C0000005) at 004E23D1 in
3DMARK2000.EXE's own image (004xxxxxh). The engine was still valid with
0 idle timeouts. The scored run recorded no fault. That is one crash in
two runs, the crashing one with grabbing on: not yet known whether the
grab, the driver or chance caused it.

**Pre-merge checks (2026-11-15).**

1. Probes on afc43ce4 (boot 125):
   - V9XD32 at 32 and 16 bpp (`m-d32`, `m-d32-16`): the same verdicts as
     1da0a043.
   - V9XMSW, 4 of 4 mode cycles and 4 of 4 depth cycles; V9XGDI `/auto`
     PASS (`gdi-afc4`).
   - V9XDDP against 46da5ad4 (`ddp-afc4`): 17 checks now pass that
     failed (Z compare, Z write mask, both overlap copies, all twelve
     render-target sizes with texture and Z). One regressed:
     `ZDepthFillOk` 1 to 0. After a depth fill to 1234h, a Lock of the Z
     buffer read 0 at (0, 0). A constant reads the same in any layout,
     so the fill's writes were not in memory where the Lock read, or
     not yet. Not explained; it belongs with the Z-Lock gap.
2. Main (9c5c86dc) merged cleanly (173b5730), but the ati driver's
   `_TEXT` went 27 bytes over the audit budget. The branch's
   `aperture_from_bar` field made each const device record 2 bytes
   larger. 319272ec compiles the field only where it is read: the ati
   image is main's 57,315 bytes again, the nvidia one 57,047, and
   run-checks passes.
3. The merged build (319272ec, boot 127; V9XD32 verdicts unchanged)
   ran 3DMark 2000 three times without frame grabs:
   - `3dm-m1`: score 3052.
   - `3dm-m3`: score 2765.
   - `3dm-m2`: the process ended without a score. Access violation
     C0000005 at 004E23D1 in 3DMARK2000.EXE: the same address as the
     grab run's crash, so the grabs are not the cause.
   - The engine was valid with 0 idle timeouts in every run.
   - Both crashes came near the end of the run (about 5.3 and 4.5
     minutes into runs that take about 6). The fault is in 3DMark's
     code, at one address, in one run of two or three: most likely
     something a late test receives from the driver. Not yet found.

**The crash is 3DMark's own over-read, not the driver's** (2026-11-15).

- The HAL's fault record for `3dm-m2` (`crash/V9XTRACE.INI`, written by
  the HAL's fault filter in 3DMark's process) has EIP 004E23D1,
  ESI 00A00018h, ECX = EDX 009FFFC8h, EBX = EDI 009FFFA0h. The HAL's
  last call was a Flip that returned normally.
- Disassembled from a local copy of 3DMARK2000.EXE: 004E2270 is a
  keyframe evaluator. It searches a vector of 28h-byte keys (begin at
  `[this+5]`, end at `[this+9]`) for the pair bracketing a time and
  takes the neighbours either side for a cubic curve. Its caller
  (00419035) evaluates it at seven time offsets per frame.
- When the time falls in the last segment, the search stops with the
  current key one before `end`. It then advances the next-but-one
  pointer by 28h and compares it with `end` for equality only. It is
  already past `end`, so the check misses, and the code reads one key
  beyond the array (004E23D1, `fld dword ptr [esi]`).
- The registers fit exactly: last key 009FFFC8h, so `end` = 009FFFF0h
  and ESI = `end` + 28h = 00A00018h, in the page after 009FFFFFh, which
  is not committed.
- An over-read past an array's end normally lands in the heap block
  that follows and yields a wrong tangent, silently. It faults only
  when the vector's storage ends within 28h bytes of the end of the
  committed heap.
- That is a matter of the process's heap layout. The driver affects it
  only through the runtime's allocations in the process, which explains
  a fault at one address in two runs of five.

So the fault is not one the driver can fix, and no driver data reaches
the faulting read: the keys are 3DMark's own animation data. Not
measured: whether other drivers' runs on this machine read past the
array too. They would on the same frames, and simply never had the
array at a heap edge in the runs recorded.

**What the copies cost is not measured yet.** Each frame here can take:

- a resolve, at the present's Blt from the back buffer;
- a load, after the clear's Blt lets the shadow go;
- DirectDraw's present copy.

Each is a 1024x768x16 surface, 1.5 MiB. There are no counters for
shadow loads and resolves yet, and none for their time.
