# GT218 Tesla 3D: a pitch-linear texture samples exactly, and 5:6:5 keeps top bits

Date: 2026-11-14

Phase 3 of [docs/plans/nvidia-gt218-3d.md](../plans/nvidia-gt218-3d.md),
on M-BXMFA8 (GeForce 210, GT218 A8), boot 117. Evidence in
`build/driver-results/m-bxmfa8-gt218-3d/`: `p3t-`, `p3t2-` and `p3t3-`
`V9XN5CH.INI`.

## The stage

`V9XN5CH /lean /3d /3d:draw /3d:gouraud /3d:texture`. A 4x4 A8R8G8B8
texture of 16 distinct colours, pitch-linear with rows 64 bytes apart,
stretched over a 40x24 rectangle with nearest sampling: each texel is
exactly 10x6 pixels and no pixel centre lies on a texel edge, so every
pixel has one right value. The texture descriptor is Mesa's for a
texture with no memory type (`nv50_create_texture_view`): TIC word 2
`D005D000h` (pitch layout, 2D without mipmaps, normalized coordinates,
border from colour, the same word EXA's 1x1 solid texture had used),
then pitch, width, and `1 << 16 | height`. EXA's vertex program scales
texel coordinates by 1/width and 1/height from its constants.

## Three runs

| Run | Build | Texture32, Texture16 | What changed |
| --- | --- | --- | --- |
| `p3t` | f550337d | 60 of 960 inside, every pixel texel (0, 0) | first run |
| `p3t2` | 88321c0e | the same, to the pixel | vertex constants sent through the engine (`CB_ADDR`, non-incrementing `CB_DATA`) instead of written by the CPU |
| `p3t3` | f152034a | **960 of 960 at both depths** | the textured draw sets `VP_START_ID` and `VP_ATTR_EN` itself |

In every run the rectangle was in the right place, every border pixel
was untouched, and the pusher and PGRAPH were clean.

**The cause was state left by the stage before.** `/3d:gouraud` runs
first; its draw sets `VP_START_ID` to its own vertex program (200h) and
`VP_ATTR_EN` to F3h/0, which disables attributes 8 and 9, the texture
coordinates. The textured draw set `FP_START_ID` but neither of those,
so it ran the Gouraud vertex program with no coordinates and sampled
texel (0, 0) everywhere. The solid draws run before the Gouraud stage,
which is why they never showed it.

The second run kills the first hypothesis, a stale constant cache:
sending the constants through the engine changed nothing. The engine
upload stays, because it is how EXA does it. Whether constants written
by the CPU after the buffer is bound are seen was not separated, so
nothing should rely on it.

Every draw now sets its own vertex program and attribute enables. That
matters for the HAL: Direct3D state must be set per draw or tracked,
never assumed from the last draw.

## 5:6:5 keeps each channel's top bits

`Texture16` counts each pixel against two conversion rules. All 960 fit
**each 8-bit channel's top bits** (red >> 3, green >> 2, blue >> 3), and
only 420 fit a x31-and-round conversion. With 16 colours whose channels
separate the two, that settles the open point from the first triangle
([record](2026-11-14-gt218-3d-first-triangle.md)) for texels: a texel
written to a 5:6:5 target keeps its top bits. Interpolated colours were
not part of this test.

## Not covered

Filtering other than nearest, mipmaps, swizzled (tiled) textures, other
texel formats, blending, and a depth buffer. The draws are still the
probe's, not the HAL's.
