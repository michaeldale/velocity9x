# B6 on the Oland R7 250: the screen shadow copied a cursor-sized square of stale desktop onto a full-screen game; reproduced, then fixed by reading the cursor's rectangle back from the screen during exclusive mode

Date: 2026-11-25. Machine: W9QI0DAD, Radeon Oland XT `1002:6610`, `ati`
package, the B8-fix set (`V9XHAL.DLL` `7BAFCE3A...`), desktop 1024x768x32,
boots 133-135. Issue:
[2026-11-13-evergreen-cursor-square-over-fullscreen-game](../issues/2026-11-13-evergreen-cursor-square-over-fullscreen-game.md).
Until now B6 was a field report from one HD 5570, with the reporter's
word that `NOSHADOW.TXT` removes it.

## The probe

`V9XCURSQ.EXE` (new, `tools/diag/cursq_probe_win32.c`) behaves like a
game that never hides the cursor. It opens a top-most popup window whose
class cursor is the arrow and whose background is black. It takes
exclusive full screen and runs two cases at 640x480x16, each 90 frames,
moving the cursor every frame on a 12-pixel circle around the centre:

- **flip:** a primary and one back buffer, the back filled green by the
  engine, then `Flip(WAIT)`;
- **blit:** a lone primary, filled by the engine, then locked and a row
  written by the CPU.

It then holds the cursor at (332,240) and reads each buffer of the chain
back through a Lock. 320x240x16 was asked for too and refused,
`DDERR_INVALIDMODE` (88760078): this card's VBE list has no 320x240
mode. Bug! at 320x240 ran in mode `0193h` on the HD 5570.

## Results

| Boot | Shadow | 640 flip: GDI's buffer (offset 0) | 640 flip: other buffer | 640 blit |
|---|---|---|---|---|
| 133 | on | **SQUARE**: box 328,240-364,280, 1,376 pixels, 95 % of it, black and white | clean | clean |
| 134 | off (`NOSHADOW.TXT`) | cursor: box 320,240-354,265, 669 pixels, 78 % | clean | clean |
| 135 | on again | **SQUARE**, identical to boot 133 | clean | clean |

With the shadow, the box is the arrow drawn on solid black: two 32x32
cursor rectangles, 4 pixels apart. The black is the probe window's
background, which is what GDI last drew there, so what the shadow holds
(`run1/box-ascii.txt`). The other buffer of the chain is clean. A square
that sits in one buffer of two flickers at the flip rate, which fits the
report. The blit case is clean both ways.

Without the shadow there is no square, but the buffer is not clean
either: the arrow over the green, an hourglass beside it (the cursor
while the probe started), and black blocks (`run2-noshadow/box-ascii.txt`).
That is the DIB Engine's software cursor saving and restoring its
background in the GDI buffer while the game flips other pictures through
it. It is not the shadow's doing, and the probe counts it as `CURSOR`,
not `SQUARE`. Whether a driver with a hardware cursor would show
anything here is not measured.

## Why, from the code

`src/display16/shadow16.c` copies the cursor's rectangle from the shadow
to the frame buffer on every set, move and check
(`v9x_shadow_copy_cursor`), and on every cursor exclusion's end. The
HAL stops writing the shadow while a process holds exclusive mode
(`v9x_shadow_for` in `src/display32/ddhal_core.c` returns null unless
`v9x_present_gdi_may_draw`), because GDI is off the screen until the
desktop is repainted. The 16-bit half is not told, so each cursor move
during the game writes a 32x32 block of what GDI last drew there over
the game's frame at offset 0. The shadow's event log could not confirm
this: after the mode restore the desktop's repaint filled all 128
entries, so the game-time events were gone by the time the probe read
the log.

## The fix

Hiding the cursor in exclusive mode would remove the square, but it
would also remove the pointer from games that use Windows' cursor over
DirectDraw. What the screen shows without the shadow, an arrow over
the game, is the behaviour to keep.

- `V9X_DD_SHARED.shadow_hold`, a new DWORD appended within ABI
  2026112001 (228 bytes of the 12 KiB block left), is written by the HAL
  as `!v9x_present_gdi_may_draw()`. It is published after
  SetExclusiveMode, FlipToGDISurface, every accepted Flip, and
  DriverInit, since a game's mode change brings a freshly filled block.
- `shadow16.c`: while the hold is set, the cursor's rectangle is read
  back from the frame buffer before the DIB Engine saves under the
  cursor or draws it. That happens on set, move and check, and at both
  ends of a cursor exclusion. The copy-out then carries the game's
  pixels with the arrow on them. The read-back is skipped while a
  drawing bracket is open, whose drawing is in the shadow only.
- This is a shared design, so it applies to every family with the
  shadow (`vbe`, and the Evergreen, SI, VI, CIK, RV280 and RV515 `ati`
  rows). It was run on the Oland only.

Gates: `run-checks.ps1` green. Boot 136, installed by
`run-release-checks.ps1` (8 of 8 files hash-checked; HAL SHA-256
`FD8C63BE...`, `V9XDISP.DRV` `4E81CAAA...`, build `61c64630-dirty`).
V9XD32 verdicts at 32 and 16 bpp are unchanged from the B8-fix checks
(T19 fails in both). V9XGLP, V9XGLIDP, V9XR3DP, V9XWPRS and V9XFBCMP
pass.

The box after the fix (`../probe/1.0-b6-fix-oland-2026-11-25/cursq/box-ascii.txt`)
is the arrow on green with black blocks beside and below it, as in the
`NOSHADOW.TXT` run: the software cursor's own save-under in a buffer the
game flips through. The shadow's event log rolled over again, so the
probe has no record of the read-backs themselves. Not run: a real game
(Bug! is not on any of our machines), 320x240 (no such mode on this
card), and the other shadow chips.

## On the R3E (M-JJN1ZZ, Mullins), later the same day

Main's `ati` set (the B6 and T19 fixes; packages labelled
`2c432932-dirty`, the same code as `e6e14b2a`) was installed by
`run-release-checks.ps1 -Machine jjn1zz` over the remote-help relay:
boots 56 to 57, 8 of 8 hashed. Every V9XD32 verdict (default and
`/bpp16`, `Failures=0`) and V9XGLP, V9XGLIDP, V9XR3DP, V9XWPRS and
V9XFBCMP read as at 0.55.0, the last complete check on this machine.
V9XCURSQ: 640x480 flip `CURSOR`, 684 pixels in 328,240-364,273, 57 %,
the other buffer and the blit case clean, exit 0, the same numbers as
the fixed Oland. 320x240 is refused here too. The old driver was not
run on the R3E, so the square was never reproduced on it: this shows
the fix holds on a second GCN chip, not that the R3E had the fault.
