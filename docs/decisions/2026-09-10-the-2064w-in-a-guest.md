# A Millennium guest in an hour: an inbox driver, a candidate that loads, and a stage name that lied

Date: 2026-09-10. 86Box guest `Win98SE-Millennium`, agent port 9877, boots 15
to 25. Nothing physical.

The four BringupKit runs earlier today produced two facts that could not have
been inferred from the Millennium II - a padded 800x600 pitch, and an aperture
that accepts only 2-byte accesses in VGA mode - and confirmed several that
could. An emulated guest was built afterwards to see what the same hour buys
on the other side of a mode set. It bought more, including one fact that
changes how this card gets driven at all, and it also caught two defects in
this driver's own failure reporting.

## The guest

`Win98SE-VBE-Tier0` cloned, `gfxcard = millennium` (86Box models `MGA_2064W`
and ships the real `matrox2064wr2.BIN`), `memory = 4`, fresh UUID and MAC,
COM1 to a file, agent forwarded on 9877. No "moved or copied" modal, which is
what a fresh MAC buys (2026-08-29's correction to that trap).

Note for anyone comparing it with the physical card: 86Box's ROM is a
different image - 65,536 bytes, revision "r2" - from the 32,768-byte V1.9
shadow captured from the physical board. The mode tables agree on the modes
this family sets; the pitches do not, which is recorded below.

## Windows 98 has an inbox driver for this card

The first boot came up at 1024x768x16 with no VGA-fallback dance, and the
registry says why:

```
InfPath          DXMGA.INF
DriverDesc       Matrox MGA Millennium
MatchingDeviceId PCI\VEN_102B&DEV_0519
drv              mgapdx64.drv
minivdd          mgapdx64.vxd
```

`MGAPDX64.DRV`, 126,880 bytes, with its own mini-VDD at 51,059 - and
`MGAPDX64.DRV` is the exact filename this family's guarded replacement
targets. So the candidate's install route exists on a stock Windows 98
machine with no Matrox retail download, which was an open question an hour
before: the historical 2164W work used a guest that already had the vendor
driver, and no copy of it exists on this host.

That also means the accepted mixed-pair boundary - our display driver, the
card's own mini-VDD - is reachable here, since Windows supplies both halves.

## The candidate loads, and refuses without damage

Staged by the `WININIT.INI` rename over `MGAPDX64.DRV`, which is the same
route the guarded package automates. Every boot from 17 to 25:

- the swap takes (the installed file is our build's size each time);
- the driver runs and its failure path reports `Stage=fail-hardware-aperture`;
- Windows falls back to `vga.drv` at 640x480x4 and the desktop comes up.

A legible refusal and no corruption is the family's whole design, and this is
the first time it has been observed on a 2064W. It is not a working driver.

## The stage name was not telling the truth

`fail-hardware-aperture` is stage code 3, which enable16.c assigns before the
aperture read. Two paths inside `V9XMAPAPERTURE` - the DPMI selector
allocation failing, and a live selector whose aperture has moved - returned
**without setting a stage code at all**, so they inherited the 3 and reported
as an aperture failure. The header comment says that helper owns codes 4
through 7; two of its exits owned nothing.

Fixed: the allocation failure sets 4, the moved-aperture refusal a new 11
(`fail-hardware-aperture-moved`), and the BAR read numbers its own four
refusals - 12 index, 13 the configuration read, 14 an I/O-flagged BAR, 15 out
of range or misaligned - restoring 3 on success so a later failure cannot be
blamed on a read that worked.

This matters beyond this card. Any investigation that has ever trusted
`fail-hardware-aperture` was reading a name that four different faults could
produce.

## And no diagnostic survives that window

Three attempts to write a key from inside the failing Enable produced nothing
in `V9XBOOT.INI`: the aperture value, then a pre-call marker, then both with
`WritePrivateProfileString(0,0,0,file)` flushing after every write. The coarse
stage, written later from ddi.c, lands every time. The serial trace is no help
either - the guest's COM1 reads `0xFF` from the driver's port check, through
both the File and the named-pipe device, so `v9x_serial_write` returns
without writing and the log stays empty.

So the stage code is the only channel out of that window, which is why the
refusals above are numbered rather than described. The flush is kept: it costs
nothing and the DirectDraw probe learned the same lesson the hard way.

## What the refusal is, and is not

Not localised. After the BAR read's own refusals were numbered, the reported
stage stayed 3 - which should mean the read was never entered, since it sets
12 on entry. That is not consistent with the hook being wired, and it is where
this investigation stops rather than guesses further.

Two things it is not:

- **Not the missing chip lookup.** The hook was rebuilt to fall back to BAR0
  when `v9x_hw16_active_device()` returns nothing, which is the behaviour it
  had before today's index existed. Still stage 3. That points away from the
  new per-chip BAR index without clearing it.
- **Not a wrong BAR value.** Windows' own resource list for the emulated card
  is a 16 KiB control aperture at `E7000000` and an 8 MiB framebuffer at
  `E6000000`, both 16 MiB aligned, so either BAR would pass the read's range
  and alignment guards. The BAR ordering is now confirmed a third way: lspci,
  the card's BIOS, and Windows.

The instrument that would settle it is a working trace out of the Enable
window. Two candidates: make the guest's COM1 answer the driver's port probe,
or add a stage code to every remaining exit in the enable sequence until the
reported number is unambiguous. The second is cheap and this commit is most
of it.

## Against the BringupKit runs

Worth stating for the next time the question is "read the card or boot it".
The Linux runs are read-only, restore what they touch and cannot lie about
what they did; they answered the mode-list question properly, and their
aperture and pitch findings stand. But an hour in a guest produced the inbox
driver binding, a working install route, the first observed refusal on this
chip, and two defects in our own reporting - none of which any read-only
probe could have reached, because all four are on the far side of a mode set.

## Gates

`run-checks.ps1` green after every change here. The guest is `boot 25`, still
falling back to VGA, and its stock `MGAPDX64.DRV` is preserved on the host and
at `C:\MGASTOCK.BIN` inside the guest.
