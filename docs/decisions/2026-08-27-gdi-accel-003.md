## What changed

`V9X_GDI_DEFAULT_OVERLAP` goes from 0 to 1. Overlapping same-surface
screen-to-screen copies now run on the engine on both S3 chips, in all eight
directions, which completes the set: desktop fills, window scrolls and window
moves are all hardware now, including the overlapping cases that a scroll
actually produces.

`C:\V9XHW.INI` reports `GdiAcceleration=gdi-fill-copy-overlap` on both S3
guests and `none` on the Mach64 VT2.

## The direction logic, settled on its own merits

Build 002's record left this open deliberately: the reference driver flips the X
and Y scan directions *independently* while this driver flips one or the other,
and 002 recorded that 003 should satisfy itself directly rather than inherit the
reasoning, because the reference doing something more general is a reason to
check rather than to assume.

First the reference's actual test, which needed the parameter layout confirmed
before it could be read at all. `bbparms.inc` declares `DestxOrg` before
`DestyOrg`, and PASCAL pushes left to right, so `DestxOrg` sits at the higher
address and `mov edi,dword ptr ss:[DestyOrg]` loads **`EDI = (DestX << 16) |
DestY`** - which is what the reference's own comments say. Its two tests are
therefore:

- `cmp di,si` - the low words, so `DestY` against `SrcY`. Flip Y when the copy
  moves down. Identical to this driver.
- `cmp edi,esi` - the full dwords, X-dominant. Flip X whenever `DestX > SrcX`,
  regardless of whether Y was already flipped.

This driver flips X only when `DestY == SrcY`. Enumerating every move class:

| Move | This driver | Correct? |
|---|---|---|
| down, any x | Y flip only | yes |
| up, any x | no flip | yes |
| same row, right | X flip | yes |
| same row, left | no flip | yes |

The two vertical cases are the ones worth arguing. Once rows are walked from the
far end, the source row for any destination row lies in the direction not yet
written - moving down and walking bottom-up, the source row is above and still
intact - **and it is a different row**, so within-row order cannot alias
anything. The X test is needed only when the copy stays on one row, which is
exactly when this driver applies it.

So both drivers are correct and the difference is not a disagreement about the
hardware: it is one driver testing a condition the other has already made
irrelevant. That reasoning now lives in `v9x_gdi_virge_copy` rather than in a
document, because it is what the next person editing those five lines needs.

## The gate was proven to fail before it was trusted

This is the part that makes 003's PASS mean something, and it is the standard
build 002 could not meet for its own cursor fix.

The direction logic was deliberately disabled - both flips made unreachable -
and the build deployed to the ViRGE guest. The `/accel` phase failed at its
first comparison:

```
Compared=FAIL
Error=pixel-mismatch
MismatchOperation=25
MismatchBytes=26808
DeclineOverlap=0
CopiesDelta=6
```

`DeclineOverlap=0` confirms overlap was enabled and the operations were reaching
the engine rather than being declined, so the mismatch is the engine's own work:
26808 differing bytes, which is the smear a wrong-corner overlapping copy
produces. The correct logic was then restored and the same run passes.

**Why this check works where build 002's cursor check did not**, because the
contrast is the useful part: a smear is written into the framebuffer and stays
there, so a readback sees it. A software cursor is lifted by `deBeginAccess`
before any readback can happen, so a readback can never see it. One class of
failure is checkable from a Win32 application and the other is not, and both are
now demonstrated rather than assumed.

## The assertion that inverts

Build 002 asserted that overlapping copies **were** being declined
(`overlap-declines-never-exercised`), because that was half of what 002 claimed.
Build 003 claims the opposite, so the assertion inverts:
`overlap-enabled-but-still-declined` fires when overlap is on and any
overlapping copy was declined for overlapping.

Without it a run could pass with the gate still refusing everything this build
turns on - the comparison would be checking the DIB Engine's own work and
proving nothing about the direction logic. Both forms are kept, each guarded by
the enabled mask, so the harness asserts whichever claim the build under test is
actually making.

### One invalid measurement, and what caused it

The first Trio64 attempt at this build **failed**, and the failure was mine
rather than the driver's. It is recorded because a 13 FPS line now sits in that
guest's benchmark log and would otherwise look like a regression.

`1024x768x32` reported `Result=FAIL` from the V9XGDI phase with every sampled
pixel reading `CLR_INVALID` and the mode reported as 640x480x16, while
`C:\V9XBOOT.INI` showed the driver had enabled correctly at 1024x768x32
(`Surface=pitch=4096 bpp=32 w=1024 h=768`). The explanation is in the
timestamps: the mode directory was created at 10:46:30, the matrix exited at
10:47:10, and an Ironfield run was launched on that guest at 10:47 - so Ironfield
took the display to its own 640x480x16 fullscreen mode while the matrix was
still testing the last one. The same contention produced that run's 13 FPS / 229
frames.

The mistake underneath it is worth naming: **the count of mode directories was
being read as a completion signal, and it is only a progress signal** - each
directory is created before that mode's tests run, so eleven directories means
the eleventh has started, not finished. Waiting for the task to exit is the only
sound check.

Both measurements were retaken with nothing else touching the guest: 11/11 modes
and 16 FPS / 280 frames, both reported above.

## What Phase 5 asked for, and what is left

PLAN.md's Phase 5 exit gate is "pixel-for-pixel comparison against a software
reference passes randomized rectangles, pitches, clipping regions, overlap
directions, and supported ROPs" plus "injected timeouts recover to an operable
desktop". Against that:

- **Randomized rectangles, overlap directions, supported ROPs** - covered by the
  `/accel` phase, on every mode of both chips.
- **Pitches** - covered incidentally rather than deliberately: the matrix runs
  four depths across four resolutions, which is eleven distinct pitches, but the
  harness does not vary pitch within a mode.
- **Clipping regions** - **not covered.** The harness draws into an unclipped
  window. GDI clips before the driver sees a blit, so the driver never receives
  a clipped rectangle to mishandle, but that is an argument rather than a
  measurement and should be recorded as such.
- **Injected timeouts recover to an operable desktop** - covered, on every
  accelerated mode, with the desktop verified still rendering afterwards.

Still off and unstarted: **CPU-to-screen upload** (build 004) and **extra ROPs**
(005). Still uncovered: the cursor-over-source case, for the structural reason in
002's record, and the `vbe` family's enable-gate run, whose guest is
QEMU-hosted.
