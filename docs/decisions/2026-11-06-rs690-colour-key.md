# RS690: source colour key by the texture unit's chroma key, RGB565 only

Date: 2026-11-06. Machine: M-GB8KRE (RS690 1002:791F, Win98 SE).
Build: branch `ati-rs690`, 66144990-dirty. Captures:
`docs/probe/rs690-colour-key-2026-11-06/`. The `$` capture is saved as
`R3dollar-*`.

## Decision

A textured draw with COLORKEYENABLE, whose texture surface has a source
colour key (DDRAWISURF_HASCKEYSRCBLT), is drawn with the texture unit's
chroma key:

- `TX_FILTER1` bits 1:0 set to FORCE (1);
- `TX_CHROMA_KEY_0` set to the key's low value as stored.

This is done for RGB565 textures only. Keyed draws on the formats with
alpha are still refused. COLORKEYENABLE on a texture with no key draws
unkeyed. The HAL publishes D3DPTEXTURECAPS_TRANSPARENCY.

No shader work was needed. Before this measurement the alternative was a
two-node shader with a TEXKILL instruction, which Evergreen and VI
effectively do.

## What the probe measured

The `Chroma*` tests in V9XRS3D, at 640x480x16 and 1024x768x32. The
gradient is drawn 1:1, nearest, REPLACE, and the key is texel (5, 3),
the only texel with that value.

| Test | Key | 16 bpp | 32 bpp |
|---|---|---|---|
| ChromaForceRaw | the texel as stored (0065h / 00CB00CAh) | 1 pixel killed (prefill left) | 1 killed |
| ChromaForce | 565 widened to 8888 with bit replication, alpha FF | no match | (the raw texel) 1 killed |
| ChromaForceZeroFill | 565 widened with zeros, alpha FF | no match | 1 killed |
| ChromaForceRawFF | as stored, top byte FF | no match | no match |
| ChromaBlend | BLEND (2) mode | — | pixel drawn as 00000000h |
| ChromaNearest2x | raw, magnified 2x, nearest | 4 killed | 4 killed |
| ChromaLinear2x | raw, magnified 2x, bilinear | 16 killed | 16 killed |

What this shows:

1. **FORCE kills the fragment.** The keyed pixel keeps what was under
   it, and no other pixel changes. BLEND does not kill: it draws the
   texel as transparent black, which matches the R200 header's
   "CHROMA_KEY_ZERO".
2. **The key is compared bit for bit against the texel as stored.** For
   a 16-bit texture that is the 16-bit value, and the upper half of the
   key must be zero. For a 32-bit texture it is the whole dword, alpha
   included. A key whose top byte differs from the texel's alpha never
   matches.
3. **Bilinear kills every pixel whose footprint touches the keyed
   texel**: 16 pixels at 2x against nearest's 4. Keyed edges come out
   slightly eroded, but nothing drawn has the key colour blended into
   it.

A DirectDraw source key comes in the surface's pixel format, so for an
RGB565 texture it is the stored value and compares exactly. For ARGB8888,
ARGB1555 and ARGB4444, Direct3D compares colour only, but this unit
compares the alpha bits too. A texel whose alpha differs from the key's
would wrongly survive, so those formats stay refused.

## Through the HAL

Boot 74: V9XD32 passed two runs at 32 bpp and one at `/bpp16`, each with
Failures 0 and T15 clean. V9XD32 has no colour-key test, so **no keyed
draw has gone through the HAL yet**. The mapping is host-tested.

## Not checked

- An application with keyed textures.
- A key range (low ≠ high). The low value is taken, as the VI engine
  does.
- The alpha formats. The way to key them is a shader TEXKILL, not
  pursued.
