# GDI acceleration, build 000: a provably free decline path

Date: 2026-08-26
Status: accepted

Implements [`docs/plans/gdi-accel-000-and-harness.md`](../plans/gdi-accel-000-and-harness.md),
the first stage of [`docs/plans/gdi-acceleration.md`](../plans/gdi-acceleration.md).

## What changed

Ordinal 1 was an unconditional `jmp DIB_BitBlt` thunk in
`src/display16/dib_thunks.asm`. It is now a C dispatcher,
`src/display16/gdi_accel.c`, carrying the acceptance gates, the ViRGE and
Trio64 fill and copy primitives, the bounded waits, the CR66 engine reset, the
poison latch, the counters and the SYSTEM.INI read. Every primitive is compiled
and none is reachable: `GdiAccelFill`, `GdiAccelCopy` and `GdiAccelOverlap` all
default to 0, so on a default build the dispatcher declines every blit.

Beside it: an `/accel` phase in `V9XGDI.EXE` that can fail, and
`scripts/run-family-enable-gate.ps1`, an opt-in per-family enable smoke gate.

## The premise that reframed the stage

`s3` is the only family with a 2D engine. `ati`, `vbe` and `matrox-m2` declare
`EngineType = NONE` on every chip, and all four link the same `ddi.c` and
`dd16.c`. Because the `BitBlt` export lives in the shared 16-bit layer, the
moment ordinal 1 became a C function **every family got the dispatcher** - and
three of them will take its decline branch on every single blit, for ever.

So the decline path is not scaffolding on the way to the interesting part. For
three quarters of the fleet it is the shipping code, permanently, and its exit
gate has to be run on a family with no engine and not only on the ViRGE. Its
cost on such a family is one WORD test against a mask the configuration never
sets.

## Corrections this stage had to make to its own plan

Every one of these is a case of the plan describing something that turned out
not to be true of the tree or the toolchain. They are recorded in the parent
plan's "Gate wording this stage found to be wrong" section as well; the two
that changed *code* rather than words are worth repeating here.

**32-bit MMIO cannot be reached from C in this driver.** Design decision 1 said
the 16-bit side would reach the ViRGE registers as `volatile DWORD FAR *`
through one selector. Measured: this driver is built without a `-3`, so wcc
emits 8086 code and

```
    *reg = value;          /*  volatile DWORD FAR *reg  */
```

compiles to `mov word ptr es:[bx],ax` followed by `mov word ptr es:2[bx],cx`.
On `CMD_SET` that is wrong rather than slow - the write is what starts the blit,
so the engine would be triggered on the low half with a stale high half - and a
split `SUBSYS_STAT` read samples the FIFO count and the idle bit at different
instants. Every 32-bit engine access therefore goes through `V9XENGINEREAD` /
`V9XENGINEWRITE` in `runtime.asm`, where `.386p` gives one bus cycle, and
`audit-family-binary.ps1` asserts the single-instruction forms
(`mov eax,dword ptr es:[bx]`, `mov dword ptr es:[bx],eax`) are present.

**The decline branch needs a typed forward.** This driver compiles PASCAL
exports with their names uppercased - the reason the build script says
`export Control.3=CONTROL` - so a C `extern WORD FAR PASCAL DIB_BitBlt(...)`
asks the linker for `DIB_BITBLT` while `DIBENG.LIB` supplies `DIB_BitBlt`. The
decline branch calls `V9XDIBBITBLTCALL`, a stack-transparent
`jmp DIB_BitBlt` in `runtime.asm`, exactly as every other DIBENG routine C code
in this driver already does.

## Sources, and why they are first-party

The eleven-argument signature and the gate order are transcribed from
`C:\98DDK\src\display\mini\xga\BITBLT.ASM:57-77`, which declares the entry point
in first-party code with its arguments named in push order. A far-Pascal frame
that disagrees with the caller by one word corrupts the stack on the first blit
GDI issues, which on this path is during boot, so this was read rather than
reconstructed. `98DDK\src\display\mini\s3v\S3BLT.ASM` - the same driver family
as ours - gates identically at `:128-133` and confirms the return value
(`mov ax,1` at `B_Done`).

The realized-brush layout is `C:\98DDK\inc\win98\inc16\DIBENG.INC:183-253`, and
the two `deBeginAccess` flags are `:126-132` of the same file, which carries
both an assembly `equ` and a C `#define` of each. There is no `dibeng.h` in this
DDK; the parent plan named a file that does not exist.

`PALETTE_XLAT` came from the reference and not from the plan's gate list. Without
it the first accelerated 8-bpp fill under a translated palette would produce
right-shaped, wrong-coloured pixels - the class of bug the harness exists to
catch, avoidable for free by copying the reference driver's gate. The
screen-to-screen exemption is copied too, from `BB_JumpToDibEngineX`
(`BITBLT.ASM:44-50`): a copy that never leaves VRAM moves pixel values
untranslated, so it still accelerates, while fills arrive with `lpSrcDev` not
equal to the screen PDEVICE and decline. That distinction is load-bearing from
build 002 onward - an 8-bpp desktop with an active palette translate is
precisely the desktop whose window scrolls and moves 002/003 exist to
accelerate, and a blanket decline would silently turn the feature off exactly
there. The s3v sample is stricter and declines with no exemption at all; xga's
rule is the one taken, and it is sound for the same reason s3v's is safe -
neither ever translates.

## Where the state lives, and why

`v9x_gdi_engine_dirty` and `v9x_gdi_poisoned` are DGROUP words, not PDEVICE
fields and not `V9X_DD_SHARED` fields. Two concrete reasons: `V9X_DD_SHARED`
does not exist before the HAL DLL loads, and `ReEnable` rebuilds the PDEVICE in
place on a live mode switch, so anything latched inside it would be silently
cleared by a resolution change. The plan requires the poison latch to survive
mode switches; DGROUP is what makes that true.

Both `deBeginAccess` entry points - `V9XDIBBEGINACCESS` and
`V9XDIBBEGINACCESSRECT` - carry the dirty check. Not because a caller is known
to race pending engine work, but because reasoning per caller about who cannot
is a worse trade than a shared stub: it is the same four instructions either
way. (The plan cited `ddi.c:957` as the rect entry's caller. That line is a
comment, not a call - the live-switch path deliberately does not wrap
`CreateDIBPDevice` in an exclusion. The entry is exported and public, so it gets
the check regardless.)

The drain slow path can run at interrupt time on a software-cursor draw, so it
touches MMIO, ports and DGROUP only: no `WritePrivateProfileString`, no serial
write. A poison report is deferred to whichever of the next `BitBlt` or
`Disable` arrives first.

## The register header move, and an unreproducible claim replaced

The parent plan's Corrections section claimed `v9xhal.dll` was byte-identical
across the first half of the register move, with a pinned build id and a hash.
That is not reproducible today and should not be asked for again: the HAL is a
Win32 PE and its COFF header carries the link timestamp, so two builds of
identical source from the same pinned `-BuildId` hash differently. Measured
2026-08-26: three consecutive builds of unchanged source produced three
different SHA-256 values.

What was verified for the second half of the move - the 2D status, command,
ROP, source-base, stride-mask and coordinate-limit constants leaving
`ddhal_internal.h` for `include/velocity9x/s3_engine_regs.h` - is that all
seven HAL translation units **disassemble identically** across it: `wdis -a` on
`blt_cpu`, `d3d_virge`, `ddhal`, `ddhal_core`, `eng_s3_trio`, `eng_s3_virge` and
`vga_scanout`, byte-for-byte equal before and after. That is the property the
hash claim was reaching for, and unlike an image hash it cannot be satisfied by
accident or defeated by a clock.

`V9X_VIRGE_FIFO_SPIN_LIMIT` and `V9X_VIRGE_IDLE_SPIN_LIMIT` deliberately stayed
behind. They are the flat HAL's own calibration, measured against a flat-model
spin; the 16-bit loop is a far call plus a DWORD countdown and does not cost the
same. Sharing one number between two loops with different costs would make one
of them wrong without saying so.

## The 16-bit spin limits are uncalibrated, and say so

`V9X_GDI_FIFO_SPIN_LIMIT` is 0x4000 and `V9X_GDI_IDLE_SPIN_LIMIT` is 0x10000.
They are derived, not measured: one 16-bit iteration is a far call into
`V9xEngineRead` plus a DWORD countdown, call it 60 to 100 clocks against the
flat HAL's ten or so, and scaling 0x00400000 by that factor lands near 0x10000 -
roughly 100 ms on a 66 MHz part. Far longer than any rectangle this driver
accelerates takes to complete, short enough that the one operation which ever
waits this long is not mistaken for a hang, and paid at most once per session
because the expiry poisons the latch.

Open item 3 of the parent plan is the measurement that should replace them. The
arithmetic above is recorded in the source so the next person changing them is
changing a derivation rather than a guess.

## BLACKNESS and WHITENESS: a normalisation with an open question

`BLACKNESS` (ROP 0x00) and `WHITENESS` (0xFF) are normalised in the dispatcher
into a solid fill with an explicit colour, rather than passed to the engine as
ROPs. That way one definition of the fill colour serves both chips and they
cannot disagree about what whiteness means.

That definition is the all-ones bit pattern for the depth, which is what both
DDK reference blitters produce - `DoBltNoDSP` (`S3BLT.ASM:243`) puts the ROP256
code straight into `CMD_SET` bits 24:17 and lets the engine generate the pixel
values. GDI documents the two operations in terms of physical palette indices 0
and 1 instead. On a palettized desktop whose realized palette does not put white
at 0xFF those are different answers.

Nothing ships on it: no primitive is enabled at 000. The `/accel` comparison
against a reference DC is what settles it, which is precisely why the harness
had to land before build 001 turns fill on.

## The harness, and the one line that matters

`V9XGDI.EXE /accel` writes `C:\V9XACCE.INI` and leaves `C:\V9XGDI.INI`
untouched, so `Result=PASS` there keeps exactly the meaning the mode matrix
already relies on.

It drives 500 seeded operations against the screen and against a DIBSection
reference DC - solid `PatBlt`s including deliberately below-threshold ones,
screen-to-screen `SRCCOPY` covering all eight overlap directions, and
`PATINVERT` decline noise - and compares the two with `GetDIBits` every 25
operations. Both sides are read back at 24 bpp through the same request, so one
comparison covers 8 and 16 bpp. Colours come from a fixed table of 16 static
system-palette entries, which is not decoration: on an 8-bpp desktop an
arbitrary RGB is mapped to the nearest palette entry, and comparing a screen
readback against a reference DC only means anything if both map the same way.

Then it reads the driver's counters through `V9X_GDIGETSTATS` and **fails if a
primitive that is advertised and enabled never fired.** That is the
anti-vacuous-pass check and the single most important line in the harness. A
comparison harness that silently exercised the decline path on every operation
would pass perfectly and prove nothing - which is exactly how the `ati` package
shipped unable to enable for a release
(`docs/issues/2026-08-26-ati-package-cannot-enable.md`): every check it had to
pass was a check it could pass without working.

On a default build 000 nothing is enabled, so that check cannot fire. The one
that can, and does, is `Calls`: if ordinal 1 were not actually ours, 500 blits
would have reached the dispatcher zero times and the pixel comparison would
still have been perfect.

Fault injection mirrors `V9X_DDFAULTINJECT`
(`docs/decisions/2026-08-16-engine-fault-injection.md`): an armed count is
consumed by the production bounded waits falling into their existing timeout
tail, so the injector drives the shipping recovery path rather than a parallel
test one. That choice has a consequence this build owns: on a default 000 build
every primitive is off, no GDI bounded wait ever runs, and an armed injection is
never consumed - `Poisoned` stays 0, honestly. The harness therefore gates its
injection step on the same condition as the zero-counter check, and at 000 that
step runs only in a deliberate `GdiAccelFill=1` session. From 001 onward it runs
unconditionally.

## The enable gate

`run-checks` builds every family package and passes, because a package that
builds is not a package that enables. `scripts/run-family-enable-gate.ps1`
starts each family's emulated guest, deploys the freshly built package over the
already associated driver, reboots, and asserts `Stage=enable-ok`. Nothing else.
Not in the default `run-checks` path - it needs VMs and minutes - but one
command, which is what makes it runnable before a merge that touches the shared
16-bit layer, where a mistake is a four-family mistake.

Coverage honesty: it reaches three families, not four, and it prints what it
skips **by name**. `matrox-m2` and the `ati` family's Rage Mobility target
declare `Emulator = 'none'`.

Two lifecycle mechanics are in the script rather than left to be rediscovered:
the forwarded host port opens **before** the guest agent listens, so it polls
`v9xctl ping` rather than trusting a TCP connect; and a guest that has produced
no agent by half the timeout budget is force-restarted once, which is safe
because a committed WININIT driver install survives a force-kill.

### A bug worth recording, because it cost three guests

The first version of that script wrote its progress messages with
`Write-Output` from inside `Start-V9xGuest` and `Wait-V9xAgent`, both of which
return a value the caller tests. In PowerShell a `Write-Output` inside a
function joins that function's output stream, so `$started = Start-V9xGuest ...`
captured the message *and* the boolean as a two-element array - which is truthy.
The cleanup branch `if (-not $KeepRunning -and $started)` therefore fired for
every target, and the run force-killed three guests it had not started. The same
shape in `Wait-V9xAgent` was worse and silent: `-not @('message', $true)` is
`$false`, so a wedged guest would have passed the wait.

Both functions now return a value and nothing else, and every progress message
is printed by the caller. `Start-V9xGuest` returns a string - `answering`,
`starting`, `started` - so "this run owns the guest and may shut it down" is a
distinct state from "something was already open on the profile", which is also
now a refusal to launch a second emulator against one VHD.

### The harness had a bug, and 000 is where it was found

The first `/accel` run failed. It failed **identically on the ViRGE and on the
engine-less ATI guest** - same operation (50), same byte (9219) - on a build
where every operation declined and the DIB Engine therefore drew both sides. A
driver-independent, deterministic disagreement is not a driver defect.

The reference bitmap was a 24-bpp DIBSection while the screen was 8 bpp, and the
decline-noise operation is `PATINVERT`, which XORs the destination: on an 8-bpp
desktop that XORs palette *indices*, and on a 24-bpp reference it XORs RGB
*bytes*. Two different answers, neither wrong, compared against each other. The
reference is now a compatible bitmap at the screen's own format and only the
readback is 24 bpp.

This is exactly what
`docs/plans/gdi-accel-000-and-harness.md` predicted in requiring the harness to
land with or before 001: "writing it against 000, where the correct answer is
'the reference DC and the screen agree because the DIB Engine did all of it', is
how the harness itself gets debugged while the stakes are zero." Had it landed
after 001, this would have presented as a fill defect in a primitive already
signed off.

### The anti-vacuous-pass check, proven to fail

Not by a stubbed build in the end - a real configuration was enough, twice.

**Once as a false positive worth keeping.** Run with `GdiAccelFill=1` on a
1024x768x**32** desktop, the check fired: `Enabled=1`, `Fills=0`,
`Error=fill-enabled-but-never-fired`. The driver was behaving perfectly -
`DeclineDepth=669` says the depth gate refused every fill, which is what the S3
primitives are supposed to do above 16 bpp. Left as it was, every 32-bpp mode in
the matrix would have failed from build 001 onward. The check is now conditioned
on the screen depth being 8 or 16, reports `ZeroCounterChecked` either way so it
can never skip silently, and still runs in eight of the S3 family's eleven
modes.

**Once as a true positive.** At 640x480x8 with fill enabled the fill fired -
`Fills=41`, `FillsDelta=14` - and the comparison failed on colour.

### The deliberate GdiAccelFill=1 run

ViRGE guest, `[Velocity9x] GdiAccelFill=1` appended to `C:\WINDOWS\SYSTEM.INI`,
rebooted. `C:\V9XHW.INI` reported `GdiAcceleration=gdi-fill`, so the INI read and
the capability clamp both work. At 640x480x8 the primitive fired.

**And it paints the wrong colour.** The driver's own counters name the cause:
`LastRop256=240` (PATCOPY, correctly classified), `LastBrushFlags=129`
(`COLORSOLID|DIBENGBRUSH`), `LastBpp=8`, `LastColor=16711935` - which is
`0x00FF00FF`, `COLORREF` magenta. A logical RGB triple where the engine wants a
physical pixel value; the ViRGE takes the low byte `0xFF`, and index 0xFF is
white. Filed as
[2026-08-26-gdi-fill-brush-colour-not-physical.md](../issues/2026-08-26-gdi-fill-brush-colour-not-physical.md),
and it blocks build 001 rather than this one - nothing ships on it, because
every primitive is off by default.

Build 000's requirement for this run was "purely to prove the primitive can fire
at all before build 001 claims it works". It fired, and it is wrong, and that is
the run doing its job.

### Fault injection and the poison latch

The `/accel` phase's own injection step sits behind a passing comparison, which
the fill defect made unreachable. Since fault injection and the poison latch are
properties of the bounded-wait and recovery paths and not of any primitive's
pixel output, the harness gained `/inject:N` and `/stats` to arm and read
without drawing - the two claims are separable and should not have been coupled.

Armed one injection, then ran a workload that performs fills:

| | before | after |
|---|---|---|
| `FaultInjectRemaining` | 1 | 0 |
| `FifoTimeouts` | 0 | **1** |
| `Resets` | 0 | **1** |
| `Poisoned` | 0 | **1** |
| `Enabled` | 1 | **0** |
| `Fills` | 49 | 49 |

Every part of the designed behaviour: the injection was consumed by the
production bounded wait, the CR66 engine reset ran, the latch set, the latch
cleared the primitive mask so every later operation declines at the first gate,
and `Fills` did **not** advance - the fill the engine did not perform was
performed by the DIB Engine instead, which is what keeps the pixels correct
through a timeout. The desktop kept rendering throughout and the guest stayed
responsive.

**The latch survives a live mode switch.** `V9XMSW /set:800x600x8` from
640x480x8 - a real `ReEnable` that rebuilds the PDEVICE in place - then the
counters again: `Poisoned=1`, `Enabled=0`, and `C:\V9XHW.INI` now reads
`GdiAcceleration=gdi-poisoned`, so the deferred report flushed as designed. This
is the thing DGROUP was chosen for: had the latch lived in the PDEVICE, this
switch would have silently cleared it and re-enabled a primitive a timeout had
turned off.

The guest was then restored to a default `SYSTEM.INI` and rebooted:
`GdiAcceleration=none`, `Stage=enable-ok`, latch clear.
