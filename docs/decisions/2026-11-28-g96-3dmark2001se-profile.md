# GeForce 9500 GT (G96): where 3DMark 2001 SE's time goes, and why a faster core did not help

Date: 2026-11-28

On M-Z2T02D (GitHub issue 30), boot 21, the nvidia set of f3c56b29's
tree (cae9af17-dirty, the clock raise in: core 550, shader 1400 MHz).
The question: the single-texture fill rate barely moved with a 37%
faster core (604 MTexels/s on boot 13 at 400 MHz, 596 on boot 18 at 550;
[clock record](2026-11-28-g96-clocks-measured.md)), so the run is not
limited by the GPU's clock. Scores are recorded, not compared or chased.
Evidence:
[g96-profile-3dmark2001se-m-z2t02d-2026-11-28/](../probe/g96-profile-3dmark2001se-m-z2t02d-2026-11-28/).

## The run

`V9XPROF.EXE "3DMark2001SE.exe"`, 3DMark's defaults, Benchmark clicked
by agent. It ran to a score of 1106 (`score.png`). 476,149 samples at
about 1 ms, none lost. V9XHAL.DLL loaded at its preferred base
B0400000h, so sample addresses are map addresses; the map and objects
were saved from the build whose HAL is installed (SHA-256 matched,
`2259051E...5236`). `report.txt` is `report-profile.ps1`'s output;
`hot-buckets.txt` is the 16-byte address histogram.

## What it says

- **About 20% is the CPU reading engine registers**, nearly all of it
  waiting. `v9x_nv50_3d_begin` calls `v9x_nv50_drain(1)` before every
  batch, because there is one 3D pushbuffer (768 KiB at reserve + 1 MiB)
  reused from its start: the CPU waits for the GPU to finish batch N
  before it writes batch N+1, and the GPU waits while the CPU writes. A
  faster core shortens only the GPU's half; the CPU's half and the
  polling stay.
- **About 19% is one store into the pushbuffer.** A store that heavy
  points at uncached memory. `V9XBOOT.INI` records `PatWrite=ok
  pages=00004000` (64 MiB) for the G96's 128 MiB BAR1 mapping, and the
  reserve that holds the pushbuffer sits near 126 MiB, so it is probably
  outside the write-combined range. Not established: which range the PAT
  cover took was not read back.
- **9% is waiting for vertical blank** at flips, which is the VSync
  setting doing its job (`VSync=application`, 3DMark asks for sync).
- KERNEL32's 22% was not resolved (its hot spots are unexported on
  Win98); it may include 3DMark's own waits.

## Not done

Nothing was changed. The two driver-side costs suggest work of their own,
each to be measured before and after:

1. Write-combine the reserve's pushbuffer: read back the PAT range the
   cover took on the G96, and cover the reserve if it is outside.
2. More than one 3D pushbuffer, so batch N+1 is written while batch N
   runs, instead of a drain per batch.

Both apply to the GeForce 210 too (the same engine and reserve), which
was not profiled.
