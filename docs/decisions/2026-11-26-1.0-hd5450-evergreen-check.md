## The Caicos hang fix on a second Evergreen card

The 0.56.1 per-group flush hung the HD 7470 in its first Direct3D
program; the fix (`a165d31f`, in the 0.61.0 tree) closes the group
after every batch on the non-Trinity parts. It had run on the HD 7470
only; the plan owed "one other Evergreen card". V9XD32 at both depths,
3DMark 2000 to its score and Quake 3 ran on the HD 5450 without a hang
or an engine timeout. That check is done.

## B6: the cursor square at 320x240

V9XCURSQ runs four cases. This card's VBE list has 320x240x16, which the
Oland's and the R3E's do not, so the 320x240 cases ran here for the
first time on the B6 fix:

| Case | Verdict | What the buffer holds at the cursor |
|---|---|---|
| 320x240 flip, GDI's buffer | **SQUARE** | box 168,120-204,160, 1,376 pixels, 95 %: the arrow on solid black, as on the Oland before the fix |
| 320x240 flip, other buffer | clean | |
| 320x240 blit | clean | |
| 640x480 flip, GDI's buffer | clean | |
| 640x480 flip, other buffer | CURSOR | the arrow over the green with the software cursor's black blocks, 66 % |
| 640x480 blit | CURSOR | the arrow over the green, 63 % |

(`cursq/V9XCURSQ.INI`, `cursq/boxes-320flip-640flip-640blit.jpg`.) At
640x480 the fix behaves as on the Oland and R3E: no square. At 320x240
the box is the stale desktop's black with the arrow on it, which is
what `shadow_hold` was meant to stop. The reporter's Bug! ran at
320x240 (mode `0193h`) and 640x480, so B6's fix does not yet cover
the reporter's case.

Why 320x240 escapes is not known. The fix in `shadow16.c` reads the
cursor's rectangle back only while `*v9x_shadow_hold` is non-zero; the
320 case is also the probe's first, so "first exclusive session after
the desktop" and "320x240" are not separated by this run. The probe
(built `61c64630-dirty`) did not find the shadow's event log
(`ShadowLogBefore` and `After` read `Taken=no`), so it cannot show
whether the read-backs happened.
