# The HD 4400 (8086:041E) binds as an alias of the HD 4600 on a DOS survey: the same BAR layout, GGC encoding and VBE framebuffer, four times the stolen memory

Date: 2026-10-23
Machine: none. No 041E has run this driver; nothing below was measured
under Windows.
Evidence: one V9XSURV report (build `d746481`, DOS 8.00,
`WindowsPresent=no`, `Access=query-only`, Tier 2 accepted at the prompt),
sent to Michael as `HD4400.INI` and committed unmodified:
[`hd4400-hsw-gt2-vgasurv-2026-10-23-d746481.ini`](../probe/references/hd4400-hsw-gt2-vgasurv-2026-10-23-d746481.ini).
The report does not name the machine or its owner.

## Decision

`8086:041E` is an alias of `hd4600-hsw` in the intel-gma manifest: its own
INF model line and `V9X_HW16_DEVICE` (`v9x_hsw_hd4400_device`), everything
else the 0412's - the Haswell open (chip 0, Haswell forcewake), engine type
GEN75, the D3D and FLIP caps, the heap layout code. It is an alias rather
than a chip because it has not run; the INF header says "not validated".

## What the survey establishes

Set beside the i5-4570 (`8086:0412` rev 06), whose values are in
[2026-10-20-haswell-stolen-layout.md](2026-10-20-haswell-stolen-layout.md):

| | 041E (survey) | 0412 (i5-4570) |
|---|---|---|
| Function 0 | `8086:041E` rev 06, class 030000, SUBSYS `041E8086` | `8086:0412` rev 06, SUBSYS `05A41028` |
| BAR0 (GTTMMADR) | `F7800004`, 64-bit, high dword 0 | 64-bit memory |
| BAR2 (GMADR) | `E800000C`, 64-bit prefetchable, high dword 0 | 64-bit prefetchable |
| BAR4 | I/O `F000` | I/O |
| GGC (50h) | `0221`: GMS 4 = 128 MiB, GGMS 2 = 2 MiB GTT | `0209`: GMS 1 = 32 MiB, GGMS 2 |
| BDSM (5Ch) | `D7200001` | `DD200001` |
| VBE | 3.0, 2047 x 64 KiB, every LFB at `E8000000` = BAR2 | 3.0, LFB in BAR2 |
| PCH | Lynx Point (8C xx) | Lynx Point |

`V9xPciReadHswConfig` accepts these BARs: both are type 100b (64-bit
memory) with zero high dwords. The device's `fb_bar` of 2 matches the VBE
PhysBase. GMS 4 decodes to 128 MiB in `v9x_intel_hsw_decode_ggc`, and
`v9x_intel_hsw_plan_heap` with 128 MiB stolen against the 64 MiB map is
already a host test case (`test_intel_hsw.c`): the map is the ceiling, so
the reserve sits under 64 MiB as it does on a 64 MiB board.

Not in the survey, so not known: `1082C0h` (the stolen-reserved register
the heap plan reads through the mini-VDD), the GT's forcewake behaviour,
and whether the BIOS leaves the render ring idle. On the 4570 each of
those was measured; here they are inferred from the device being the same
GT2 silicon family.

## Other findings

- The option ROM's PCIR names `8086:0406`, not `041E`. Intel ships one
  image ("HSW Mobile/Desktop", build 2173, 05/07/2013) across ids. The
  driver identifies the chip by configuration space only, which this
  confirms is the only safe source.
- VBE lists 15 modes up to 1280x1024, no 24 bpp. The attached monitor's
  EDID is an LE1711, 1280x1024 native (108 MHz preferred timing), which
  is why nothing larger is listed. `017D`-`017F` repeat
  `0107`/`011A`/`011B`.
- 800x600x8 (`0103`) has an 832-byte pitch, as on the 915GM's BIOS.
- The sequencer decodes three index bits: `Seq.08` to `Seq.1F` in the
  survey are aliases of `Seq.00` to `Seq.07`.

## What would promote it

A boot of the intel-gma package on this machine with `V9XHW.INI`
(`HeapLayout=chip`, `EngineStatusEnable=open`), then V9XDDF, as for the
HD 4000 in [2026-10-21-ivybridge-bcs-blits.md](2026-10-21-ivybridge-bcs-blits.md).
Until then it is "it should come up", not supported.
