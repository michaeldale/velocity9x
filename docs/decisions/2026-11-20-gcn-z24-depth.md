# GCN: Z24 depth, because UT2004 stops at its device setup with only Z16

Date: 2026-11-20. Machine: W9QI0DAD, Radeon Oland XT `1002:6610`, Windows
98 SE, DirectX 9.0c, desktop 1024x768x32, boot 122 on the ati set already
installed (its build not read). Program: Unreal Tournament 2004 demo,
build 3334, in `C:\UT2004Demo`, the same files as the HD 4600's install
(every exe and dll the same size), its `UT2004.ini` as shipped: the
Direct3D 8 renderer, 800x600 full screen, `Use16bit=False`.

## What the program did

Michael reported that the UT2004 demo and 3DMark03 did not start on this
machine and suspected bad downloads. 3DMark03 is unrelated to the driver
(see the end). UT2004:

- Run as installed, it shows the Visual C++ runtime's "Runtime Error! ...
  requested the Runtime to terminate it in an unusual way" and exits.
  `UT2004.log` stops at `Log: Opened viewport` / `Log: Enter Se` (the log
  is buffered; the 4 KiB written is all there is) and the minidump is 0
  bytes. The driver's `V9XTRAIL.TXT` has no entry from the run: no mode
  was set.
- On the Pixomatic software renderer (`RenderDevice=PixoDrv...` in a copy
  of the ini, `UT2004.exe ini=UT2004P.ini`) it reaches `Enter SetRes:
  800x600 Fullscreen 1` and its menu. The install is good.
- Through the d3d8 logging proxy (version 4, `D3D8.DLL` + `D3DR.DLL` in
  `System\`, log `C:\V9XDIAG\D3D8LG4.TXT`), its last calls before the
  abort are depth formats for the X8R8G8B8 desktop, all refused:

  ```
  CheckDeviceFormat type 1 adfmt 22 usage 2 rtype 1 fmt 77 -> 8876086a  (D24X8)
  CheckDeviceFormat type 1 adfmt 22 usage 2 rtype 1 fmt 71 -> 8876086a  (D24X4S4)
  CheckDeviceFormat type 1 adfmt 22 usage 2 rtype 1 fmt 75 -> 8876086a  (D24S8)
  ```

  It does not ask for D16 at 32 bpp; it aborts.
- With `Use16bit=True` in the copied ini it logs `Using back-buffer format
  23(16-bit)`, `Using depth-buffer format 80(16-bit)`, `Creating device`
  and runs to its menu on the hardware HAL. Closing it then raised UT's
  own Critical Error: `CheckDepthStencilMatch failed` from
  `DetermineFormats <- UD3DRenderDevice::SetRes <- EndFullscreen`, the
  same question asked for the 32 bpp desktop on the way out.

The GCN HAL published `dwDeviceZBufferBitDepth = DDBD_16` and
`depth32_bits = 0` ("Z16 only for now", `d3d_vi.c`), so Direct3D 8 had
D16 and nothing to match an X8R8G8B8 target. The HD 4600, where UT2004
runs, publishes D24X8 (`depth32_bits = 24`).

## What changed

Z_24 in 32-bit cells on every GCN chip of the family (Oland in GFX6 mode,
Carrizo and Mullins in GFX8 mode), depth in the low 24 bits as the core's
other `depth32_bits = 24` engines hold it:

- `vi_3d.c`: `DB_Z_INFO` FORMAT `Z_24` (2) when the new `depth_32` field
  is set, the rest of the word the Z16 one (tile index 4 on GFX6, 5 with
  tile split on GFX8, or the linear mode).
- `vi_3d.c`: `v9x_vi_z32_detile_band` / `retile_band`, the Z16 sample
  order on 32-bit cells. AMD's addrlib uses one depth sample order (x0 y0
  x1 y1 x2 y2) at every element size, so the measured Z16 order carries
  over; a tile is 256 bytes.
- `d3d_vi_map.c`: 2- or 4-byte depth accepted, pitch in whole 8-pixel
  tiles of the cell, `depth_pitch` in pixels.
- `d3d_vi.c`: Z24 surfaces placed (rows of whole 64 bytes, which are whole
  tiles at 4 bytes too), converted at Lock and Unlock, and filled on the
  CP with the colour target named 8888; `depth32_bits = 24` and
  `DDBD_32` published.
- `dd16.c`: the GCN engine type added to the engines whose DirectDraw
  caps name a 32-bit Z.

Host tests: the Z24 register words on GFX8 and GFX6, the 32-bit band
conversion, and the map's 4-byte rules, each watched fail first.

## Measured

Gates: `run-checks.ps1` green. Its first run failed on size, not
behaviour: a fourth DWORD compare of the engine type in `dd16.c` put the
intel-gma driver's `_TEXT` at 57,353 bytes, over its 57,344 budget; the
deep-Z engines are now one bit mask tested with a shift.

On the Oland, the whole ati set (package `7ad8b7e5-dirty`, this change on
main `7ad8b7e5`) by `run-release-checks.ps1 -Machine oland`, boot 122 to
123, 8 of 8 files hash-checked. Every probe verdict is the 0.58.0 run's:
V9XFBCMP, V9XGLIDP, V9XGLP, V9XWPRS PASS, V9XR3DP COMPLETE, V9XD32 at 32
and 16 bpp FAIL on T19 alone, as before.

`V9XD32 /z24` (32 bpp target, 32-bit Z): the same verdicts as the default
run, the one failure T19. The Z24 path itself:

- the clear: all 307,200 cells read `00FFFFFF` through Lock
  (`ZClearFar24=0x0004B000`), so the CP fill, the Z_24 format and the
  detile at Lock agree on every cell;
- T3, T5 and T8 pass; T5 (red at 32-bit Z, green at 16) is the 24-bit
  precision test;
- the depths read back linear are the drawn ones: T3's front quad
  `400000` (0.25), the kept one `800000` (0.5), untouched `FFFFFF`. The
  DB writes Z_24 in the low 24 bits, and the Z16 sample order holds for
  32-bit cells.

UT2004 as installed (32 bpp, D3D8, its own ini): it now finds D24X8
(`CheckDeviceFormat ... fmt 77 -> 00000000`), creates its device at
800x600 X8R8G8B8 + D24X8 and draws its menu (OBS frame
`obs-ut2004-menu-z24.jpg`); closing it exits cleanly and restores the
desktop. On that exit the proxy logged one `Reset -> 88760868`
(D3DERR_DEVICELOST), after which UT made a new device and exited; not
traced. The Haswell recipe's botmatch (`dm-rankin ... -benchmark
-seconds=77`, `botmatchexec.txt` holding `showhud` and `ship`, as the
Haswell's) ran to its score: **28.36** (1.41 min, 28.23 average, 129.20
max fps), no fault, no failed Set or Draw in the proxy log, depth
ordering right in the frame OBS took (`obs-ut2004-rankin-z24.jpg`). The
score is recorded, not compared.

Not measured: Carrizo and Mullins (GFX8 mode, same DB format field and
depth sample order, no machine run), the linear depth mode at 32 bits
(Mullins only), OpenGL at 32 bpp now that the ICD can be offered a
32-bit Z on GCN, and whether 3DMark 2001 SE changes at 32 bpp.

The proxy and the ini copy were removed from `C:\UT2004Demo\System`
afterwards; `Benchmark\Stuff\botmatchexec.txt` was left.

Evidence: [`../probe/r7250-ut2004-z24-2026-11-20/`](../probe/r7250-ut2004-z24-2026-11-20/):
the proxy log excerpt, `v9xd32-z24-V9XD32.TXT`, the release-check folder,
the benchmark result, the two OBS frames, and the agent screenshot of the
16 bpp run (black: agent screenshots miss flipped frames).
