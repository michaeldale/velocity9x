# RV280 3D engine draws by register writes, no CP

Date: 2026-11-15

Machine: M-HNBJNV, Radeon 9250 (`1002:5960`), Windows 98 SE. The driver
was branch `ati-rv280`'s ati package (`539fb5ce-dirty`, boot 19). Probe:
`V9XR23D.EXE` + `R23D.VXD` at `2835f69e-dirty`. Phase 5 of
[`../plans/ati-rv280-radeon-9250.md`](../plans/ati-rv280-radeon-9250.md),
first step. Evidence: [`../probe/rv280-3d-draw-probe-2026-11-15/`](../probe/rv280-3d-draw-probe-2026-11-15/).

## Question

Does the R200 3D engine draw when every register is written directly over
BAR2, with the CP off and no microcode? The values come from xf86-video-ati
6.14.6's MMIO paths:
- `RADEONInit3DEngineMMIO`'s R200 branch, `radeon_commonfuncs.c:777-803`;
- `R200PrepareComposite` and `RadeonCompositeTile`,
  `radeon_exa_render.c:995-1132` and `2455-2509`.

The X driver only draws textured rectangles. Two things it does not show
were hypotheses this probe measured:
- **Diffuse-only blending:** `TXCBLEND_0` and `TXABLEND_0` set to
  ARG_C = diffuse with A = B = 0, the stage's output in R0, and
  `PP_CNTL` enabling blend stage 0 with no texture unit.
- **Colour byte order:** the order of the bytes in a packed (`PK_RGBA`)
  vertex colour.

The vertex dword order (X, Y, then colour 0) follows the register's bit
order, as Linux `r200.c` `r200_get_vtx_size_0` counts the fields. That
count gives sizes, not an order, so the order was also on test.

## What ran

`src/chipsets/ati/rv280/rv280_3d.c` builds every value. Its host test,
`tests/host/test_rv280_3d.c`, was written first and crashed against a
stub that left the list unset.
- **Init:** `RB3D_CNTL` = 0 (`RADEONEngineInit`), then the R200
  branch's ten writes. TCL is bypassed by leaving `SE_VAP_CNTL`'s
  `TCL_ENABLE` clear (`SE_VAP_CNTL` 00250000h), and `SE_VTE_CNTL` is 0,
  so there is no viewport transform.
- **Per draw:** 14 writes of colour buffer and state, then `SE_VF_CNTL`
  (triangle list, walk data, no `RADEON_MODE`) and three dwords per
  vertex to `SE_PORT_DATA0`, then `WAIT_UNTIL` 3D idle-clean.
- The VxD waits for idle, which flushes the destination cache through
  `RB3D_DSTCACHE_CTLSTAT`.

The target was a 64-pixel-wide surface at frame-buffer offset 16 MiB,
prefilled with A5h. The triangle's corners were (2,1), (54,1) and
(2, height-2).

## Measured

| | 1024x768x16 | 1024x768x32 |
|---|---|---|
| FlatOrder0: colour `FFFF0000`, `COLOR_ORDER_RGBA` clear | red (`F800`), 601 of 601 | red (`00FF0000`), 220 of 220 |
| FlatOrder1: same colour, `COLOR_ORDER_RGBA` set | blue (`001F`), 601 of 601 | blue (`000000FF`), 220 of 220 |
| Pixels outside changed, either flat test | 0 | 0 |
| Gouraud (red, green, blue corners): inside wrong | 0 of 601 | 0 of 220 |
| Gouraud worst channel error, steps | 1 (5/6-bit) | 2 (8-bit) |
| 2D fill after the 3D tests: bytes off | 0 | 0 |

`RBBM_STATUS` read 140h at the start, after the init and at the end, so
the engine was idle. Every wait finished in 3 to 8 status reads.

- **Diffuse-only blending works.** The vertex colour reaches the colour
  buffer through blend stage 0 with no texture unit.
- **A D3D colour goes in as it is.** A D3DCOLOR (`AARRGGBB`) dword is the
  packed colour with `COLOR_ORDER_RGBA` clear. Setting the bit swaps red
  and blue.
- **The dword order is right:** X, Y, colour.
- **Gouraud is right:** colours interpolate to within a step of the value
  at the pixel centre, as on the RS690.
- **2D is unharmed:** the 3D state left behind does not break the 2D
  engine DirectDraw uses.

Before the init, `SE_CNTL` read `001300C0` and `RB3D_CNTL` `00001800`.
VBE leaves values there, so the init has to write them.

## Not explained

At 32 bpp the drawn pixel's alpha byte is 0, though the vertex alpha was
FFh and `TXABLEND_0` passes diffuse alpha. That is harmless for an XRGB
target. The cause is not known and matters once alpha blending and alpha
targets are built.

## Not checked

- Textures, Z, blending, alpha test, culling, fog and specular: none of
  them ran.
- 8 bpp: refused by the builder, since the colour buffer has no palette
  format.
- Throughput: a triangle costs 1 + 9 MMIO writes after the state.
- Larger or many primitives in one `SE_VF_CNTL`, and long runs.
