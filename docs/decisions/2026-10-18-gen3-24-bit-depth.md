# Gen3 24-bit depth: D24X8 with 565 and ARGB8888 targets, and a probe that tells it from 16

2026-10-18, MICHAEL-NETBOOK (945GSE / GMA 950), boot 211, development
build `a1d7cc1e-dirty` (this change). Decision 1 of
[`../plans/32bpp-acceleration-and-3d.md`](../plans/32bpp-acceleration-and-3d.md)
(offer 24-bit depth beside 16, the application chooses), and step 1 of
[`../plans/intel-24-bit-depth.md`](../plans/intel-24-bit-depth.md), which
asked for 565 + Z24 to be measured first. Evidence:
[`../probe/netbook-gen3-z24-2026-10-18/`](../probe/netbook-gen3-z24-2026-10-18/).

## Sources

`DEPTH_FRMT_24_FIXED_8_OTHER` = `(2<<2)` (Mesa 20.3.5 `i915_reg.h:170`).
Mesa selects it from the depth buffer's cpp alone, whatever the colour
format (`i915_vtbl.c:611-616`); xf86-video-intel pairs it with ARGB8888
(`i915_video.c:155`). No reference pairs it with RGB565: Mesa's window
configurations give 565 only 16-bit depth (`intel_screen.c:1056-1058`).

## The change

- **The core sizes depth per surface.** A context's depth cell (2, or 4 for
  a 32-bit Z surface) comes from the surface's own pixel format
  (`DDPF_ZBUFFER`, 32 bits), not from the engine's one number. An engine
  takes a 32-bit Z surface only with the new appended limit `depth32_bits`
  (the bits of depth it holds, 24 for Gen3); otherwise the surface is
  refused with the new `V9X_D3D_ZREJECT_FORMAT`. The draw carries the layout
  (`V9X_R3D_DEPTH_Z24X8`) to the engine.
- **Depth fills** take the destination surface's cell: DDBLT_DEPTHFILL at 4
  bytes (the Gen3 blitter's 32 bpp fill, b9a1d7c6) with the value masked to
  24 bits, so the runtime's 0xFFFFFFFF is the far plane. Clear2's full
  scale is 0xFFFFFF for a 32-bit buffer. The CPU clear writes 32-bit cells.
- **Caps:** Gen3 reports `dwDeviceZBufferBitDepth` DDBD_16 | DDBD_32. The
  16-bit side adds DDBD_32 to `ddCaps.dwZBufferBitDepths` when
  `v9x_d3d_mode_deep_z` says so: hardware state, Gen3 engine. DirectDraw
  will not allocate a 32-bit Z surface without it. DriverInit's DDBD_16 is
  set before the chip is known and is unchanged. DDI 6's Z pixel formats
  list D16 and, for such an engine, a 32-bit format with a 24-bit mask.
- **Gen3:** `v9x_i9xx_retarget_state` also takes ARGB8888 + D24 and
  565 + D24, disabling alpha writes only for ARGB8888; the flat decoder
  follows. The depth binding's footprint is measured at the cell's size
  (`bind_depth_at`, as `bind_target_at` was). Z placement handles 4-byte
  cells. I9XXCODE is unchanged (`0DFD9h`); `_TEXT` grew 72 bytes.

Host tests were written before the code and failed to compile. The
`bind_depth_at` cases were added with its code and not seen failing alone.

## The instrument, and the first form of T5 that was wrong

`V9XD32 /z24` creates the Z buffer at 32 bits and clears it at full scale.
T5 draws a green quad, then a red one a fraction of a 16-bit step nearer,
with LESS: 16 bits must keep the green, 24 must draw the red.

The first T5 put the green at z 0.25, three quarters of the way through a
16-bit step, and the red 2e-6 nearer. **The red drew with a 16-bit buffer
too** (all four runs, `*-first-t5.txt`). That rules out the premise that
two depths in one step compare equal. The stored value rounds up to the
next step, and the incoming fragment is compared at more than 16 bits,
so it passes against it. The test moved to the lower quarter of a step
(green at 16000.25 / 65535, red at 16000.15 / 65535). There both rounding
and truncation store 16000 and the red fragment, above 16000, fails.

## Measured (boot 211, second T5)

| Run | Colour + depth on Gen3 | T1-T4 | T5 pixel | Result |
|---|---|---|---|---|
| `/bpp16` | 565 + D16 | pass | `07E0`, green kept | PASS |
| `/bpp16 /z24` | 565 + D24 | pass | `F800`, red drawn | PASS |
| (none) | ARGB8888 + D16 | pass | `0000FF00`, green kept | PASS |
| `/z24` | ARGB8888 + D24 | pass | `00FF0000`, red drawn | PASS |

- **24-bit depth works with both colour formats**, including 565 + D24,
  which no reference driver shows.
- The 32-bit Z surface was created, attached and depth-filled with no
  error in both `/z24` runs; T3's ordering holds at 24 bits.
- Snapshot after all eight runs: `I9xxDrawsSubmitted=64`,
  `CountD3dContextCreate=16`, `D3dContextRejects=0`, `I9xxDepthSkipped=0`,
  `CountBltEngine=24`, no breadcrumb, idle or abandon counts; the DRV, HAL
  and trace builds agree.
- V9XDDP at 16 bpp: all 78 `...Ok` keys identical to the 0.19.0 run on
  this netbook.

## Not measured, and owed

- **3D WinBench 98's Z accuracy tests** (the reason for
  `intel-24-bit-depth.md`), and which depth it chooses now that DDBD_32 is
  offered.
- What a DX5 title asks for once DDBD_32 is in the caps, and whether any
  title assumes a 32-bit Z surface holds 32 bits of depth.
- The OpenGL ICD still creates 16-bit depth; its pixel formats do not
  offer 24.
- Textured, blended and fogged draws over a 32-bit depth buffer: V9XD32 is
  untextured.
