# Carrizo's first 3D draw: the full clear state runs, the draw completes and writes nothing; the BIOS left the 3D engine unconfigured

Date: 2026-10-28

Status: **measured, one machine, three runs on one boot; the draw does not
work yet.** M-XP7053's Radeon R7E (`1002:9874`), boot 19. Phases 2 and 3
of [the 3D plan](../plans/ati-carrizo-gfx8-3d.md). Reports in
[`../probe/m-xp7053-carrizo-first-draw-attempt-2026-10-28/`](../probe/m-xp7053-carrizo-first-draw-attempt-2026-10-28/).

## What was built

- `vi_clear_state.c`, generated by `gen-carrizo-clear-state.ps1` from
  Linux's `clearstate_vi.h` (MIT, AMD 2014; the header's SHA-256 is
  checked). It holds 885 context registers in seven runs.
- `vi_shader.c`: GCN 3 encoders for VOP1, VOP2, VOPC and EXP, and two
  shaders built from them.
  - A RECTLIST vertex shader that picks each corner from VertexID and
    four user SGPRs.
  - A pixel shader that exports four user SGPRs as a colour.

  Each encoder is checked against LLVM's GFX8 assembler test bytes, and
  both shaders word for word (`test_vi_3d.c`, written first; it failed to
  build before the modules existed).
- `vi_3d.c`: `cp_gfx_start`'s whole stream, and a solid rectangle into a
  linear colour buffer, closed by Linux's `ring_emit_fence_gfx`
  end-of-pipe event. Host-tested for packet counts and the key register
  values.
- `V9XCZ3D.EXE`, a second publisher on `CZCP.VXD`. The VxD gained a bulk
  copy from the data array into its window, reads of `GB_ADDR_CONFIG` and
  the tile table, and a write of `GB_TILE_MODE8`.

## What ran

Each run brought the CP up as V9XCZCP does. Then it submitted:
1. the ring test;
2. the full start stream with `vi_cs_data`, and a scratch write behind it;
3. a 32x8 rectangle into a 64x16 32 bpp target, `COLOR_8_8_8_8`, tile
   index 8, prefilled with `5A5A5A5A`.

- **The full clear state is accepted.** `CP_RB0_RPTR` reached 3B0h, and
  `600DCAFE` landed in 13h polls in all three runs.
- **The draw's fence lands, and no pixel does.** The end-of-pipe event
  wrote its value within 6-7 polls, and RPTR reached the end (450h). All
  1,024 target dwords read `5A5A5A5A`, inside the rectangle and out.
- **Run 2: the tile table.** `GB_TILE_MODE8` read `00C0077C`. That is
  array mode Fh, not linear-aligned, and Linux's Carrizo table has 4 at
  index 8. `GB_TILE_MODE0` read `00802AE0` in the register probe, where
  Linux writes `00800010`. So the BIOS did not program the table. The
  probe now writes 4 before the draw: read back 4 in run 3, restored
  after. Still nothing drew.
- **Run 3: `SPI_SHADER_PGM_RSRC3_VS/_PS`** (CU enable, wave limit) were
  set to radeonsi's `003FFFFF`, and the viewport Z range to [0, 1.0].
  Still nothing drew.

After each run the CP was halted and the RLC stopped again. SDMA0 and
the desktop were unaffected throughout.

## What the evidence says

`GB_ADDR_CONFIG` reading Linux's golden `22010001` had suggested the BIOS
set the GFX block up. The tile table says otherwise. A legacy VBE boot
brings up the display and leaves the 3D engine near reset. Linux's
`gfx_v8_0_gpu_init` and `init_golden_registers` do the rest, and none of
it has been done here:
- the Carrizo golden-register tables;
- the whole tile and macrotile tables;
- `setup_rb`;
- `SH_MEM_CONFIG`, `APE1` and `BASES` for every VMID, through
  `SRBM_GFX_CNTL`;
- `PA_SC_FIFO_SIZE`, the scan converter's FIFO depths (Carrizo 20h, 100h,
  30h, 130h);
- `GRBM_CNTL`'s read timeout;
- `HDP_ADDR_CONFIG` and `DMIF_ADDR_CALC`.

A scan converter with zero-depth FIFOs, or an SQ with no memory
configuration, would explain a draw that finishes at once and writes
nothing. That is a hypothesis: none of those registers was read.

## Not checked

- The values of `PA_SC_FIFO_SIZE`, `SH_MEM_CONFIG` and the golden
  registers as the BIOS left them.
- Whether the shaders ran at all. Nothing reported waves launching or
  pixels exported.
- The rest of the tile table.
