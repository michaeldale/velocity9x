## Reading of the results (written by hand)

This run is the baseline for [the 1.0 plan](../plans/release-1.0.0.md),
not a release check. The driver code is 0.60.0's; `ac9aa76b` only bumps
the version. The machine list was a scratch copy of the private one with
the four 86Box guests (a new optional `Port` per machine in the runner),
M-BXMFA8's Oland 6611 and the HD 4600 on the `vbe` package added. The
agents on the four guests were updated from 0.9.1-0.16.0 to 0.19.0 first.
After its `vbe` run the HD 4600 was put back on `intel-gma` (boot 296,
8 of 8 files, the nine probe runs exit 0 again; that run's folder is not
kept here).

First release-check run of these packages since 0.42.0: `s3` (two
guests), `matrox` (one guest), `vbe` since 0.47.0. All installed 8 of 8
and booted.

- **V9XFBCMP FAIL on the ViRGE/DX guest and the RIVA 128ZX: the probe,
  not the driver.** It asked GDI for a 5:6:5 copy of the screen, and both
  desktops are 5:5:5, so GDI converted every pixel (768,979 of 786,432
  differ on the ViRGE, 456,080 of 480,000 on the RIVA). The probe now
  takes the masks from the primary surface. Rerun on both S3 guests the
  same boot: ViRGE/DX `ScreenRedMask` 7C00h, `Differ=0`, PASS; Trio64
  F800h, `Differ=0`, PASS
  ([`fbcmp-555-rerun/`](../probe/1.0-baseline-2026-11-21/fbcmp-555-rerun/)).
  Not rerun on the RIVA 128ZX. A first attempt through GetDIBits on a
  compatible bitmap returned 01576DF3h as the red mask on both guests and
  was dropped.
- **Oland 6611:** its first release-check run. V9XD32 fails
  T19 FfSpecFog only (11h pixels at both depths), the known Oland
  [issue](../issues/2026-11-17-t19-ffspecfog-mismatch-oland-gt218.md).
- **RIVA 128ZX:** V9XD32 `/bpp16` fails T22A and T22X (the known black
  32-bit textures,
  [issue](../issues/2026-11-17-riva128-t22-32bit-textures-draw-black.md))
  and T20Ok reads FFF3h; V9XGLIDP fails BlendHalf as before.
- **ViRGE/DX guest:** V9XD32's default run asks for 32 bpp and gets
  `NO-HAL-AT-DEPTH`; the entry should ask for `/bpp16`. V9XGLIDP fails
  FogTable, as the README says of this card.
- **Millennium guest (no 3D engine):** V9XD32 `NO-HAL-AT-DEPTH`, V9XGLIDP
  fails to open and V9XR3DP reads `FAIL-DESCRIBE` (DescribeResult 5),
  while V9XGLP passes. Whether Glide and the render interface are meant
  to be absent on an engineless card with software Direct3D off was not
  checked. Open.
- **Mach64 VT2 guest:** its desktop is 8 bpp, so V9XD32 (`NO-MODE`),
  V9XWPRS and V9XFBCMP did not measure anything. Rerun at 16 bpp owed.
- **V9XGLP `CvaResult=FAIL-MISSING`** on the Millennium and Mach64 VT2
  guests, inside an overall PASS. Not looked at.
- **Trio64 guest: windowed presents take 134 ms** (DirectDraw) and 135 ms
  (OpenGL) for a 512x384 window, against 2.1 and 3.4 ms on the ViRGE/DX
  guest in the same emulator. Not explained. That guest's SYSTEM.INI has
  carried `Direct3D=2` since 2026-10-18.

## Later the same day: the 86Box guests again

Evidence:
[`../probe/1.0-baseline-2026-11-21-86box/`](../probe/1.0-baseline-2026-11-21-86box/).
Same build, same probes with the fixed V9XFBCMP.

- **ViRGE/DX guest, V9XD32 `/bpp16`:** fails T1 (176h mismatched
  pixels), T4 (1FAh) and T14 (176h). **Not a regression in the driver:**
  the released 0.36.0 `s3` files, installed on the same guest (HAL
  943,104 bytes, checked), fail the same three with the same counts under
  today's probe
  ([report](../probe/1.0-baseline-2026-11-21-86box/virge-0.36.0-ab/)).
  On the physical ViRGE/DX only T4 failed on 2026-11-04. Whether the
  probe or 86Box accounts for T1 and T14 is not separated. V9XFBCMP
  passes. The guest is back on today's build (boot 695, 8 of 8).
- **Mach64 VT2 guest at 800x600x16:** V9XWPRS and V9XFBCMP pass now;
  V9XD32 still reads `NO-MODE`.
- **Trio32 guest (port 9875), first run:** boots the `s3` package, 8 of
  8. Its desktop is 8 bpp, so V9XD32, V9XWPRS and V9XFBCMP measured
  nothing; 16 bpp rerun owed. 86Box's Trio32 answers as `5333:8811`.
  V9XGLIDP and V9XR3DP fail to open and describe there, as on the
  Millennium guest. The Trio64 guest, with `Direct3D=2`, passes both, so
  on a card with no 3D engine they are probably absent unless software
  Direct3D is on. Not confirmed by switching it.
- **Mode matrix** (`run-vm-mode-matrix.ps1`: each mode set at boot, then
  V9XGDI, its acceleration phase and the palette check): `ati` on the
  Mach64 VT2 passes its six modes; `s3` passes all eleven modes on the
  Trio64 guest and on the ViRGE/DX guest. Each S3 guest stuck once at
  "Windows is shutting down" on the way, and needed its emulator
  restarted
  ([issue](../issues/2026-11-21-86box-s3-guests-stick-at-shutdown-in-mode-matrix.md)).

Not run: M-D7TFW4, which shows both an HD 7470 (`1002:6778`) and the
HD 7660D (`1002:9901`); the 0.57.0 checks and the released 0.56.2 both
failed and hung on it in that state. The GM45, the R3E, the RS690 and
the Oland XT machine did not answer. No guest or machine for `sis` or
`3dfx`.
