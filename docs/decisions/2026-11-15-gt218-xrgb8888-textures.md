# GT218: XRGB8888 textures, V9XD32 T22X passes

Date: 2026-11-15

Status: implemented and measured on W9QI0DAD (ASUS GeForce 210, GT218
`10DE:0A65`, FX-6300, Win98 SE), boots 20 and 21. Step 0 of
[nvidia-gt218-ps11.md](../plans/nvidia-gt218-ps11.md).

## The change

- `nv50_d3d.h` / `nv50_d3d.c`: a fifth sampler format,
  `V9X_NV50_D3D_TEX_B8G8R8X8`. Its TIC word 0 is the B8G8R8A8 word with W
  taken from the constant one (`ONE_FLOAT`, 7) instead of memory alpha:
  Mesa's `nv50_formats.c` row `F3(A, B8G8R8X8_UNORM, ..., B, G, R, xx,
  UNORM, A8B8G8R8, TD)`, the same treatment the tree already gives
  B5G6R5. Word 0 is `0x3a712488`; the host test holds it.
- `d3d_nv50.c`: a 32-bit RGB surface without `DDPF_ALPHAPIXELS` and masks
  `00ff0000/0000ff00/000000ff` resolves to that format, and the format
  list grows from four to five entries (XRGB8888 last, as `d3d_g4.c`
  lists it).
- `d3d_nv50_map.c`: the format is four bytes a texel for the pitch check.

The untouched top byte of an X8R8G8B8 texel never reaches the shader, so
whatever the application left there (V9XD32 T22X writes non-0xFF on
purpose) cannot leak into alpha blending or the alpha test.

## Measurement

Same V9XD32 binary (built from this tree) both runs, 32 bpp and then
`/bpp16`. Boot 20 ran the installed driver (main 5be22308 plus
V9xEngineStart, a0b71d84-dirty in the machine record); boot 21 ran this
change, deployed with `update-associated-driver.ps1 -NoReboot` and `reset`,
the four installed files (`V9XDISP.DRV`, `V9XMINI.VXD`, `V9XHAL.DLL`,
`V9XSETP.DLL`) hash-checked against the package after the restart.
Reports in [`docs/probe/w9qi0dad-gt218-xrgb8888-2026-11-15/`](../probe/w9qi0dad-gt218-xrgb8888-2026-11-15/).

| | boot 20 (before) | boot 21 (after) |
|---|---|---|
| T22X 32 bpp | `T22XOk=0`, pixels all 0 | `T22XOk=0xF`, pixels `002040C0 00C08020 0010E070 0090A0F0` |
| T22X 16 bpp | `T22XOk=0` | `T22XOk=0xF` |
| T22A (ARGB8888) | `0xF` both depths | `0xF` both depths |
| `Failures` | 2 (T22X, T20) | 1 (T20) |
| other 18 `*Ok` keys | — | identical at both depths |

Every other line that differs between the two reports is a handle, a
surface pointer, a PID or a tick count, except four 32 bpp Z diagnostic
counters (`ZClearFar16`, `ZClearOther`, `ZDepthFar16`, `ZDepthOther`).
Those count what a Lock of the Z buffer reads back, which is the GT218's
open "Z Lock conversion" item: Lock returns unconverted engine Z, and the
counts move from run to run. No verdict reads them. At 16 bpp they did
not move.

T20 (partial) is the remaining failure, unchanged and still on the
GT218's open list.

## Gates

`build-host.ps1` passed with the new TIC test; `run-checks.ps1` passed
before the commit.
