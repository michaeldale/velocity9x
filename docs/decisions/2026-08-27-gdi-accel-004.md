# GDI acceleration, build 004: monochrome CPU-to-screen upload

Date: 2026-08-27
Status: implemented and verified on the ViRGE/DX; default off

The results record for the design in
[`2026-08-27-gdi-accel-004-design.md`](2026-08-27-gdi-accel-004-design.md),
which narrowed build 004 to **monochrome expansion only** and argued colour
upload is not worth implementing. That narrowing stands. What follows is what
the implementation actually took, including a defect that took four guest runs
to find and is worth recording in full because the shape of it will recur.

## The defect: two structs that share their first ten bytes

The first run with `GdiAccelUpload=1` reported `Enabled=23`, `Uploads=0`, and
**`Result=PASS`**. Every monochrome operation was being declined and the
comparison passed anyway, because the DIB Engine had drawn the pixels correctly.
A build that accelerates nothing looks exactly like a build that accelerates
everything correctly, if the only thing being checked is the pixels.

The counters said `DeclineGeometry`. Adding a reject bitmask said bit 8 - the
64 KiB selector bound - with the offending source address `0x20000000`. Half a
gigabyte, for a 64x64 monochrome bitmap.

The cause is that GDI hands a monochrome `BitBlt` source over as a plain Win16
**`BITMAP`**, not a `DIBENGINE`, and the two layouts share only their first ten
bytes:

| Offset | DIBENGINE | BITMAP |
|---|---|---|
| 0 | `deType` (`TYPE_DIBENG` **or 0**) | `bmType` (0) |
| 2, 4, 6 | `deWidth`, `deHeight`, `deWidthBytes` | same three |
| 8, 9 | `dePlanes`, `deBitsPixel` | `bmPlanes`, `bmBitsPixel` |
| 10 | `deReserved1` | **`bmBits`** - 16:16 far pointer |
| 14 | `deDeltaScan` | *(end of struct)* |
| 18 | **`deBits`** - fword, 32-bit offset + selector | - |

Every field the dispatcher's gates read - width, height, stride, bits-per-pixel
- is in the shared prefix, so every gate passed and read a correct value. The
one field past the boundary, the bits pointer, was garbage. `deBitsPixel` at
offset 9 is 1 for a monochrome bitmap under **either** interpretation, so even
the check that exists specifically to identify a monochrome source could not
tell the two apart.

The discriminator is `deType`: `TYPE_DIBENG` (0x5250) for a DIBENGINE, **zero**
for a BITMAP (`DIBENG.INC:55`). It must be read before any field past byte 10.

A second, quieter bug fell out of the same confusion: the source VRAM test read
`deFlags` at offset 24, which for a `BITMAP` is past the end of the object
entirely. It now runs only on the DIBENGINE branch - a plain BITMAP has neither
the field nor the possibility of being in video memory.

### The wrong correction, and the right one

The first fix read the bits pointer from offset 10 as an **fword**, matching
`deBits`. The next run reported `0x0d170020`. Still not an offset - but
`0x0d17 mod 8 == 7`, which is the low bits of a ring-3 LDT selector. The high
half was the selector, not the high half of an offset.

`GDIDEFS.INC:48` settles it: `bmBits dd 0`, "Far pointer to bits of main memory
bitmap". A plain 16:16 pointer - offset at 10, **selector at 12**, struct size
14. Which also explains something that had looked like a shortcut in the
reference: `mov si,ds:[si.bmBits.off]` (`S3BLT.ASM:948`) is not truncating a
32-bit offset to 16 bits, because the field is 16 bits to begin with.

With that, `Uploads=29`, `DeclineGeometry=0`, and `Compared=PASS`.

## What the harness now asserts

Three checks, in the shape builds 002 and 003 established, added because none of
the existing ones could see this defect:

- `upload-enabled-but-never-fired` - with upload on, `uploads` must move.
- `upload-declines-never-exercised` - `decline_upload` must move either way:
  with upload off every memory-source operation declines there, and with it on
  the colour-source ones still do.
- `upload-unexpected-reject-reason` - with upload on, the reject bitmask must
  contain only bit 0 (accepted) and bit 4 (colour source refused). Any other bit
  means monochrome work is being refused for a reason this build does not intend.

**That third check is the one that would have shortened this.** Bit 8 was set on
every run from the first, while the pixel comparison passed.

`upload-declines-never-exercised` is gated on `stats.enabled != 0`, which is
load-bearing rather than defensive: on a family with no 2D engine every
operation declines at the first gate and no counter past it moves, so without
that gate the check would fail on ati, vbe and matrox-m2 while all three behave
exactly as designed. This is the fourth time in this plan that a zero-counter
check needed a liveness predicate to avoid failing a healthy driver, and the
first time it was caught by reasoning before a run rather than after one.

## The colour swap, tested by making it fail

The ViRGE reads a **set** mono bit as *background*, so the implementation
assigns `SRC_BG_COLOR` from the DRAWMODE's `TextColor` and `SRC_FG_COLOR` from
its `bkColor` - deliberately crossed. A passing comparison does not confirm
that; it only confirms nothing detected it.

So the assignment was un-crossed on purpose and rerun. `Compared=FAIL` at
operation 25 - the first monochrome blit - with screen `(128,0,0)` against
reference `(0,255,255)`. Inverted, as predicted, and detected two uploads in.
The swap is right and the check that says so can fail.

## Verified state, ViRGE/DX at 640x480x8

```
Advertised=23   Enabled=23      Uploads=29      UploadsDelta=29
DeclineUpload=27                DeclineUploadDelta=22
UploadRejectMask=0x00000011     UploadRejectDetail=0x00000020
DeclineGeometry=0               Compared=PASS   Result=PASS
```

`UploadRejectDetail` is the accepted source's start offset: 32 bytes. Small, as
the 16-bit addressing in the transfer helper requires - and now known to be
small for a structural reason rather than by luck.

## Mode matrices

All three emulated guests, one pass each, with the ViRGE deliberately left with
`GdiAccelUpload=1` so the matrix exercised the new path in every mode it serves
rather than only in the one mode it was first verified in.

| Guest | Modes | Result | Upload state |
|---|---|---|---|
| s3 / virge-dx | 11 | **11/11 PASS** | on: `Uploads=29` in all eight accelerated modes |
| s3 / trio64 | 11 | **11/11 PASS** | off: `DeclineUploadDelta=51` in all eight |
| ati / mach64-vt2 | 6 | **6/6 PASS** | no engine; declines at the first gate |

The counters are identical across every accelerated mode on each chip, which is
what makes the set worth more than its first member:

- **ViRGE, eight accelerated modes**: `Uploads=29`, `DeclineUploadDelta=22`,
  `UploadRejectMask=0x11` - accepted plus colour-refused, and **nothing else**,
  at both 8 and 16 bpp.
- **ViRGE, three 32-bpp modes**: `Uploads=0`, mask `0x00`,
  `ZeroCounterChecked=0`. The checks skip, and say so.
- **Trio64, eight accelerated modes**: mask `0x02` - bit 1, "not enabled" -
  because with upload off the first test catches colour and monochrome alike
  before the depth test is reached.

`ati` passing matters specifically: it is the case
`upload-declines-never-exercised` would have failed on without its liveness
guard, so the guard is now measured rather than argued.

## DirectDraw regression

`V9XDDP` on both S3 guests after the matrices, since 004 adds an engine command
the HAL shares the engine with. `Result=COMPLETE` on both, `BltFillHr=0`,
`BltFillPixelOk=1`, `SrcCopyPixelOk=1`, all four overlap probes ok, and the HAL
caps unchanged. The Trio64's three `0x80004005` results are its texture calls,
on a chip reporting `D3DHalFound=0`.

`FlipPixelOk=0` appears on both chips and is **not** a regression: it reads 0 in
every recent pre-004 capture, including the one taken with the **native S3
driver**. It is a property of the probe's flip readback rather than of any
driver, and is left alone here rather than folded into this build's result.
