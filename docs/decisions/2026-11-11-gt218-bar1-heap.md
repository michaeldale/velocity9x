# GT218 maps BAR1: a 126.5 MiB DirectDraw heap where VBE gave 14 MiB

Date: 2026-11-11

Phase 4's heap item of [docs/plans/nvidia-gt218.md](../plans/nvidia-gt218.md),
taken before any engine because the
[BAR window record](2026-11-11-gt218-bar-windows.md) showed BAR1 + 0 holds
the desktop and BAR1 stores distinct writes across its 256 MiB with no BAR
VM.

## The change

- `include/velocity9x/hw16.h`: an appended device field,
  `aperture_from_bar`. Non-zero, in a family with no `read_aperture` hook:
  map the row's `framebuffer_bar`, read from PCI by the existing
  chip-agnostic `V9xPciReadBar`, instead of the VBE's PhysBasePtr. A
  refused read keeps the VBE's. Michael chose this shape over an
  nvidia-only conditional calling a new external (2026-11-11).
- `src/display16/enable16.c`: applies it after the `Aperture` trace (the
  boot record keeps the BIOS's base) and records `ApertureFromBar=`.
  Compiled only where the family manifest defines
  `V9X_HW16_APERTURE_FROM_BAR` (nvidia): built unconditionally it took the
  ati image's `_TEXT` to 57,457 bytes, 113 over the audit's 57,344-byte
  budget. Moving `cedar_hw16.obj` to its own segment was tried first and
  fails to link (`ati_hw16.obj` calls it near), so that is not an option
  for the ati family as built.
- GT218 row (`gt218_hw16.c`): `framebuffer_bar` 1, `aperture_from_bar` 1,
  `map_bytes` 128 MiB (the Cedar rows' size on the same host), and a heap
  that is the whole mapping (`v9x_gt218_measure_video_memory`, through the
  nvidia family's new `measure_video_memory` hook, which returns 0, "keep
  4F00h's", for the RIVA 128).

Gates: check-tree, build-host, run-checks passed (package `803ae36a-dirty`).

## Boot 83, M-BXMFA8

DRV, VxD, HAL, SETP and ICD renamed in by WININIT, hash-checked. Evidence:
`build/driver-results/m-bxmfa8-gt218-boot83/`.

| Key | Boot 82 (VBE window) | Boot 83 (BAR1) |
|---|---|---|
| `Stage` | enable-ok | enable-ok |
| `Aperture` (BIOS's) | `b=cf000000` | `bar=1 b=cf000000` |
| `ApertureFromBar` | — | `b=d0000000` |
| `DpmiMap` | `01000000:ok` | `08000000:ok` |
| `VddReserve vram=` | 14,680,064 | 134,217,728 |
| MTRR | WC 8 MiB at `CF000000` | WC 128 MiB at `D0000000` (`MtrrWrite=ok`, mask `F8000800`) |
| V9XGDI `/auto` | PASS | PASS |
| V9XMSW `/cycle:4` | PASS 4/4 | PASS 4/4 |
| DirectDraw `GblHalVidMemTotal` | not run | `0x07E80000` (126.5 MiB, one heap) |

The desktop draws correctly in the agent's screenshot (a framebuffer
readback; the monitor itself has not been looked at). V9XHW.INI still says
`VbeVramBytes=14680064`: that key is the BIOS's figure, not the heap's.

V9XDDP `Result=COMPLETE`. Its failing keys are the Direct3D ones
(`D3DZ*`, `Mixed*`; the row advertises no Direct3D, `Direct3DMode=none`)
and `FlipPixelOk`, which has its own issue saying it cannot be read
(docs/issues/2026-09-02-flippixelok-is-uninterpretable.md). There is no
V9XDDP run on the VBE window to compare with, so whether any key changed
with the aperture is not known. The DirectDraw stage record
(`V9XDDH.INI`, `setinfo-callback-missing` after `setinfo-ok`) is the same
as on boots 81 and 82.

## Open

- No program has yet allocated past 14 MiB. The heap is advertised; using
  it (a texture-heavy game, or a probe that fills the heap and reads it
  back) is the test that would show BAR1 + x is video memory x.
- BAR1 write-combining over 128 MiB is installed but unmeasured for speed.
- 256 MiB (all of BAR1) was not tried.
