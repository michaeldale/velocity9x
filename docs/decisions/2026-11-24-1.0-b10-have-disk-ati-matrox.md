# B10, the ati, matrox and vbe packages by Have Disk, and why the settings tab moved: DESK.CPL seeds the Tag from OEMCPL.INF

Date: 2026-11-24. Machine: 86Box, fresh clones of `Win98SE-Native-S3`
(the S3 reference VM, never had Velocity9x) with the emulated card
changed, host port 9879. Build `6f5ce760-dirty` (the dirt is the
quarantined 0.52.0 zip deletion), then the same tree with the fix below.

## The installs

Each clone was checked clean first (no `V9XDISP.DRV`, no `C:\V9XDIAG`),
the package pushed to a folder on C:, and installed by Device Manager,
Update Driver, "Display a list...", Have Disk.

| Package | Card (86Box) | Windows' driver before | Models offered | First boot |
|---|---|---|---|---|
| `ati` | Mach64 VT2 `mach64vt2` | its own "ATI Graphics Pro Turbo PCI (atim64 - VT)", 1024x768x16 | one, "Velocity9x ATI Mach64 VT2" | boot 86: `enable-ok`, 1024x768x16, `Adapter=ATI Mach64 VT2 264VT2`, `Direct3D=not-advertised` |
| `matrox` | Millennium `millennium`, 4 MB | its own "Matrox MGA Millennium", 1024x768x16 | one, "Velocity9x Matrox Millennium MGA-2064W" | `enable-ok`, 1024x768x16, `Adapter=Matrox Millennium MGA-2064W` (twice, two clones) |
| `vbe` | ViRGE/DX `virge_dx_pci` | S3's own | one, "Velocity9x VBE-generic display (any VESA VBE 2.0+ adapter)", after Windows' "current driver may be a closer match" warning | `Stage=fail-hardware-vbe-mode`, desktop at 640x480 |

No install asked for `V9XDISP.DRV`. `BitsPerPixel` stayed 16 before each
restart; no first boot came up at 16 colours.

The `vbe` failure is on a card that has its own package. It is
consistent with the open gap that the family refuses modes without a
linear frame buffer
([issue](../issues/2026-11-06-vbe-family-refuses-banked-modes.md)), but
this boot wrote no VBE mode list, so that is not shown. A `vbe` install
on the Mach64 VT2 (whose BIOS the vbe family has driven before) was
tried and abandoned: after the card change Windows asked to restart
before logon, where the agent cannot click, and the 86Box hard reset
used instead sent the clone to Safe Mode. That clone is not evidence
about the driver.

## The settings tab was moved, not lost

On the Mach64 and the first Millennium clone the Velocity9x tabs were
missing from Display Properties after the first logon, although
`V9xSyncModes` had run (its `V9XSYNC.INI` appeared 35 s into the boot)
and the installed `V9XSETP.DLL` was the build's. The handler's Tag stayed
at `0xDD2653C1` for three minutes of polling
(`matrox-millennium/first-logon-poll.txt`). Opening Display Properties
removed the top-level key and the tabs appeared instead under Settings,
Advanced (`matrox-millennium/dp-advanced.png`), with the handler now in
`Class\Display\0000\shellex\PropertySheetHandlers\Velocity9x`.

DESK.CPL 4.10.2222 owns the check (it is the only one of DESK.CPL,
SHELL32, SHDOCVW, SHLWAPI and SETUPX that names the `Tag` value).
Disassembled (`desk-cpl/`):

- The seed is `GetWindowsDirectoryA` + `\INF\OEMCPL.INF`, the find data
  zeroed, `FindFirstFileA`, and the sum of `nFileSizeHigh`,
  `nFileSizeLow` and both halves of `ftCreationTime` and
  `ftLastWriteTime`. Tag = seed + the CLSID text's first eight
  characters as two DWORDs. On these clones that gives 0xC4754D1C, and
  0x3EEABBC9 for our CLSID.
- A handler whose Tag fails goes to a second check. OEMCPL.INF is a
  "database of known OEM CPL extensions" by CLSID; for one not listed,
  DESK.CPL looks for the CLSID among each display device's own handlers
  and INF. If it belongs to a display device, the key is moved into that
  device's driver key, whose pages show under Settings, Advanced, and the
  top-level key is deleted; otherwise the Tag is rewritten and the key
  kept.

`V9xRegisterPage` took its seed from a neighbour handler (PlusPack,
DeskHtmlExt, Voodoo2) instead. On these clones the neighbours carried
Tags under another seed (0x62B0E514: PlusPack `0xED1249C2` before any
Display Properties, `0x4ED6B1CA` after), so the inverted seed reproduced
`0xDD2653C1`, which equals the stored Tag, and the function returned
without writing. Opening Display Properties rewrote the neighbours to
DESK.CPL's seed, which is why running `V9xRegisterPage` by hand
afterwards worked (Mach64, `ati-mach64/display-props-after-manual.png`).

This corrects the s3 record of the same day
([2026-11-24-1.0-b10-have-disk-s3.md](2026-11-24-1.0-b10-have-disk-s3.md)):
the "installer's Tag" there was not Windows'. The INF's RunOnce
`V9xRegisterPage` runs during the install (the Tag is set before Finish
and RunOnce is empty), with the neighbour seed. Why the neighbours on the
reference image carry a seed DESK.CPL does not use was not found. The
s3 record's value `0xDD2532C1` is not in its evidence; the two clones
here measured `0xDD2653C1`.

## The fix

`V9xRegisterPage` (`tools/diag/settings_propsheet.c`) computes the seed
as DESK.CPL does, from OEMCPL.INF, and first deletes our own subkey from
any display driver key DESK.CPL moved it into, so the pages are not shown
twice. Still no new export. `run-checks.ps1` passes.

- Cleanup path, on the used Millennium clone (handler moved, top-level
  key gone): the new DLL staged by WININIT rename; after the restart the
  top-level Tag is `0x3EEABBC9`, the driver-key copy is gone, the tabs are
  top-level and Settings, Advanced shows none
  (`matrox-millennium/after-fix-dll-*.png`).
- Fresh install, a new Millennium clone with the rebuilt package: the Tag
  is `0x3EEABBC9` straight after the files are copied, stays so through
  the restart and logon, and Display Properties shows the tabs at top
  level (`matrox-millennium-fixed/`). The `vbe` install on the ViRGE/DX
  shows the same: `0x3EEABBC9` after copy and top-level tabs even with the
  driver failed.

## One boot that did not finish

The used Millennium clone, rebooted by the agent after the WININIT
staging, stayed at the Windows 98 logo for over eight minutes
(`matrox-millennium/host-after-wininit2.png`). WININIT had run (the
staged file was renamed). An 86Box hard reset booted to `enable-ok`.
That boot overwrote `V9XBOOT.INI`, so where the hung boot stopped is not
known. Not seen on any other boot here; recorded once.

## Later: vbe on a Millennium

On a fresh Millennium clone `vbe` installs the same way and reaches
`enable-ok` at 1024x768x16 through the BIOS's linear frame buffer
(`vbe-millennium/`; [record](2026-11-24-1.0-b5-b9-86box.md)).

take (no Riva 128 ROM, no SiS 6326, no Voodoo4/5), so they need a clean
physical machine. The release candidate's own zips.
