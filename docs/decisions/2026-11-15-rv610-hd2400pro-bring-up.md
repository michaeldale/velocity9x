# The Radeon HD 2400 Pro (RV610) joins the ati family: DirectDraw on its DMA engine, Direct3D and OpenGL through its CP, every probe passing

2026-11-15, remote-help machine M-NZHWBR (W9QI54F0), which until the
evening before held the HD 2600 XT (RV630, `1002:9588`) and now holds a
Sapphire Radeon HD 2400 Pro: `1002:94C3`, subsystem `174B:E370`. The
0.51.0 release checks found it: the 0.51.0 `ati` driver refused the card
(`Stage=fail-hardware-present`) and Windows showed "There is a problem
with your display settings". Evidence: `docs\probe\rv610-2026-11-15\`.

## The survey (read only)

V9XRVMM, taught `94C3`, through the RV630's register BAR:

| | RV610 here | RV630 (2026-11-13) |
|---|---|---|
| `CONFIG_MEMSIZE` | 256 MiB | 256 MiB |
| frame buffer in GPU space | `E0000000`-`EF000000` | the same |
| BAR0, BAR2 | `E000000C`, `F7E20004` (64 KiB) | the same layout |
| memory channels | one, 64-bit | |
| inactive quad pipes | `FE`: one pipe | `FC`: two |
| inactive SIMDs | `FC`: two | |
| CP | ME halted, PFP running | ME halted |
| DMA ring | off, idle | off |
| D1 | VGA mode (Windows' fallback) | VBE on D1GRPH |

## What differs from the RV630, and where it comes from

Linux `r600.c` `r600_gpu_init`, `CHIP_RV610` branches, and xf86-video-ati
6.14.6 `r6xx_accel.c`:

- one pipe and one tile pipe: `GB_TILING_CONFIG` `PIPE_TILING(0)`.
  From this card's RAMCFG `CCh` that gives `CB00h`, the value its BIOS
  left;
- 4 hardware contexts (ME_INITIALIZE), not 8;
- no vertex cache: `SQ_CONFIG` loses `VC_ENABLE`,
  `VGT_CACHE_INVALIDATION` is `TC_ONLY`, and vertex buffers are synced
  through the texture cache (`TC_ACTION_ENA`). The shaders keep
  `CF_INST_VTX`, as xf86's do on this chip;
- `SQ_MS_FIFO_SIZES` replaced by `08E00A0Ah`, 17/17 GS and ES GPRs,
  `VGT_GS_PER_ES` 48, `TC_L2_SIZE(8)`;
- xf86's thread split: 136 PS and 48 VS threads (RV630: 144, 40);
- microcode: linux-firmware's `RV610_pfp.bin` has the RV630's SHA-256
  (`c0f58b75...`), `RV610_me.bin` is its own (`566508c9...`), fetched into
  `build\external\rv610\firmware` and generated into
  `r6_cp_microcode.c`.

The driver keeps one R6xx path. `r6_3d.c` takes the chip as an argument
(`V9X_R6_CHIP_RV630`, `V9X_R6_CHIP_RV610`), with the RV610's
`gpu_init` table beside the RV630's in the same order. The HAL learns the
chip from a new identity bit, `V9X_DD_ENGINE_CAP_R6_RV610`, which the
RV610 row in `cedar_hw16.c` stamps, as the Evergreen rows stamp theirs.
The row shares the RV630's fill hook, which picks the caps by the active
row: a hook of its own put the family's `_TEXT` 13 bytes over its budget.
The host tests check every RV610 value against the sources above, and
were written to fail first.

## A trap on the way: Windows had saved 16 colours

After the 0.51.0 driver refused the card (boot 29), Windows wrote its VGA
fallback into `HKLM\Config\0001\Display\Settings` (`BitsPerPixel=4`,
640x480). At 4 bpp Windows runs `vga.drv` and never calls ours. Boots 34
to 36 therefore said nothing about either build: `V9XTRAIL.TXT` had no
entry after the owner's restarts, the 0.51.0 driver put back alone (boot
36) logged nothing either, and a marker written over `V9XBOOT.INI` before
boot 35 survived it. Setting the key back to 16 bpp at 1024x768 (boot 37)
brought the driver back. A card swap behind a refusing driver will do
this to any tester.

## Stage 1: DirectDraw (boot 37)

`V9XHW.INI`: `Adapter=ATI Radeon HD 2400 Pro (RV610)`,
`EvergreenEngine=claimed`, `EngineCaps=20000007` (fill, copy, flip, the
RV610 bit), `enable-ok`. V9XDDP at 16 bpp: fill, source copy, colour-keyed
fill and the four overlapping copies exact; 20 flips in 321 ms, 17 ms at
most (the RV630: 332 ms, 17 ms). `FlipPixelOk` reads 0, as on every card
([issue](../issues/2026-09-02-flippixelok-is-uninterpretable.md)).

## Stage 2: the CP and first draws (V9XR63D, boots 37-38)

V9XR63D, taught `94C3` and the chip argument, with `RV610_me.bin` as
`ME.BIN`:

| Draw | Boot 37 | Boot 38 (after `reset`) |
|---|---|---|
| solid | ME_INITIALIZE, ring test, draw, idle, put-back pass; 0 mismatches | |
| Gouraud | pass, 0 mismatches | |
| textured MODULATE | pass, 0 mismatches | |
| Z16 LESS | **fail**: 256 mismatches, the depth buffer all zeros | pass, twice; depth tiles `80008000` .. `40004000` |

The Gouraud and textured draws fetch their vertices through the texture
cache, so that difference is measured. The first-boot depth failure, gone
after a `reset`, matches the RV630's
([issue](../issues/2026-11-13-rv630-depth-constant-z.md)): the same
unexplained state after the CP's first load on a boot.

## Stage 3: Direct3D claimed (boot 39)

The whole `ati` set (8 of 8 hash-matched) by `run-release-checks.ps1
-Machine hd2600`: V9XD32 at its default depth and at 16 bpp, V9XGLP,
V9XGLIDP, V9XR3DP, V9XWPRS and V9XFBCMP all pass. V9XD32's T13-T16 pass
on the hardware HAL (T19 skips: no pixel shaders on R6xx here; T18 has no
T&L device, as on the RV630). The renderer name read "Radeon HD 2600 XT":
`d3d_core.c` now names it by the identity bit, and V9XGLP on boot 40 reads
`Velocity9x Radeon HD 2400 Pro`.

3DMark 2000, default benchmark (1024x768, 16-bit colour and textures,
16-bit Z, triple buffer), boot 40: completed, **2989** 3D marks, no hang
(`boot40-3dmark2000-score.png`). Recorded, not compared; no V9XTRACE ran,
so its draw and refusal counters were not read. 3DMark names the display
"Velocity9x VBE-generic display": the card's device node is still the one
the owner installed with the `vbe` INF, whose files the runner replaced
with the `ati` package's. A Have Disk with the `ati` INF, which now lists
`94C3`, would rename it; not done.
