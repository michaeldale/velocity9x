# A8U4I5 (Rage 128 Pro): V9XD32's new T20/T21 make its later T4 and T16 fail

**Resolved 2026-11-08: the driver, not the probe.** T20's and T21's
textures, placed by the HAL in blocks of their own, left DirectDraw's
heap placing T4's target 4 bytes past a 32-byte base, which the Rage 128
refused. The HAL now places an offscreen render target itself; T4 and
T16 pass at DDI 5 and 6 on boot 680
([record](../decisions/2026-11-08-render-target-placement-trinity-rage128.md)).
The "Not the driver" reasoning below was wrong: the probe change exposed
a driver fault rather than causing one.

Date: 2026-11-06. Machine: A8U4I5, Rage 128 Pro (1002:5046), ati
package. Found in the 0.37.0 release checks.

## What was seen

With the V9XD32 built from main (T20 and T21 added for the RS690,
judged on caps since 68c45d5c), the run on the Rage 128 fails T4Flat
and T16 at the default DDI, `/ddi6` and `/ddi5`. Failures are 4, 3 and
4. T20 and T21 pass on what the card advertises: T20Expected F3, T21Ok
F. The failing run:

- **T4:** `T4ClearHr=0x80004001` (E_NOTIMPL) on the offscreen device.
  Its draw leaves `T4Pixel=0`, so all 990 judged pixels inside are
  wrong.
- **T16:** the DX7 device reports FAIL.
- **Engine:** RunIdleTimeouts 0 and RunFifoTimeouts 0. Every stage
  between T21 and T4 (T9-T13) passes.

## Not the driver

| V9XD32 | Driver | T4Flat | T16 | Failures |
|---|---|---|---|---|
| main (T20/T21) | 0.36.0 release-check build, boot 669 | FAIL | FAIL | 4 |
| main (T20/T21) | 0.37.0 candidate `55a661a2`, boot 671 | FAIL | FAIL | 4 |
| 0.36.0 source (`5d95df34`) | 0.37.0 candidate `55a661a2`, boot 671 | EXACT | PASS | 0 |

Since 0.36.0, the only source changes outside RS690 files are RS690
dispatch hooks, each guarded by the RS690 being active. So the probe's
new tests leave something behind that breaks the later ones on this
card. The 0.37.0 driver is not at fault.

## Not known

T20 resets every render state it sets. The textures T20 and T21 create
(two 8x8 textures and a 32x32 mip chain) are held until stage
`11-release`. Video memory pressure on the Rage 128's heap is a
hypothesis, not a measurement. Whether an application could reach the
same state (a Clear refused with E_NOTIMPL after mipmapped and keyed
textures exist) is also not known.

## Next

Release T20's and T21's textures as soon as they are judged, or move
the two tests after T4 and T16, and see whether T4 and T16 recover.
If they do, find what the held surfaces cost the Rage 128's Clear.
