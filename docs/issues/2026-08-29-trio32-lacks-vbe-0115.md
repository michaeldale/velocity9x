# The Trio32 is offered 800x600x32 and its BIOS refuses it

Status: **open, measured, not a regression.** One mode of twelve, on a card
that has been binding to the `trio64` chip entry since the family merge. Found
by the first boot anyone has given a Trio32.

## The symptom

On `Win98SE-Trio32` (86Box `s3_trio32_pci`, 2 MiB, agent port 9875), selecting
800x600x32 gives `Stage=fail-hardware-vbe-mode` in `C:\V9XDIAG\V9XBOOT.INI`, a
fall back to 640x480, and a mode the Display applet offers and the machine
cannot enter.

Measured 2026-08-29, driver build `485f516-dirty`; see
[`docs/decisions/2026-08-29-s3-trio32-alias-guest.md`](../decisions/2026-08-29-s3-trio32-alias-guest.md).

## The cause

`ValidateMode` accepts the mode and should: 800x600x32 is 1,920,000 bytes and
fits 2 MiB. The refusal is the BIOS's, at INT 10h 4F02h. `V9XMODES.INI`
publishes the row normally:

```
Row0a=m=0115 g=800x600x32 p=3200 rgb=00ff0000,0000ff00,000000ff src=baseline
```

Two controls in the same matrix run narrow it to the mode number rather than
the depth or the resolution:

* 640x480x32 (VBE `0112h`) **passed** - the part does 32 bpp.
* 800x600x16 (VBE `0114h`) **passed** - 800x600 timing is fine.

So 86Box's Trio32 ROM `86c732p.bin` does not list VBE mode `0115h`. Every other
declared mode that fits 2 MiB passed, with GDI acceleration.

This is the failure mode the shared S3 mode table already names in its own
comment - "a VRAM check catches a mode too large, not a mode missing, so that
row would validate and then fail at 4F02h" - written about BARRY's missing
`0100h`. It is the second ROM to show it, and the first to show it for a
high-colour row.

## Why it is not a regression

The Trio32 publishes `5333:8811`
([`2026-08-29-s3-device-id-survey.md`](../decisions/2026-08-29-s3-device-id-survey.md)),
so it has matched the `trio64` chip entry and inherited its twelve-row mode
list since the family merge. The device-id aliases added on 2026-08-29 changed
nothing about which modes this card is offered. What changed is that the card
was booted.

## Why it is not fixed here

The one-line fix - drop `0115h` from the shared table - would cost every 4 MiB
S3 target a mode its BIOS does list, which is the same trade the `0100h`
paragraph refuses for Doom95. The general fix is the one that note also leaves
open: reconcile the declared list against the running BIOS's own mode list
rather than against VRAM alone. The driver already collects that list on
families with `MiniVddVbeCollect = $true`; this family assembles the collection
out, deliberately, because it hung a physical Trio64
([`2026-08-18-trio64-minivdd-boot-hang.md`](2026-08-18-trio64-minivdd-boot-hang.md)).

So the honest options, in order of cost:

1. **Record it and move on.** One mode, one emulated part, and the driver
   already fails safe: it reports a stage code and falls back to 640x480.
2. **Inventory the ROM** with `build-vbe-inventory.ps1` on this guest and
   publish the measured list, which would say whether anything else in the
   twelve is missing on this BIOS. Cheap, and it is the Stage 0 instrument this
   project already uses for exactly this question.
3. **Split the mode list** so a Trio32 declares its own. That needs the Trio32
   to be a chip rather than an id sharing the `trio64` entry, which needs the
   guest it now has - and it is only worth doing if step 2 shows the two lists
   genuinely differ by more than this one row.

Step 2 is the next action. Nothing should be removed from the shared table on
the strength of one refused mode.
